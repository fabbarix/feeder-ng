# Page-layout and check-ui guards: where a package adds its files

Add **your own** files below; never edit a shared one (`registry.mjs`, the facade `../page-layout-rules.mjs`, the driver, the base modes and rules files, `page-layout-seed/index.mjs`). Every mistake listed here stops the run and names the file.

- **Rule**: `rules/Pnn-<slug>.mjs`, `export default { id: 'Pnn', title, always, evaluate(m, { width, route, kind }) }`; `evaluate` returns `[{ rule: 'Pnn', message: 'Pnn …' }]`. Use the number reserved for your package (`PLANNED` in `registry.mjs`, plan §9) with its mode: `always: true` for "always fail", `false` for "by mode". Read your metrics as `m.yourKey ?? []`: the resize walk and older probes do not fill them. Fails on load: a file name that is not `Pnn-<slug>.mjs` or not `.mjs`, a number outside P1..P43, an id that is not the file's, a second module for an id, a missing `evaluate`/`always`/`title`, the other mode than the plan's.
- **Probe**: `probes/<slug>.mjs`, `export default { name, key, source, order?, minWidth?, soft? }`. `source` is page code (an IIFE string) and its value becomes `m[key]` for every rule. It runs by `order` (default 1000), from `minWidth` px; a `soft` probe that throws gives `null`. With `scenarios: [names]` it runs only on those scenarios' pages. With `dark: true` it runs again in the dark-scheme pass, and a rule's optional `evaluateDark(dm, ctx)` reports from those values (as P10 does). Fails: a repeated name, a key another probe fills (on load), a key the layout probe fills with a value other than null (at run time, as not inspected).
- **Scenario**: `scenarios/<slug>.mjs`, `export default { order?, scenarios: [...], setups: { name: async (h) => {} } }`. A scenario is `{ name, route, open? }` (runs at every profile viewport) or `{ name, route, start, widths, setup?, emulate?, rules? }`: `widths` are numbers or keys of `SCENARIO_VIEWPORTS` (`430`, `667x375`, `375x256`, `844x390-inset`); `setup` brings the page to its state (helpers of `helpers.mjs`); `emulate` is CDP calls made before the first navigation (a text size: `{ method: 'Page.setFontSizes', params: { fontSizes: { standard: 24 } } }`); `rules` limits the findings reported there. Rules see `ctx.scenario`. Run only yours: `scripts/check-page-layout.sh --scenario NAME[,NAME]`. Fails on load: a repeated scenario or setup name, a setup the module does not define or without widths, widths without `start`, an unknown viewport, a malformed `emulate` or `rules`.
- **Seed**: `scripts/test/fixtures/page-layout-seed/<area>.mjs`, exporting `order` (100 up) and `async seed(ctx)`; it runs after the base areas, by `order`. Write any id the guard needs into `ctx` (the ids file).
- **Mode line**: a file in `scripts/check-page-layout.modes.d/` (no extension needed), read after `check-page-layout.modes` in name order. Lines: `fail_routes=/route …`, `warn_routes=/route …` (warn wins), `default=warn|fail`, the warn bridge and the per-rule warn below. Any other line fails the run.
- **check-ui rule**: `scripts/check-ui.d/<slug>.sh` calls `register_rule NAME` and defines `rule_NAME()` (hyphens become underscores) using `viol`, `src_files`, `css_scan`, `code_match`. Its mode goes in `scripts/check-ui.rules.d/<slug>.rules` (`NAME=fail`, `NAME.fail_paths=web/src/…`); without one it warns. A mode line in a later file wins, but **`fail_paths` lines add up** (B9-07): every `NAME.fail_paths=` line, in `check-ui.rules` and in each rules.d file, adds its folders to the rule's fail paths, so a package lists only the folders it has cleaned (B9-08 to B9-10 each name their own) and never repeats or drops another package's. A folder listed twice counts once. Fails (exit 2): a name registered twice or shadowing a built-in, no `rule_NAME`, a non-`.sh` file in `check-ui.d`, an unknown rule or mode in a rules file.

## The warn bridge

`width<=N = warn until B9-NN` in a modes.d file turns every finding at a **profile** viewport N px wide or less into a warning, always-fail rules included, and the run prints `N px: K findings, warn until B9-NN`. Scenario findings (`<route>#<name>`, their own viewports) are never bridged. Delete the file and those findings fail again. No bridge ships at release (B9-55): the run is clean at 375.

## The per-rule warn

`Pnn@/route = warn until B9-NN` in a modes.d file (B9-13) turns the findings of **one by-mode rule** on **one route pattern** (exact, `:id` or a trailing `/*`, as `fail_routes`; the route's scenarios `<route>#<name>` included) into warnings. Every other rule keeps the route's mode, so prefer it to `warn_routes`, which waives every by-mode rule on the route. An always-fail rule cannot be named (the line is an error), and so are a pattern without a leading `/` and any mode other than `warn`. The run prints `Pnn@/route: K findings, warn until B9-NN` for each line, 0 included, so a line whose route is clean shows up for deletion. None ships at release (B9-55): every rule is always fail, so the line can only name a rule a later wave adds by mode.

## How the guard runs (fast-checks)

- **Seed once, probe on copies.** `scripts/check-page-layout.sh` seeds one server, stops it and copies its data dir to `build/page-layout-snapshot`. The work is split in **units** (`units.mjs`): a route of the route table at every profile viewport, a scenario at its viewports, a resize walk. Before every unit the worker's server restarts on a fresh copy of the snapshot (`unit-server.sh`, about 0.1 s), so **a scenario never sees another scenario's writes and never depends on the order it runs in**: write every setup to start from the seed alone, and never add a scenario that only undoes another (shop-complete-restore was dropped). Within a unit the server is shared (its widths, and the dark pass that replays the setup), so a setup may still remember what it did, to undo it on its next run; a module that keeps such state in a module-level variable exports `reset()` to forget it, and the driver calls every `reset()` at the start of a unit (registry `RESETS`; `pageLayoutUnits.test.ts` fails on a module with state and no `reset`).
- **Parallel workers.** `PAGE_LAYOUT_WORKERS` drivers (default: half the CPUs, at most 12), each with its own Chrome and its own server (ports from 61000 up, above the kernel's ephemeral range), take the units longest first (`--claims`, an atomic `mkdir` per unit) and write their results; `merge.mjs` prints them as one driver would, and fails as not run when a unit was never reported. `PAGE_LAYOUT_WORKERS=0` runs one driver against the seeded server, as before (a `PAGE_LAYOUT_GUARD_CMD` always does).
- **A fixed time of the week.** The seed server and the seeder run at Wednesday 15:00 UTC of the current week, the probe servers ten minutes later (`FEEDER_TEST_NOW`, refused without dev login), and every probed page reads the same clock (`test-clock.mjs`, injected before the page's scripts). No run crosses the seeded Household's midnight, and every run sees the same hour. `PAGE_LAYOUT_NOW=<ISO>` seeds at another instant (debugging).
- **Only what changed.** `--routes /a,/b` runs those route-table entries (and no scenario unless `--scenario` names some); `--changed-since <ref>` asks `scripts/lib/check-plan.mjs` which routes and scenarios the files changed since `<ref>` can reach: a feature's files reach the routes whose screens import them (the import graph of `web/src`), `ui/`, `app/`, `theme/`, the stylesheet, the guard and the seed reach every route, a scenario module reaches its own scenarios, and a Go package reaches the routes its area serves (`scripts/lib/check-areas.mjs`). `scripts/check.sh` with `CHECK_SINCE=<ref>` passes it on.
- Timings on the 24-CPU machine, quick profile, 649 probes: one driver 1000-1560 s; 6 workers 330 s; 12 workers 188 s; 16 workers 153 s.
- A fixture test that only reads route findings passes `--routes` instead of `PAGE_LAYOUT_ONLY`: on a static fixture every scenario's setup finds nothing and waits out its own timeout.
