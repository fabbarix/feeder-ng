# Receipts are read by the configured assistant

Status: **Accepted** (2026-11-13; the user's answers Q2, Q4 and Q5 and the release in [receipt-reading.md](../design/receipt-reading.md) §13, with Q1, Q3 and Q6 proposed and not asked). To ship in 1.0.0-beta.7 with the Scan redesign. Design: [receipt-reading.md](../design/receipt-reading.md). Spec: [functional-spec.md](../spec/functional-spec.md) decision 51 and §10.5.

The user asked: "allow the user to take a picture of the receipt and sent it to the configured assistant with the scan contents to fill prices, weights and corrections to the products." At the end of a shop a Member photographs the **Receipt** and Feeder asks the assistant the Admin configured for the Recipe Assistant ([ADR 0006](0006-recipe-assistant-calls-anthropic-from-the-server.md)) to match its lines to the Scanned list, then shows a **Receipt review** of proposed changes. This adds a second outbound data flow to the provider and a second structured output schema that must compile, so it is recorded here as ADR 0006 was for recipes.

## Decision

1. **Receipts go to the configured provider, from the server, through the Recipe Assistant's settings.** No second provider, key, model or switch: the Admin's base URL, key and model for the Recipe Assistant serve both, and the same availability check, the same Limiter and the same job rules apply. A receipt read counts as one read (one running read per User; 30 accepted reads per Household per rolling hour for non-Admins; kept 10 minutes; at most 3 per User) (Q3, proposed, not asked).
2. **What is sent** in one request: up to 4 photos (Q1, proposed, not asked) prepared as for recipes (JPEG, longest side at most 2,576 px, metadata and location removed), and one text block, wrapped as untrusted data, holding the Shop's name, the date, the currency and, for each grouped Scanned row, its index, Product name, barcode (empty for a weighed code), Base Unit, pack size, number of Scans, quantity, weighed flag and Price. **Never sent:** Ingredient names, Lines, Members, Users, other Shops, the Household's name, any Picture, the Shopping List. Logs carry the request id, token counts and timing, never the photos, the rows or the answer.
3. **Any Member may send** receipt photos, with the privacy note shown above the button ("The receipt photos and your Scanned list are sent to Anthropic to read the receipt. Feeder does not keep the photos."), the same as recipe reading (Q2). The Admin turns the whole assistant on or off; there is no separate "Receipt reading" switch.
4. **The photo is discarded after the read and never stored** (Q4). It lives in the request and the job's memory only, never on disk, in `/data/images`, in the phone's database or in the offline queue; the job drops it when the model call ends and keeps only the answer, for 10 minutes. A read needs a connection, so no photo is ever queued offline.
5. **Only today's shop can be read** (Q5): the current Scanned list, before Change Shop. The server loads the session's events by the phone's client UUIDs, for this Shop, applied and not undone, and computes a **fingerprint** over them; an apply whose fingerprint no longer matches (a Scan, an Undo or a Price edit since the read, or a Change Shop) is `409 receipt_session_changed` with nothing written.
6. **The model proposes; the server decides; the User applies.** The answer is checked by a pure `Finish` (sentinels mapped back, rows matched by the integer index the server gave, never by text, amounts validated, nothing else trusted) and turned into proposals by a pure `Propose`. Nothing is written until the User checks rows and applies them. The review defaults are Prices, Weights and Quantities checked, and Corrections, Shop and date, Not scanned and Not on the receipt unchecked (Q6, proposed, not asked). A whole-receipt discount is a note, never spread over Prices.
7. **The output schema is small on purpose, and a test holds it there.** In 1.0.0-beta.6 the Recipe Assistant's schema grew from 5 to 9 union-typed properties and every read failed with "The compiled grammar is too large"; earlier, optional fields nested in arrays compiled for 180 s and were refused as "Schema is too complex". The receipt schema is therefore written by hand (not projected from another schema), checked in as a golden file, and held to this rule:
   - every property required, and `additionalProperties: false` on every object;
   - **no unions**: no `anyOf`, `oneOf`, `allOf` or `type: [..., "null"]`; a missing value is a sentinel (`""` for text, `-1` for an amount or an index, `0` for a count, a weight or a pack size);
   - **flat**: one array of flat objects, with no array or object inside a line; no `$defs`, `$ref`, `pattern` or `format`; one small `enum`;
   - **under a budget**: at most 16 properties in total (the schema has 15: 5 on the receipt, 10 on a line), at most one array. A budget test walks the schema and fails above it, so a new field needs a deliberate change to the test and a run of the live test;
   - **the live test**: `TestLiveReceiptSchemaCompiles`, opt-in (`FEEDER_LIVE_SCHEMA_CHECK=1` with a key), sends the schema to the default model with a one-line message and `MaxTokens: 16` and passes only on success or "output too long". It never runs in CI, and is run once before the release. A second opt-in test reads a synthetic receipt fixture.
8. **Apply without a single transaction, with compensation.** The scan service is not one SQL transaction: a purchase composes the Stock, Catalogue and List ports, each with its own writes, and stays atomic by compensation (its undo list). Applying a receipt does the same one level up. It builds the whole plan first (validating before the first write), then runs it under the scan service's lock so no other phone's Scan interleaves, using only existing operations (set Prices, add Scans, Undo, correct a Product, create a Product for an Add) so Stock Lots, purchases, Prices, Shopping List ticks and Bought stay right with no new rules. Every step records its inverse (a new Scan, its Undo; an Undo, the original Scan again under a new id; a Price change, the previous Prices; a Product correction, the previous name and pack size), and the first failure runs the inverses in reverse and answers `500 receipt_apply_failed` with nothing left changed. New events carry ids derived from the read (`receipt:<readId>:<n>`), so a retried apply does not repeat. One live update is published at the end.

## The user's answers (2026-11-13)

- **Release.** Both the Scan redesign and receipt reading ship in **1.0.0-beta.7**, overriding the design's earlier beta.8 recommendation.
- **Q2.** Any Member may send receipt photos, with the privacy note shown, the same as recipe reading.
- **Q4.** The photo is discarded after the read and never stored.
- **Q5.** Only today's shop can be read: the current Scanned list, before Change Shop.
- **Q1, Q3 and Q6** were not asked; the design's proposals stand: up to 4 photos, reads share the Recipe Assistant's limit, the review defaults as in decision 6.

## Considered options

- *A separate "Receipt reading" setting, provider or key*: a second place to configure and to leak a key, for one more call to the same provider. Rejected: the Admin's choice to turn the assistant on already covers sending photos.
- *Keeping the photo with the session as a record*: needs storage, a retention rule and a deletion path for a document that shows the Household's purchases and often a card's last digits. Rejected (Q4); the Scanned list and the Prices are the record.
- *Reading an earlier session's receipt*: needs the server to keep and show past Scanned lists, which the redesign deliberately does not have (no `GET /api/scan/session`). Rejected (Q5).
- *Projecting the output schema from a shared one, as the Recipe Assistant does*: that is how beta.6 broke. Rejected for a hand-written schema with a budget test.
- *A single SQL transaction for the apply*: needs the Stock, Catalogue and List ports to accept a `*sql.Tx`, a refactor of three modules for one feature. Rejected here; recorded as a follow-up.
- *Applying the model's proposals without a review*: a misread line would change Prices and Stock silently. Rejected: nothing is written until the User applies.
- *Matching rows by name*: the model could rename or merge rows. Rejected for the server's integer index.

## Consequences

- A second data flow of household purchases (names, barcodes, Prices, quantities, the Shop) and a photo to the provider; the deploy guide names it and the Recipe Assistant's settings page says Members can send receipts.
- New package `internal/receipt` (pure core: schema, prompt, `Finish`, `Propose`, plan), a read service and routes sharing the Recipe Assistant's Limiter and client factory (`internal/recipeassistant/service/shared.go`), `ApplyReceiptPlan` in the scan service, and `UpdateProduct` on the Product port.
- New error codes: `no_receipt_found`, `receipt_session_changed`, `receipt_read_gone`, `scans_empty`, `receipt_apply_failed`.
- The apply depends on `PATCH /api/scan/prices` (SR1) and `Ensure` with a kind (H4) for adding a Supply.
- The apply is atomic by compensation, so a crash between a step and its inverse could leave a partial result; the fingerprint then no longer matches, and the User sees the Scanned list as it is and can correct by hand. A single transaction across the ports is the follow-up that removes this window.
- Not in this feature: keeping receipts, earlier sessions, spend reports, spreading a whole-receipt discount over Prices, creating a session from a receipt alone.
