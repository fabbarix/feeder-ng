## 3. Decisions made while writing the tests (the plan left them open or contradicted itself)

- **Read states** are the API names of plan §7: `fetching` (page reads start here), `preparing` (photo reads), `reading` (text reads start here), `checking`, `images`, `done`, `failed`, `cancelled`. There is no `queued` state: `StartRead` returns with the job already in its first state. `JobView.States` lists every state visited.
- **Overall cap**: 180 s from the start of the job (`service.DefaultOverall`, `Deps.Overall` for tests). It covers fetch, preparation, both model calls and images. Exceeding it, or any deadline in the adapter, is `assistant_unreachable`. Cancel is `cancelled`, not an error.
- **Order in `StartRead`** (the handler has already done user -> `Check`): availability (`assistant_off`, 503, for off, no secret key, key sealed under another master key; `photos_not_supported_by_model` when the model is known to lack image input) -> source validation (nothing is held or counted when it refuses) -> `Limiter.Acquire` -> job. `Service.Check` only delegates to `Limiter.Check`.
- **Photo validation** is split: synchronous (422): count 1..4, each photo exactly one of `dataUrl`/`url` (else 400), data URL must be `image/jpeg|png|gif|webp;base64` (else `photo_unsupported`), decoded size at most 8 MB (`photo_too_large`); in the `preparing` state (job `failed`): bytes that do not decode (`photo_unsupported`), pixel bomb (`photo_too_large`), URL fetch failure (`photo_unavailable`, generic, no cause). This resolves plan §7 listing `photo_unsupported` among 422s.
- **Photo indexes are 0-based** on the wire (`photos/{index}`, `photo: {index, recipe}`, `review.photos[].index`), like `$.recipes[i]`. The BDD says "photo 2 for Recipe 1" for index 1, recipe 0.
- **Settings PUT errors** are `422 {"error":{"code":"invalid_settings","errors":[{"field","code"}]}}`; fields: `enabled`/`apiKey` for `secret_key_missing`, `baseUrl`, `model`, `apiKey`. `models` and `test` answer the bare code (`key_required_for_new_base_url`, `base_url_*`, `api_key_refused`). A refused key on `models`/`test` is `422 api_key_refused`. The BDD step "the answer is 422 X" matches the top-level code or any `errors[].code`.
- **Unreadable saved key** (master id differs or GCM fails): `apiKeyReadable: false`; `models`/`test`/reads never use it (`api_key_required`); a re-entered key fixes it.
- **Connection test checks** are `key`, `model`, `output`; their `code` is the read error code (`assistant_bad_key`, `assistant_model_unavailable`, ...). A failing check is still HTTP 200 with `ok:false`.
- **Effort**: the service sends `Effort: "medium"` only when the model's `ModelInfo.Effort` is true (looked up once per client, failures mean none).
- **Logging**: one line per call and per read with read id, User id, source kind, page **host only**, photo count, model, status, request id, token usage, outcome code. Never the key, source text, page path/query, output text or photo bytes (tested).
- **Finished jobs** are kept 10 minutes after finishing, at most 3 per User (newest). Jobs are per User: another User gets 404 on GET and DELETE.
- **Redirects** are refused by the adapter's HTTP client, so the key cannot leave the saved origin by a redirect (tested with a redirecting server).

### Candidate photos, as amended by the review (replaces plan §3.5/§7 wording on drop timing)

- A failed Confirm calls `Sessions.Restore(rv)`; **photos travel with the restored Review** (`Review.Photos`). They are dropped only by a **successful Confirm** (a `Take` that is not restored), `Close`/`DELETE`, idle TTL (1 h) or eviction past `MaxUserReviews`. Plan §7's "dropped when the call ends, success or not" is superseded. A bad `photo` choice or `import_not_ready`/`import_stale` therefore leaves the Review and its photos, and a retry with the photo succeeds (test "failed Confirm, then retry with the photo, succeeds").
- `Sessions.Photo` (like `Get`) **renews the idle timer**: a User looking at thumbnails keeps the Review alive (tested).
- **Memory bound**: candidates are stored shrunk to `recipefile.CandidateMaxSide` = 1,600 px on the long side (JPEG, no metadata; the 2,576 px prepared photos are only for the model) **and** a per-User cap `recipefile.MaxUserCandidateBytes` = 16 MiB over all open Reviews, counting restored Reviews. Past the cap the User's oldest Reviews lose their photos first (the Reviews stay open); a single Review over the cap on its own opens without photos. Worst case per User: 5 Reviews x 4 photos, still at most 16 MiB.
- **Authorisation**: `Photo(userID, id, i)` is scoped by owner like `Get`; another User, an Admin, or an unknown id gets 404, anonymous gets 401.
- **WithPhoto** (pure, in `recipefile`): the chosen candidate goes through `imaging.Process` to become the Recipe's image at `$.recipes[i].image`; out-of-range index/recipe, no candidates (non-photo review) and undecodable photos wrap `ErrPhotoChoice`, which the handler answers `422 validation_failed`, field `photo`.
