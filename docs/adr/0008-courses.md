# A Meal Slot serves ordered Courses, each its own Planned Meal; a Whole meal in the main Course covers the rest

Status: **Accepted** (2026-11-11; amended the same day with Course Attendance, optional Courses and the cooking timeline, points 7 to 9). Spec: [functional-spec §3.1, §7, §8, §11, §16 and decisions 29 and 30](../spec/functional-spec.md). Cool-down and Variety Rules became soft at the same time: [ADR 0009](0009-soft-cool-down-and-variety.md). Plan: [docs/dev/design/crs-plan.md](../dev/design/crs-plan.md). Amended by [ADR 0013](0013-bought-planned-meals-held.md) (points 2 and 8, Bought Planned Meals) and [ADR 0014](0014-meal-slot-on-one-date.md) (point 8, Guests and a date nobody eats), both Proposed.

Until now a Meal Slot on a date held exactly one Recipe: one Planned Meal per `(date, Meal Slot)`. A Household that eats a Main with a Side, or a Starter and a Dessert at Sunday Lunch, had to fold them into one Recipe or leave them out of the plan, the Shopping List and the Stock maths. Feeder now has **Courses**:

1. **One Planned Meal per `(date, Meal Slot, Course)`.** The Household defines its Courses in Settings, with an order (seeded: Main, Side, Starter, Dessert). A Recipe is marked with one or more Courses; a Meal Slot lists the Courses it serves, in its own order (Dinner = Main, Side). Each Course of a slot on a date is its own Planned Meal: planned, swapped, Pinned, marked Cooked or Not cooked, and with its own Batches, Leftover and Reheat. The Planned Meal key gains the Course, and so do every record keyed by it: Leftover sources, Couldn't plan reasons, Slot Rules, Cook Mode timers and Advance Step marks, and the Advance Step reminder keys. A Course is filled only by a Recipe marked with that Course (**Course fit**), fresh or as a Leftover.
2. **Whole meal.** A Recipe may be marked **Whole meal** (a one-pot Recipe, most Ready Meals): a Recipe that needs no other Course beside it. When the Planned Meal in a slot's **main Course** is a Whole meal (fresh or from its Leftover), that slot's other Courses **that hold no Planned Meal** are **covered** on that date: the planner leaves them empty, removes any unpinned, unresolved Planned Meal there first, and records no Couldn't plan for them. Covered is derived from the main Course's Planned Meal and the other Course's emptiness; it is not stored. Pinned, Cooked and Not cooked Planned Meals in the other Courses stay (a User's choice wins), and a User may still set (and so pin) a Recipe in one of them. Such a Course is **not covered**: it is shown, counted on the Shopping List and reminded about like any other Planned Meal, and it never has a Couldn't plan reason. While one exists the planner does not pick a Whole meal (fresh or Leftover) for that slot's main Course. In any Course other than the main Course a Whole meal Recipe is an ordinary Recipe.
3. **A Ready Meal maps to Whole meal by default, not by rule.** Ready Meal does **not** imply Whole meal, for two reasons: the flag is needed anyway for one-pot Recipes that are not Ready Meals (a stew, a traybake), so it exists on its own; and a Ready Meal in the main Course may still want a Side (a frozen pizza with a salad), which a rule would make impossible to plan. So Whole meal is its own stored flag, and marking a Recipe as a Ready Meal switches it on when the Recipe's Courses include the main Course; the User can switch it off. On upgrade every existing Recipe gets the main Course, and every existing Ready Meal is marked Whole meal, because until now a Ready Meal was the whole slot. A Recipe File without `wholeMeal` follows the same default.
4. **The main Course is a flag on one Course.** Exactly one Course carries it (a partial unique index), seeded on Main. It is what Course-less data falls back to (existing Recipes, Meal Slots and Slot Rules on upgrade; a Recipe File without `courses`; an unknown Course name at Import Review, unless the User picks another) and where Whole meal applies. **Renaming** it changes nothing else: every record points at the Course id. It **cannot be removed** while flagged (`409 course_main`): the Admin first gives the flag to another Course (**Make main**), which moves the flag in one step and changes no Recipe, Meal Slot or Planned Meal. Whole meal Recipes then cover only when planned in the new main Course.
5. **Removing a Course** (Admin, Settings > Courses) follows the Archived pattern of Recipes and Products:
   - The main Course and the last Course cannot be removed.
   - A Course that **any Planned Meal or Leftover** refers to (any state, past ones included) cannot go for good: Delete answers `409 course_planned` and the UI offers **Archive** instead. An archived Course leaves the Courses list, every picker and the planner, and is taken off every Recipe, Meal Slot and Slot Rule; its history keeps its name, and it can be unarchived (it comes back to the list, not to the Recipes and Meal Slots it was taken off).
   - A Course that was not planned is removed for good.
   - In both cases the Admin picks a **replacement Course** (default: the main Course) for the Recipes and Meal Slots that would be left with no Course; Recipes and Meal Slots with other Courses just lose it. Unresolved Planned Meals in that Course from today on are removed and their slots replanned; Pinned ones are listed in the dialog before it is confirmed. Slot Rules on that Course are removed and listed too. All of it is one transaction.
6. **Planner semantics.** The planner walks `(date, Meal Slot, Course)` cells: slots in time order; within a slot the main Course first (it decides covering), then the slot's other required Courses in the slot's order, then its optional Courses in the slot's order (point 7). Cool-down, recency and Variety Rules count a Recipe across Courses (it is the same Recipe in any Course), and one Recipe fills at most one Course of one slot on one date. Cool-down and Variety Rules are soft when too few Recipes fit ([ADR 0009](0009-soft-cool-down-and-variety.md)). Slot Rules target one Course of a slot. Leftover first works per cell, with Course fit and the same two rules as fresh Recipes: one Recipe per slot and date, and no Whole meal in the main Course while another Course of the slot is Pinned, Cooked or Not cooked. Each Course needs the portions of its own **Course Attendance** (point 8) and cooks its own Batches for them. Details are in the spec, §7.2.
7. **Optional Courses.** A Course on a Meal Slot may be marked **optional** ("Dinner = Main, Side, Dessert (optional)"). An optional Course is planned when a Leftover fits it or a fresh Recipe fits it **without breaking a rule**; otherwise it is left empty, silently: no Couldn't plan reason, no row on Today, the Plan or the board, nothing on the Shopping List. It is never filled by a relaxed pick (ADR 0009, point 5), and No Recipes for this Course is never recorded for it.
   - *Where the flag lives:* on each Meal Slot's Course (`meal_slot_courses.optional`), not on the Course. The same Dessert is optional at a weekday Dinner and expected at Sunday Lunch, and a flag on the Course could not say that; it also sits beside the slot's Course order, which is already per slot, and the multi-day editor (R15) applies it like the order.
   - *At least one Course of a slot is required* (`422 courses_all_optional`), so a slot can never go empty without a word. The main Course may be optional when another Course is required.
   - *Walk order:* required Courses first, so an optional Course never takes a Recipe or an Ingredient remainder that a required Course of the same slot could use.
   - *Whole meal:* covering is decided first and is unchanged; a covered optional Course is simply covered. An optional Course left empty does not count as kept for the Whole meal hold-back.
   - *Setup checklist and Couldn't plan:* unchanged; an optional Course never makes a step look missing and never appears in a cause.
   - A User may still set a Recipe in an empty optional Course (the slot menu's "Add Dessert"), which pins it as usual.
8. **Course Attendance.** Attendance stays owned by the Meal Slot (usual, and per date), and the Members who eat each Course of the slot are the slot's Attendance **less the Members who opt out of that Course** ("Sam opts out of Dessert"). The default is that nobody opts out, so a new Course, a new Member and an upgraded Household change nothing. Opt-outs are set per Meal Slot Course in the Meal Slot editor (the usual ones, applied by the multi-day editor like the Courses) and per date in the Date Attendance sheet (they replace that Course's usual opt-outs on that date only). Course Attendance decides that Course's portions, Batches and Leftover, whose Exclusions, Dislikes and Favourites count for it, and the portions its Leftover must cover. A Course that nobody eats on a date (everyone attending the slot opts out) is left empty silently, like an optional Course; a slot nobody attends is still Couldn't plan (Nobody attends) for each Course. Portion Factors stay per Member and slot: there is no per-Course portion size (open question 2, answered "not now").
9. **One cooking timeline per slot.** Cook Mode opens for a Meal Slot on a date and interleaves the Steps of every fresh, unresolved Course into one **cooking timeline**, with one cook, so that every Course is ready together at the end (spec §11). Each Course keeps its Recipe's own schedule (`schedule.Compute`, the Recipe File's scheduling rule) as one block; the blocks are placed as late as possible towards the slot time, and a Course whose Active Steps would clash with another's is moved earlier as a whole. So a slot with one fresh Course gets exactly its Recipe's schedule, as before: single-Course Households see no change in Cook Mode, the Next gate or Start cooking. Leftover Courses appear in it as their Reheat. Each Step still belongs to its Course: timers, Advance Step marks, Cooked and Not cooked stay per Course and keep the per-Course cook scope `meal:<date>/<mealSlotId>/<courseId>`, so the same timer shows in the timeline and in the single-Course view, which remains a filter of the same screen. This replaces the earlier "one Course at a time with a Course switcher" design. Start cooking is one reminder per slot, at the start of its timeline.

**Considered options**

- *Keep one Planned Meal per slot and give it several Recipes* (a list of Recipe ids on the Planned Meal): fewer key changes, but Pinned, Cooked, Swap, Leftovers, Reheat, Cook Mode and Stock deduction all work on one Recipe today; each would need a per-Recipe state inside one row, which is the same model with a worse shape. Rejected.
- *Model a Side as Ingredients of the Main* (or a "with" link between Recipes): no planner change, but the Household cannot vary the Side, plan a Dessert, or keep a Side's Leftover. Rejected.
- *Courses as Tags* ("side" Tag plus Slot Rules per Tag): no new concept, but a slot would still hold one Recipe, and Tags are free names created on first use, not an ordered household list with a main one. Rejected.
- *A Course list built into the code* (Starter, Main, Side, Dessert): simpler migrations, but the user decided the Household defines its own (Soup, Salad). Rejected.
- *Ready Meal implies Whole meal*: what the user first suggested, and no new flag to set. Rejected because the Whole meal flag is needed anyway for one-pot Recipes that are not Ready Meals, and because a Ready Meal in the main Course may still want a Side (a frozen pizza with a salad). Kept as the default instead (point 3).
- *Main Course by position* (the first Course in the household order is main): no flag, but reordering the list in Settings would silently change which Recipes cover a slot. Rejected in favour of an explicit flag.
- *Main Course by name* ("Main"): breaks on rename and on other languages. Rejected.
- *Whole meal covers when planned in the slot's first Course* (per slot, not the household flag): handles a slot without the main Course, but then a slot's Course order changes the planner's meaning. Rejected: one rule, one main Course.
- *Variety Rules and Cool-down per Course*: lets the same Recipe be a Starter today and a Main tomorrow, but that is exactly what Cool-down exists to stop, and a per-Course count would double every Tag limit. Rejected. A per-Course *default* Cool-down (the earlier open question 1 and spec §7.6) was also dropped: Cool-down and Variety Rules give way when too few Recipes fit instead ([ADR 0009](0009-soft-cool-down-and-variety.md)).
- *Leftovers tied to the Course they were cooked in*: simpler matching, but a soup cooked as Monday's Main is a fine Starter on Wednesday. Rejected in favour of Course fit on the Recipe.
- *Removing a Course with history for good* (reassigning old Planned Meals to the replacement): would collide with the `(date, Meal Slot, Course)` key where the replacement was planned too, and rewrites history. Rejected for Archive.
- *Per-Course Attendance as a full list per Course*: each Course would need its own copy of the slot's Attendance, a new Member would have to be added to every Course of every slot, and a date change to the slot would no longer reach the Courses. Rejected for opt-outs on top of the slot's Attendance (point 8), which keeps "people opt out" (decision 23).
- *Optional as a flag on the Course* (Dessert is optional everywhere): simpler, but cannot say "Dessert is expected on Sunday". Rejected (point 7).
- *Optional Courses filled by a relaxed pick* (like required ones): would plan the same Dessert most nights in a Household with two Desserts, which is what "optional" is meant to avoid. Rejected.
- *One Course at a time in Cook Mode with a Course switcher* (the earlier design): simpler, but the cook has to work out the interleaving by hand and the Side is ready 20 minutes early or late. Rejected by the user for the cooking timeline (point 9).
- *Every Step as late as possible on its own* (the first draft of point 9): ends more Courses exactly at the slot time, but it changes a single Recipe's schedule too (a Passive Step that `Compute` starts early would start later), so a one-Course slot would no longer match the Recipe's total time, Step captions or Start cooking. Rejected for whole-Course blocks.
- *A cook scope per slot* for the timeline: one scope for the whole slot's timers. Rejected: timers, marks and Cooked are per Course, a Step index is only unique within its Recipe, and the single-Course view must show the same timers; the timeline is a view over the Courses' scopes.

**Consequences**

- Two migrations, in the same release. **1400** rebuilds `planned_meals` (with the Course and ADR 0009's `relaxed` flag), `plan_unfilled` and `slot_rules` with the Course in their keys (keeping `planned_meals`' AUTOINCREMENT counter, so no Planned Meal id is handed out twice), adds the Course to Leftovers and cook scopes, adds `meal_slot_courses.optional` and the Course Attendance opt-out tables, seeds the four Courses, gives every Recipe, Meal Slot and Slot Rule the main Course and marks Ready Meals Whole meal. **1410** rewrites the stored Advance Step reminder keys; it ships with the notification change that writes the new keys, so the two never disagree. Neither can be undone; going back means restoring the snapshot `feeder-pre-1400.db` taken before 1400 and starting the image that ran before (plan, *Migration*).
- Every plan route gains a `{courseId}` segment; the course-less routes stay as aliases for the main Course only while the SPA moves over, and are removed before the release (the SPA ships in the same binary). The slot-wide actions get new paths (`…/{slotId}/all/not-cooked`, `…/all/cooked`), so a cached old SPA can never mark a whole slot by calling an old path. Plan, Today and board payloads carry a `courses` list per slot, with each Course's opt-outs, its optional flag and why it is empty when it is.
- Cook Mode scopes become `meal:<date>/<mealSlotId>/<courseId>`; Cook Mode itself opens per slot (`GET /api/cook/meals/{date}/{slotId}/all`, the cooking timeline) and the single-Course view stays. Start cooking and Confirm Cooked stay one per slot (Start cooking now fires at the start of the slot's timeline); Advance Step reminders are per Course.
- The Recipe File gains the optional `courses` (Course names) and `wholeMeal` (boolean or null, no default; null means absent); it stays version 1, and files without them import as above. The Recipe Assistant's output schema is a projection of the Recipe File schema, so it gains both as required properties; the model says "none" with `[]` and `null`, both pruned, so the import defaults apply.
- The Shopping List needs no new rule: it sums every Planned Meal, so every Course.
- A slot whose main Course is a Whole meal shows the covered Courses as part of that Planned Meal, not as empty or Couldn't plan; a kept Planned Meal in another Course of that slot shows as its own row, as usual.
