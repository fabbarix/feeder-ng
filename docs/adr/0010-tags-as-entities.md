# Tags are managed by the Household, carry a colour, and Slot and Variety Rules follow them

Status: **Accepted** (2026-11-11). Amends spec §4, §13 and §14; adds §4.1 and §17 and decision 32 ([functional-spec](../spec/functional-spec.md)). Plan: [tg-plan.md](../dev/design/tg-plan.md).

The user asked: "We need a way to manage tags (add/edit/rename); we should be able to also set the colors for a tag pill, to visually distinguish them."

What exists today (checked in the code at e87d71d):

- A Tag already has a row: `tags (id, key UNIQUE, name)` from migration 0300, and Recipes link to it through `recipe_tags (recipe_id, tag_id, position)`. `key` is `recipe.TagKey(name)` (trimmed, inner whitespace collapsed, lower-cased; no accent folding), and `name` keeps the first spelling.
- A Tag is created only on use (`upsertTag` in `internal/recipe/store`, called when a Recipe is saved or imported) and is kept when no Recipe carries it any more. There is no way to rename, recolour, merge or remove one: a typo ("fsh") lives for ever.
- **Slot Rules** and **Variety Rules** do not point at that row. They hold the Tag's **key** as text (`slot_rules.tag`, `variety_rules.tag`, both commented `recipe.TagKey`), with no foreign key. The planner matches them against each Recipe's Tag keys (`internal/plan/plan.go`). Nothing stops a rule from naming a key no Tag has.
- `GET /api/tags` (in `internal/recipe/httpapi`) answers `[{ "name", "recipes" }]`, ordered by name. The SPA shows Tags as neutral Chips: the Recipes list's Tag filter (`TagChips`), the Recipe editor's `TagInput` and its suggestions, and the Tag Selects of the Planning rules screen. Recipe tiles and the Recipe detail show no Tags yet (the first Tag only picks the generated tile's glyph).

So Tags are already rows; the change is that the Household now **manages** them, each carries a **colour**, and the rules that name a Tag **follow** what happens to it.

## Decision

1. **A Tag is a household entity: id, name, key, colour.** The `tags` table stays, with its ids and keys, and gains `colour`. `recipe_tags` is unchanged, so every Recipe keeps exactly its Tags and every Tag its Recipe count. A Tag may exist with no Recipe: it is offered in suggestions and pickers, and it stays when its last Recipe loses it (as today). Only the Household removes a Tag, on the Tags page. The key rule moves to the new package `internal/tag` as `tag.NameKey`; `recipe.TagKey` stays as a one-line call to it, so every caller keeps working.
2. **Any User manages Tags**, on **Settings > Tags** (`/settings/tags`), as for Storage Places and the Planning rules: add, rename, recolour, merge and delete. Tags are used by Recipes and rules, which any User already edits, so an Admin-only page would protect nothing.
3. **Slot Rules and Variety Rules keep naming a Tag by its key**, and the Tag repository (`internal/tag/store`) rewrites them in the same transaction as every rename, merge and delete. The planner, the plan repository, the rule API and the SPA's rule screens keep working on keys and need no change for this. A new rule must name an existing Tag (`422 tag_unknown`, task TG-R): with the page in place, a rule naming no Tag would be invisible and would never follow a rename. That check lives in the rule handlers (`internal/plan/httpapi`), through a small `TagExists` dependency wired at mount, not in `internal/plan/store`: the plan repository and the runner stay free of Tags, and their tests keep adding rules without a Tag row.
4. **Rename** changes the name and, when the key changes, the key; rules on the old key move to the new one in the same transaction. Until TG-R merges, a rule can name a key no Tag has, so the new key may already carry rules: the rename then applies the Merge outcome (point 5) to them rather than moving the rules blindly, so a duplicate Slot Rule is dropped and the existing Variety Rule wins (`variety_rules.tag` is its primary key). A new spelling with the same key ("fish" to "Fish") changes only the name. A name whose key another Tag already has is refused (`409 tag_name_taken`, naming that Tag), and the page then asks "Merge fish into Seafood?".
5. **Merge** moves one Tag onto another, in one transaction: every Recipe that carried the first carries the second instead (once, where it already had both), Slot Rules on the first move to the second (a rule that would then repeat one already on the same Meal Slot and Course is dropped), and the first Tag's Variety Rule moves to the second only when the second has none; otherwise the second keeps its own and the first's goes. The merged Tag is removed; the Tag it went into keeps its name and colour. The confirm dialog names every one of these outcomes before it applies them.
6. **Delete** takes the Tag off every Recipe and removes the Slot Rules and the Variety Rule that name it, in one transaction, after a crafted confirm that names them: "fish is on 12 Recipes. Deleting it takes it off them, and removes the Slot Rule Friday Dinner · Main = fish and the Variety Rule for fish." It is not refused when rules name the Tag. This follows the Courses removal, which lists the Slot Rules that go and removes them; the Tags equivalent of a Course's replacement is **Merge instead**, offered as the dialog's other action.
7. **Colour comes from a closed palette of ten**, not a colour picker: Tomato, Apricot, Mustard, Olive, Sage, Teal, Sky, Blue, Plum and Rose. The value is the palette id (`"sage"`), never a hex, so the colours can be retuned in one place. Each colour is three design tokens per scheme, `--tag-<id>-bg`, `--tag-<id>-fg` and `--tag-<id>-dot`, defined in OKLCH for light and dark in `web/src/styles.css`. Text (`fg` on `bg`) reaches at least 7:1 in both schemes (WCAG AAA for small text; AA needs 4.5:1), and the dot reaches at least 3:1 against the pill (non-text contrast). A test computes both from the token values. The colour picker is a crafted radiogroup of ten swatches with their names; there is no Custom swatch and no native colour input. A colour id the SPA does not know (say, a palette retuned later) renders as a neutral pill.
8. **A new Tag gets the next colour**: the palette colour carried by the fewest Tags, ties broken in palette order. So the first ten Tags get ten different colours, and colours repeat only past ten. This applies wherever a Tag is created: the Tags page (which preselects it, and the User can change it), the Recipe editor, Import and the Recipe Assistant. Migration 1440 gives the existing Tags the same colours they would have got had they been created in name order.
9. **The colour shows wherever a Tag pill shows**: the Recipes list's Tag filter, Recipe tiles (new: the first two Tags, then "+N"), the Recipe detail (new: every Tag, each leading to the Recipes list filtered by it), the Recipe editor's Tag field and its suggestions, the Tags page, and the Tag pickers and lists of the Planning rules screen. A Tag pill is the shared `Chip` with a Tag colour: the tinted fill, the colour's text and a leading dot. The dot, and the absence of a status glyph, tell a Tag pill apart from status chips, whose colours stay reserved (ux-brief) and are never used for Tags. Why chips stay neutral: "3rd fish this week" names the Tag (by its name, not its key) without its colour.
10. **The Recipe File and the Recipe Assistant contract do not change.** A Recipe File carries Tag names (`tags`, version 1), never colours or ids; export writes names; import matches each name to a Tag by key and creates a missing one with the next colour (point 8), through the one function that creates Tags (`internal/tag/store`, which `internal/recipe/store` calls). The Recipe Assistant's schema, prompt and golden files are untouched.
11. **Events.** Every Tag write publishes `tags` after commit. Rename, merge and delete also publish `recipes`, because they change Recipes: the SPA refreshes the Recipes it shows, and the planner replans (it already does on `recipes`), which rewrites stored why chips that named the old key. When the write also moved or removed a Slot Rule or Variety Rule, it then publishes `plan.invalidate {"reason":"rules_changed"}` through `plan.Invalidate`, last. That is what a rule edit on the Planning rules screen does: `runner.ChangeRules` plans with `ReasonRulesChanged` and `clearAll` (`internal/plan/runner/runner.go:222`), so unpinned Planned Meals placed by a rule that is gone are cleared and replanned. A `recipes` replan alone keeps them. It is published last because the runner coalesces pending invalidations and keeps the last reason (`Runner.Invalidate`). A recolour or an add does not replan. In the SPA, rename, merge and delete on the Tags page, and the `tags` event handler in `lib/tags`' `useTags`, invalidate `['tags']`, `['slot-rules']`, `['variety-rules']` and `['plan','tags']`, so the Planning rules screen shows the moved or removed rules.

## Considered options

- *Rules point at the Tag's id* (`slot_rules.tag_id`, `variety_rules.tag_id`): cleanest on paper, but it changes the plan repository, the rule API (`PUT /api/variety-rules/{tag}`), the planner adapter and the SPA's rule screens, all owned by Courses teams that are working now, for no gain the User can see. Rejected for key plus rewrite in the Tag repository (point 3).
- *A foreign key from the rules to `tags(key)` with `ON UPDATE CASCADE`*: would let SQLite rewrite the rules on rename, but needs a rebuild of `slot_rules` (rebuilt by 1400 a release ago) and `variety_rules`, turns every existing test that adds a rule for an unknown Tag into a constraint failure in other teams' code, and still needs explicit code for merge and delete. Rejected; the repository rewrite plus `tag_unknown` on create give the same guarantee on every path the app has.
- *Refuse Delete while a rule names the Tag*: a dead end that sends the User to another screen to remove rules one by one. Rejected for the Courses pattern (name what goes, remove it in the same transaction) with Merge instead as the other action.
- *A free colour picker, or Member-style swatches plus Custom* (Member colours are hex swatches with a Custom picker, drawn as a ring on a neutral surface so contrast never depends on them): a free colour on a filled pill cannot guarantee readable text in both schemes. Rejected for a closed, tested palette.
- *Prune unused Tags automatically*: would remove a Tag the User just added on the page, and the next import would bring it back in another colour. Rejected; unused Tags stay until the User deletes them.
- *Colours in the Recipe File*: would make a file depend on one Household's palette and break version 1. Rejected.

## Consequences

- Migration **1440** (`internal/db/migrations/1440_tags.sql`, task TG-A): `ALTER TABLE tags ADD COLUMN colour TEXT NOT NULL DEFAULT 'tomato'`; a `tags` row (name = key) for every key a Slot Rule or Variety Rule names that no Tag has; then every Tag's colour from its rank in name order. Plain SQL, no rebuild, no foreign-key pragma. Recipe counts are unchanged. A schema test fails when any table other than `slot_rules` and `variety_rules` has a column named `tag`, because the Tag repository rewrites keys only in those two.
- New Go packages `internal/tag` (pure rules), `internal/tag/store` and `internal/tag/httpapi`; `GET /api/tags` moves from `internal/recipe/httpapi` to `internal/tag/httpapi` and gains `id`, `key`, `colour` and the rule counts, keeping `name` and `recipes` so an old SPA still reads it (spec §17).
- New shared web code: `web/src/lib/tags` (types, API client, `useTags`, the palette, next colour and the merge and delete summaries as pure functions), the Tag colour on `Chip`, a `TagDot`, a `TagColourPicker` and a `TagSelect`; the Settings > Tags page in a new `web/src/features/tags`.
- Recipe payloads still carry Tag names (`tags: string[]`); the SPA finds each name's colour in `useTags` by key, so no Recipe, plan or import payload changes.
- `docs/spec/recipe-file.md` keeps its contract; its wording of `tags` ("Free labels") is reworded by team H after E1 merges, since E1 owns the file during Courses.
