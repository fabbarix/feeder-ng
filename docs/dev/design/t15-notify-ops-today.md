# T15 notify-ops-today: design

Scope: spec §1 (nightly backups, Docker/GHCR), §8 (To confirm), §12 (Web Push), the Today screen (ux-brief Home), release and CI workflows. Contract: [../architecture.md](../architecture.md), [ADR 0004](../../adr/0004-go-binary-sqlite-on-data-volume.md). Builds on household ([t1](t1-auth-household.md): quiet hours, time zone), stock ([t10](t10-stock.md)), and against the unmerged T11 (scheduler, Today tiles), T13 (service worker, scan session) and T14 (timer finished). Tests first (red); the Developer implements until `scripts/check.sh` passes.

## Decisions taken
- **No GCP.** VAPID keys are generated by the server on first start (`push.LoadOrCreateVAPID(dataDir)`) and kept in `/data/vapid.json` (mode 0600, JSON `{publicKey, privateKey}`; a corrupt file is an error, never silently regenerated, because that would orphan every subscription). The public key is served to the SPA.
- **Per device, per type, default off.** A subscription row belongs to one User and one browser endpoint; its enabled types are rows in `push_subscription_types`. Type ids (JSON and DB): `advanceStep`, `startCooking`, `confirmCooked`, `leftoverUseBy`, `stockSpoil`, `timerFinished`. A new subscription starts with nothing enabled unless `types` is sent. Re-subscribing an existing endpoint (same browser, new session or other User) updates it in place: it moves to the signed-in User and keeps nothing of the old User's choices (types are replaced by the request).
- **Endpoint safety.** The server POSTs to a user-supplied URL, so `push.ValidateEndpoint` accepts only `https`, no userinfo, and rejects IP literals in loopback, private, link-local or unspecified ranges and `localhost`. Keys must be base64url (`p256dh` 65 bytes, `auth` 16 bytes).
- **Pure due computation.** `notify.Compute(Facts, loc)` turns plain facts into `Candidate`s (`Key`, `Type`, `At`, text). `notify.Due(cands, now, quiet, loc)` defers quiet-hours candidates to the end of the window (`DeferQuiet`) and returns those whose send time has arrived and is not older than `Grace` (6 h; a Feeder that was down for a day does not replay stale reminders). Timer finished is never deferred. Quiet hours are `household.QuietHours` (start inclusive, end exclusive, wrapping midnight), evaluated in the household time zone; all candidate instants are exact (`time.Date` in the zone, so DST is right).
- **Rules.** Advance Step due: slot time − the step's lead time, for meals still `planned` that are not served from a Leftover. Start cooking: slot time − the Recipe's total time (same meals; omitted when total time is 0). Confirm Cooked: slot time + 2 h for meals still `planned`, including Leftover-served ones. Leftover Use-by: 10:00 household time on the Use-by date for `available` Leftovers. Stock about to spoil: 10:00 on the day before the go-off date, only if `UsedByPlan` is false (the fact source decides that from projected usage); lots with no go-off date are skipped.
- **Dedupe.** Key = `<type>:<identity>@<due instant UTC RFC 3339>`, so moving a slot yields a new reminder and a repeated tick yields none. `SentLog.Claim(subscriptionID, key)` is an atomic insert-or-ignore (primary key `(subscription_id, key)`); true means "first". Claim happens before sending (at most once); on a transient send error the claim is released so the next tick retries; `ErrGone` (HTTP 404/410 from the push service) deletes the subscription. `push_sent` rows older than 14 days are pruned by the nightly job.
- **Dispatcher.** `notify.Dispatcher` (ports only: `FactSource`, `SettingsSource`, `Subscriptions`, `SentLog`, `Sender`, `clock.Clock`) with `Tick(ctx)` (once a minute, run by a goroutine the module starts on `Deps.Context`) and `TimerFinished(ctx, ev)` (called from the events bus). The Scheduler is daily-only, so the minute tick is its own loop.
- **Backups.** `backup.Snapshot` runs `VACUUM INTO` a temp file in `<data>/backups`, verifies it (`PRAGMA integrity_check`), then renames to `feeder-YYYY-MM-DD.db` (household date; same-day re-run replaces it). Retention (`backup.DefaultPolicy`): keep the newest **7 daily** snapshots, plus for the older ones the newest snapshot of each of the **4 most recent ISO weeks** (so about 11 files, covering roughly a month). Only files named `feeder-YYYY-MM-DD.db` are ever considered or deleted. Nightly at **02:30** household time (`backup.NightlyAt`), before planning's 03:00. Admins also get `GET/POST /api/admin/backups` (list, back up now) so a backup can be taken before an upgrade. Restore is documented in deploy.md (stop, copy a snapshot over `feeder.db`, delete `-wal`/`-shm`).
- **Today data.** Counts decide layout, tiles come from their owners. `internal/today` adds only what nobody else serves: `GET /api/today/advance-steps` (Advance Steps due today, from the same `notify.FactSource` as push) and `GET /api/today/streak`. `today.Streak(today, lastWaste, since)` = whole days from the last `stock_waste` date (or from the earliest Stock Lot purchase when there is no waste) to today; waste today = 0. T14's board should reuse it.
- **Today vs Shopping List.** `composeToday` returns `{mode:'shopping'}` when a scan session is active, else ordered tiles. Order: next Planned Meal (xl, accent), spoiled "Throw out or keep?" (full, spoil tone), Advance Steps due (lg), To confirm, couldn't-plan notice, Leftovers, use-soon, streak. Empty tiles are dropped; when only the streak could show, the illustrated witty empty state is shown (plus the streak tile if > 0).

## Data (migration `1000_notifications.sql`, written in this commit)
`push_subscriptions(id, user_id, endpoint UNIQUE, p256dh, auth, label, created_at)`, `push_subscription_types(subscription_id, type)`, `push_sent(subscription_id, key, sent_at)`; all cascade with the subscription / User.

## API (all `r.User` unless noted; camelCase; errors `{"error":{"code","message","field"?}}`)
| Route | Result |
|---|---|
| `GET /api/notifications/config` | `{vapidPublicKey, types:[ids], quietHours:{start,end}, timeZone}` |
| `GET /api/notifications/devices` | `{devices:[{id, label, createdAt, endpointHash, types:{advanceStep:bool,...}}]}` of the signed-in User; `endpointHash` = hex sha-256 of the endpoint (lets the browser recognise "this device" without the server echoing secrets) |
| `POST /api/notifications/devices` `{endpoint, keys:{p256dh,auth}, label?, types?:{...}}` | 201 new / 200 updated device; 422 `validation_failed` field `endpoint`, `keys`, `types` |
| `PUT /api/notifications/devices/{id}` `{label?, types:{...}}` | 200 device (types given are set, others unchanged); 404 `not_found` for another User's device; 422 unknown type |
| `DELETE /api/notifications/devices/{id}` | 204; 404 |
| `GET /api/admin/backups` (Admin) | `{backups:[{name, size, createdAt}]}` newest first |
| `POST /api/admin/backups` (Admin) | 201 `{name, size, createdAt}`; prunes by policy |
| `GET /api/today/advance-steps` | `{steps:[{mealDate, mealSlotId, recipeName, description, dueAt, dueTime, slotTime, state}]}` (`dueTime`/`slotTime` are "HH:MM" in the household zone; `state` is `due` once dueAt has passed, else `upcoming`) due today (household date), soonest first, meals still planned |
| `GET /api/today/streak` | `{days}` |

## Seams on other teams (the interfaces this design needs)
1. **Facts (T11 plan + T8 recipes + T10 stock).** `notify.FactSource.Facts(ctx, now) (Facts, error)`; the real adapter `internal/notify/httpapi/facts.go` is the Developer's after T11/T10 merge: meals from `plan/store` (state `planned`, slot instant via `plan.SlotInstant`, `Recipe` name, Advance Steps with lead times and total time from `recipe`), available Leftovers from `plan/store`, lots from T10 `stock.Lots` with `UsedByPlan` from `service.Projected`/planned usage. Until then `facts.go` is a stub returning empty Facts.
2. **Scheduler (T11).** `app.Deps.Scheduler.Daily(name, "HH:MM", JobFunc)` and `Deps.Context`/`App.Close`. The Developer registers `backup.nightly` (`backup.NightlyAt`) and `notify.prune` (03:30) in Mount. Until T11 merges Mount registers nothing; BDD uses `POST /api/admin/backups` and the dispatcher handle.
3. **Service worker (T13).** The SW calls `registerPushHandlers(self)` from `web/src/features/notifications/sw/push.ts` (written and tested here; plain functions over a minimal `self` type). T13 only needs one import and call in its SW entry. The SW and `vite-plugin-pwa` config stay T13's.
4. **Scan session (T13).** `useScanSessionActive(): boolean` exported from `features/scan`, and the Shopping List screen element (`ShoppingListScreen`) for Today to embed. Wired in `features/today/seams.ts` (stubs return false / null until then).
5. **Timer finished (T14).** On timer end T14 publishes on `internal/events` topic `timers` the payload `{"changed":"finished","timerId":N,"label":"Pasta","recipeName":"Carbonara"}`. The module subscribes and calls `Dispatcher.TimerFinished`; all devices opted in to `timerFinished` get it, ignoring quiet hours. If T14 names things differently, only `httpapi/timers.go` changes.
6. **Today tiles (T11, T10).** Imported through `features/today/seams.ts`: T11 `NextMealTile`, `ToConfirmTile`, `CouldntPlanNotice`, `LeftoversTile`, `usePlan`, `useToConfirm`, `useCouldntPlan`, `useLeftovers`; T10 `SpoiledTile`, `useSpoiledLots`, `useStockTotals` (use-soon).
7. **Shared files touched (minimal, by the Developer):** `internal/modules/{notify,backup,today}.go` (own files), one link `NotificationSettingsLink` in `features/settings` SettingsPage, and `cmd/feeder` already runs `Scheduler.Run`.
