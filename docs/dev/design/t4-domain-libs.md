# T4: domain libraries (units, schedule, stock)

Three pure Go packages (stdlib only; no SQL, HTTP or `time.Now`). Other teams (recipes, import/export, stock, planning, shopping, cook) import them. Specs: `docs/spec/recipe-file.md` (Ingredients, Units, Steps and timing), `docs/spec/functional-spec.md` §5-6, ADR 0003.

## Layout and signatures
- `internal/units/units.go`: `Base` (`Gram`, `Millilitre`, `Piece`), `Conversion{Unit, ToBase}`, `Ingredient{Name, Base, Conversions}`, `ToBase(q, unit, ing) (float64, error)`, `Factor`, `GlobalFactor`, `IsConvertible`, `ParseBase`, `NormalizeName`, `NormalizeUnit`. Errors: `*UnconvertibleUnitError{Ingredient, Unit, Base}` (matches `errors.Is(err, ErrUnconvertibleUnit)`), `ErrInvalidQuantity`.
- `internal/recipe/schedule/schedule.go` (package `schedule`): `Step{Kind, DurationMinutes, LeadTimeMinutes, After}`, `Validate(steps) ValidationErrors`, `Compute(steps) (Schedule, error)` with `Schedule{Steps []Timed, Advance []AdvanceStep, TotalMinutes}`, `ScaleUses(uses, batches) ([]Use, error)`.
- `internal/stock/lot.go` (package `stock`): `Date` ("YYYY-MM-DD", `None` = ""), `Lot`, `NewLot`, `Deduct`, `CookedNeeds`, `SetTotal`, `Total`, `Totals`, `Spoiled`, `Keep`.

## Decisions
- **Units**: global units: `kg` for g only; `l, dl, cl, tsp, tbsp, cup` for ml only; the Base Unit itself is always valid; `piece` has no global units. An Ingredient-specific Unit Conversion overrides a global unit of the same name. Units match case-insensitively after trimming. Zero quantity is valid; negative/NaN/Inf give `ErrInvalidQuantity`. Name matching key: lower case, trimmed, whitespace runs collapsed to one space (Unicode-aware lower-casing).
- **Schedule**: `DurationMinutes == 0` means "not given" (Active without duration is instantaneous; Passive needs > 0; Advance needs `LeadTimeMinutes` > 0). Minutes are ints. `after` indexes are into the full step list (Advance Steps included) but may not point at an Advance Step (`after_advance_step`) nor at self/later/out of range (`after_not_earlier`). A non-Advance Step starts at max(cook-free time, End of every `after` Step); cook-free is the previous non-Advance Step's End if Active, its Start if Passive (0 initially). `TotalMinutes` is the maximum End over non-Advance Steps. `Advance` lists Advance Steps in step order. The spec's worked example (40 min) is a test. `ScaleUses` multiplies quantities by Batches (fractions fine; Batches must be a finite number > 0).
- **Stock**: quantities are Base Units (float64). `Deduct` order: lots with a go-off date first (soonest), then undated lots; ties by oldest purchase then lowest ID. It never mutates its input, drops emptied lots, floors at 0 and returns the `Shortfall` (the caller shows "Stock shows only 300 g ..."). `CookedNeeds` = Batches x line quantity, optional lines excluded, same-Ingredient lines summed, quantities already converted to Base Units by the caller via `units.ToBase`. `SetTotal` decrease reuses `Deduct`'s order; increase appends one new lot (ID 0, store assigns) purchased today, go-off = today + Shelf Life. A lot is spoiled when go-off < today (fine on the go-off date itself). `Keep` pushes the existing go-off date by 1 day (literal spec reading (confirmed by the spec: go-off + 1; a lot several days overdue stays spoiled after Keep and is listed again).
- **Deduct tolerance and bad input**: `Deduct` uses the same eps (1e-9) as `SetTotal`. A lot left with <= eps is dropped, and a Shortfall <= eps is 0 (0.1 + 0.2 covers 0.3). A NaN or +-Inf `need` is a no-op like `need <= 0` (no error return; nothing taken, no Shortfall, lots unchanged).
- **Conversion validation**: `ValidateConversion(base, c) error` returns `*InvalidConversionError{Unit, ToBase, Base, Reason}` (matches `errors.Is(err, ErrInvalidConversion)`). Checks in order: unit empty after `NormalizeUnit` (`ReasonEmptyUnit`), unit equals the Base Unit (`ReasonBaseUnit`), ToBase not finite or <= 0 (`ReasonBadToBase`). Overriding a global unit such as `cup` is valid. An invalid conversion is never used: `ToBase` returns the validation error for a unit matching it, `Factor`/`IsConvertible` report not found, and there is no fall-back to a global unit of the same name. Other, valid conversions are unaffected.
- **Imperial units (display only)**: named constants `GramsPerOunce` 28.349523125, `GramsPerPound` 453.59237, `MillilitresPerFluidOunce` 29.5735295625, `MillilitresPerUSCup` 236.5882365, `MillilitresPerUSTablespoon` 14.78676478125, `MillilitresPerUSTeaspoon` 4.92892159375, plus `DisplayFactor(base, unit)` (oz, lb for g; fl oz, us cup, us tbsp, us tsp for ml). For Weight Barcode Rules and imperial display. They are not recipe units: `GlobalFactor`, `Factor` and `ToBase` still reject oz, lb etc. (the recipe-file spec lists only kg, l, dl, cl, tsp, tbsp, cup).
- Waste recording and persistence are the stock store's job (not in these packages).

## Tests
Table-driven unit tests next to the code: `units_test.go`, `schedule_test.go`, `lot_test.go`. No Gherkin (pure packages). New exported functions (`ValidateConversion`, `DisplayFactor`) are `panic("TODO")` stubs until the Developer implements them. The files are gofmt-clean and `go vet` clean in a scratch module.
