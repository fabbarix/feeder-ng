Scope: functional-spec §3 (Planning Horizon, Planner Style, time zone), §7 (when it runs, Swap), §8 (Cooked, Not cooked, Leftovers, "To confirm"), §11 (Mark as Cooked entry point), §15 decisions 4, 14, 17. Builds on the pure planner ([t3-planner-core.md](t3-planner-core.md)), household ([t1](t1-auth-household.md)), recipes ([t8](t8-recipes.md): the `PlannedChecker` registry), products ([t9](t9-products-shops.md): last-bought pack sizes) and, once merged, Stock ([t10-stock.md](t10-stock.md), read-only on branch `team/t10-stock`). ## Decisions taken
- **Who may edit Slot Rules and Variety Rules: every signed-in User.** Spec §2 lists the Admin duties (allowlist, Members, Meal Slots, Shops, Weight Barcode Rules, household settings) and "every User can do everything else". Meal Slots stay Admin (T1). The plan itself (set, swap, confirm, Cooked, Regenerate) is for every User.
- **Addressing.** A meal is addressed by `{date}/{mealSlotId}`, never by row id: rows are rewritten on every run, the slot is the stable identity.
- **Pure / impure split.** `internal/plan` (pure) maps stored state to `planner.Input` (`BuildInput`) and a `planner.Result` back to row changes (`Reconcile`), and holds the Cooked rules. `internal/plan/store` is SQL only. `internal/plan/runner` orchestrates with small ports (`Sources`, `StockPort`) so it is unit-tested with fakes; the Developer writes the real adapters (`sources.go` over household, recipe, product, units; `stockport.go` over T10's `service`). Handlers are thin.
- **One transaction per run or action** (`Store.InTx`): read snapshot, plan, write. Cooked adds `StockPort.DeductCookedTx(ctx, tx, needs)` to the same transaction and calls `PublishDeduction` after the commit (T10's contract). Runs and actions are serialised by a mutex in the Runner (each rewrites the whole horizon).
- **What the planner is allowed to rewrite.** `Plan` fills empty slots and replans an unpinned Planned Meal only when the planner finds it invalid (archived Recipe, new Exclusion, too few portions, vanished Leftover source). It does not reshuffle valid meals: every trigger except Regenerate is a plain `Plan`. Exceptions, all by clearing unpinned meals first (`Snapshot.Clear`) and keeping the same seed: Swap/set/confirm clear the slots after the target (spec §7.3); a rule edit (`ReasonRulesChanged`) clears every unpinned meal, because a Slot or Variety Rule changes what is valid but the planner does not check rules on kept meals.
- **Unconfirmed meals whose slot is over** (waiting in "To confirm") are passed to the planner as Pinned: they still count for Stock projection, Leftovers and Cool-down, and are never replanned or dropped. They stay until Mark as Cooked or Not cooked (no auto-expiry: see QUESTIONS in the report). Empty slots whose time has passed are not planned.
- **Cooked date.** The actual Leftover is dated from the meal's slot date (`cookedOn`, Use-by = that date + the Recipe's or default Use-by days), not from the click, because confirmation can lag by a day. A Recipe override of `0` means same day.
- **Cooking a meal served from a Leftover** deducts no Stock and consumes its portions from that Leftover (floor 0); no new Leftover.
- **Leftover edit.** The sheet's ± moves in half portions; the server accepts any value in `[0, Batches x Yield]` (`plan.CheckLeftoverPortions`) else 422 `validation_failed` field `leftoverPortions`.
- **Pinned dependants.** When a Leftover shrinks (Cooked with fewer portions), is skipped (Not cooked), is discarded, or its source meal is replaced by Swap/set, the Pinned meals that no longer fit are unpinned (`plan.DependantsToUnpin`) so the run can replan them (spec §8.3 says "unpinned and replanned"). Unpinned dependants are replanned by the planner itself. A larger Leftover leaves the extra pending.
- **Auto-discard.** Leftovers with Use-by before today (household date) are discarded by `Runner.DiscardExpired` (first step of the nightly job and also callable on demand). T10 now has `RecordWasteTx`, so the waste row (reason `leftover_discarded`, ingredient nil, quantity = portions) is written in the same transaction as the discard (`TxWaster.RecordLeftoverWasteTx`); a failure rolls the discard back. `StockPort.RecordLeftoverWaste` (after the commit, failure logged) remains only as the fallback for a port without `TxWaster`. After the commit a stock waste event is published (topic `stock`), so Stock screens refresh. A Leftover is still good on its Use-by date.
- **Triggers** (spec §7.1). Nightly 03:00 household time via `internal/scheduler`; invalidations through the events bus (below); Regenerate on demand (bumps `plan_state.generation`, which seeds the jitter via `plan.SeedFor`). Invalidations are coalesced by one worker (`Runner.Start`); `Runner.Invalidate` never blocks and never runs inline; `GET /api/plan` reports `updating` while one is pending or running (the SPA shows a note, BDD waits on it).
- **Invalidation hook.** Other modules call `plan.Invalidate(bus, reason)` (publishes `plan.invalidate` `{"reason":...}`). Existing modules need no change: `plan.ReasonForEvent` maps their topics: `recipes` (Recipe edited/archived, preferences) -> `recipe_changed`; `household` `changed` in attendance, mealSlots, members, settings -> `attendance_changed`; `stock` `changed:"lots"` -> `stock_take` (also fires for scans and the Cooked deduction itself: harmless, a plain Plan is idempotent and coalesced); unpin and Cooked/Not cooked call the Runner directly. `Runner.Subscribe(ctx, bus)` feeds the worker.
- **Scheduler** (`internal/scheduler`, reusable). `Daily(name, "HH:MM", fn)`; `RunDue(ctx)` runs each job whose household-local time has passed and that has not completed for the household date (persisted in `scheduler_runs`, so a restart neither repeats nor skips; downtime gives one catch-up run, no backlog); a failing job stays due and is retried on the next tick. `Run(ctx, tick)` loops (default 1 min). It lives on `app.Deps.Scheduler` (small shared change, below); a module registers jobs in `Mount`, `cmd/feeder` starts `Run`. The household zone is injected with `SetZone` (planning's `Mount` sets it from the household settings). Tests drive it with a fake clock and `RunDue`.
- **Rules reference Tags by `recipe.TagKey`** (lower case, spaces collapsed); `BuildInput` normalises Recipe Tags and rule Tags alike, the API stores the key and shows it.
- **Recipes hard delete**: `plan/store.Checker` registers as `"planning"` (a Recipe with a Planned Meal, a Leftover or a Slot Rule counts as planned -> 409 `already_planned`).
- **Clearing before planning (Runner).** Besides `ReasonRulesChanged`, every run treats as empty (cleared first, `invalidOnRead` in `runner/snapshot.go`) the Planned Meals that are unpinned, in state planned, and not already cleared, and that the planner would keep although they are no longer valid. Exactly two cases: (1) nobody attends the slot (attendance portions <= 0): cleared whatever the meal is, Leftover-served meals included; (2) the slot has Slot Rules and the meal is fresh (not served from a Leftover) and its Recipe matches none of them (by Recipe id or Tag key): cleared. Leftover-served meals are exempt only from case 2. Pinned, Cooked and skipped meals are never cleared this way. Tests: `TestPlanRecordsWhyASlotCouldNotBePlanned` (attendance), `TestPlanClearsUnpinnedMealsThatBreakASlotRuleAndKeepsPinnedOnes`.
- **Rule edits are atomic.** Creating or deleting a Slot Rule and setting or deleting a Variety Rule write the rule and replan (`ReasonRulesChanged`) in one transaction through the Runner (a Runner method taking the rule write as its step), not as a store write followed by a separate `Plan`. A failed replan leaves the rules unchanged.
- **Scheduler time-zone guard.** A change of household time zone can make the same job look due twice for one household date (or move the local date back). `RunDue` skips a job when its last run date (`scheduler_runs`) is on or after the current household date (`last >= day`), so a job that already ran on a later date after a westward zone change does not run again. A job run is recorded under the household date it ran for. There is no mutex serialising runs: `s.mu` only guards copying the job list and zone, and ticks do not overlap because the single `Run` loop calls `RunDue` one tick at a time. Tests drive it with the fake clock and `SetZone`.
- **Known planner limit (not fixed here).** A Slot Rule never falls back and the walk does not reserve its Recipe: if an earlier slot takes the named Recipe, Cool-down can leave the rule's slot empty ("couldn't plan"). See the report.

## Data (migrations `0600_planning.sql`, `0601_scheduler.sql`, written in this commit)
`planned_meals(date, meal_slot_id UNIQUE together, recipe_id, batches, portions, state planned|cooked|skipped, pinned, from_leftover_id, from_date + from_meal_slot_id (the fresh meal that produced the Leftover), why_json, resolved_at)`, `leftovers(recipe_id, from_date, from_meal_slot_id, portions remaining, cooked_on, use_by, status available|discarded, discarded_on)`, `slot_rules(meal_slot_id, recipe_id XOR tag)`, `variety_rules(tag PK, max_per_week, not_consecutive_days)`, `plan_unfilled(date, meal_slot_id, reason, slot_rule_claimed, eliminated_json)`, `plan_state(generation)`, `scheduler_runs(job, ran_on)`. Deleting a Meal Slot cascades its meals, rules and reasons.

## API (JSON camelCase; all routes `r.User`; errors `{"error":{"code","message","field"?}}`)
Meal = `{date, mealSlotId, recipeId, recipeName, batches, portions, state, pinned, servedFromLeftover:{leftoverId|null, date, mealSlotId, recipeName}|null, why:[Why]}`; Why = `{code, value?, memberIds?, members?, ingredientId?, ingredient?, recipeId?, recipe?, tag?, date?}` (names added by the handler). Slot = `{date, mealSlotId, name, time, at, portions, attendance:[{memberId,name,factor}], meal|null, unfilled:{reason, slotRuleClaimed, eliminated:{considered, exclusion, coolDown, varietyRule, advanceStep}}|null, rules:[SlotRule]}`.

| Route | Result |
|---|---|
| `GET /api/plan[?from=&to=]` | `{today, horizonDays, updating, slots:[Slot]}`; default today .. end of the Planning Horizon; explicit dates may lie outside it |
| `GET /api/plan/to-confirm` | `{slots:[Slot]}` unconfirmed 2 h after the slot time, oldest first |
| `GET /api/plan/couldnt-plan` | `{slots:[Slot]}` with `unfilled`, slots not yet over |
| `GET /api/plan/leftovers` | `{leftovers:[{id, recipeId, recipeName, portions, cookedOn, useBy, fromDate, fromMealSlotId}]}` soonest Use-by first |
| `POST /api/plan/regenerate` | 200 `{placed, kept, unfilled}` |
| `PUT /api/plan/{date}/{slotId}` `{recipeId, batches?}` | 200 Meal (Pinned); set and swap are the same call. 404 `unknown_slot`; 422 `in_past`, `unknown_recipe`, `recipe_archived`, `validation_failed` (batches); 409 `already_resolved` |
| `POST .../confirm`, `POST .../unpin` | 200 Meal; 404 `not_found`; 409 `already_resolved` |
| `GET .../alternatives` | `{alternatives:[{recipeId, recipeName, batches, newLeftoverPortions, newLeftoverUseBy, score, why}]}` (3); 404 `unknown_slot`; 409 `not_swappable` |
| `GET .../cook` | `{meal, fresh, batches, yield, portionsNeeded, proposedLeftover, maxLeftover, leftoverUseBy, needs:[{ingredientId, ingredient, quantity}]}`; 404, 409 `already_resolved` |
| `POST .../cooked` `{leftoverPortions?}` | 200 `{meal, leftover|null, warnings:[{ingredientId, name, baseUnit, have, need, shortfall, message}]}`; 409 `already_resolved`; 422 `validation_failed` field `leftoverPortions` |
| `POST .../not-cooked` | 200 Meal (state skipped) |
| `GET/POST /api/slot-rules`, `DELETE /api/slot-rules/{id}` | rule `{id, mealSlotId, recipeId?, recipeName?, tag?}`; POST 201; 422 `validation_failed` (both/neither), 422 `unknown_reference`, 409 `duplicate_rule`; DELETE 204/404 |
| `GET /api/variety-rules`, `PUT/DELETE /api/variety-rules/{tag}` | rule `{tag, maxPerWeek, notConsecutiveDays}`; PUT 200 (422 `validation_failed` when it limits nothing or `maxPerWeek` is outside 1..21); DELETE 204/404 |

Events: topic `plan` `{"changed":"plan","reason":...}` after every run or action that wrote.
