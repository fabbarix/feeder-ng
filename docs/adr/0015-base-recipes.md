# Base recipes own an Ingredient, are expanded at read time, and join the cooking timeline as composed Steps

Status: **Accepted** (2026-11-12; the user's answers P1 to P7, all option A except P4 = C and P7 = B). **Target: beta.6**: nothing of it is built in beta.5. Design: [docs/dev/design/base-recipes.md](../dev/design/base-recipes.md). Spec: [functional-spec.md](../spec/functional-spec.md) decision 46 and §19, both marked "Scheduled for beta.6"; when beta.6 ships they are folded into §4, §6, §7.2, §8, §9, §11 and §13.

The user asked for **Base recipes**: a béchamel, a pasta frolla or a stock that other Recipes call for by amount ("500 ml Béchamel"), never planned on its own, nested at any depth, scaled from its Yield, covered from Stock first (a bought jar, a frozen batch), with every Ingredient inside counting for Exclusions, and with its Steps on the cooking timeline so it is ready just before the Step that uses it. Three architectural choices follow; each touches code that several teams share.

## Decision

1. **A Base recipe owns an Ingredient, and a Base recipe line is a line of that Ingredient.** `recipes.base_ingredient_id` (unique) marks a Recipe as a Base recipe and names its Ingredient; `recipes.yield_unit` gives its Yield a unit. The Ingredient is created with the Base recipe, follows its name, keeps a `batch` Unit Conversion equal to the Yield, and cannot be deleted or merged away while the Base recipe exists. A line calling for a Base recipe is an ordinary `recipe_lines` row of that Ingredient, with an optional `needed_at_step`. So Stock of a Base recipe is ordinary Stock Lots of its Ingredient: Products and barcodes, Scan, Stock-take, Shelf Life, Storage Places, Used from, waste, the picker and Unit Conversions all work unchanged. This is the Ready Meal's idea (spec §4), linked by id instead of by name. When a Base recipe gets the name of an existing plain Ingredient ("béchamel" on older Recipes, a jar in Stock), Feeder **asks** whether the Base recipe takes over that Ingredient, and the confirm names the Recipes it is on and its Stock. **Yes**: that Ingredient becomes the Base recipe's (`base_ingredient_id` points at it, its Stock Lots, Products and Exclusions stay), and all its lines become Base recipe lines at once. **No**: it is kept apart, and the Base recipe gets its **own** Ingredient, keyed `base-recipe:<recipe id>` in `ingredients.name_key` rather than by its name. With no same-name Ingredient the Base recipe always gets its own. The same ask comes when a Base recipe is **renamed** to a name an existing plain Ingredient has: the same confirm, naming the Recipes and Stock; Yes takes that Ingredient over and merges the Base recipe's former Ingredient into it (its Stock carries over), No keeps them apart. Plain lines of a kept-apart Ingredient become Base recipe lines only by an explicit **link**: one line at a time (re-point `ingredient_id`, remembering the old Ingredient in `recipe_lines.linked_from_ingredient_id` for Undo), or ticked in the **bulk link** list offered when a Recipe becomes a Base recipe. Once no line uses the old Ingredient, Feeder offers to merge it into the Base recipe's.
2. **Expansion happens at read time, in one pure package.** `internal/recipe/baserecipe` turns a Recipe into a need tree (Base Units, one Batch of the root, each Base recipe node scaled by `amount ÷ Yield` through `internal/units`, nested, cycle-checked) and offers `Flatten` (no Stock; each Base recipe Ingredient kept as an optional zero line), `Resolve` (Stock first), `ComposeSteps`, `NeededAt`, `FindCycle` and `MatchReference`. Nothing is denormalised except the cached total time, which the store rewrites for every Recipe that uses an edited Base recipe. The consumers stay thin adapters: the planner gets `Flatten` through `DBSources.Recipes` (no change to `internal/planner`: Course fit already keeps a Course-less Base recipe out, and Exclusions read optional lines); the Shopping List's `Need` gains `Made` and draws the Base recipe Ingredient before expanding the shortfall; Cooked runs `Resolve` against Stock before `DeductCookedTx`. Cycles are refused on every save.
3. **The cooking timeline sees composed Steps.** The recipe store composes each Recipe's cook Steps: each Base recipe's Steps form a block, inserted into the Recipe's Step list at the position (up to its Needed at Step) where `schedule.Compute` gives the shortest total time, ties to the latest; the Needed at Step waits for the block. `schedule.Compute` and `cook.Timeline` are unchanged, and timers, Advance Step marks and reminder keys keep using Step indexes, now of the composed list. Steps carry their Base recipe's name for Cook Mode. A block that Stock covers keeps its indexes but becomes zero-length and hidden.

## The user's answers (2026-11-12)

- **P1 = A.** Amounts scale with the Base recipe line; Step durations stay as written, as for Batches.
- **P2 = A.** A Base recipe carries only an Exclusion, stored as the Exclusion of its Ingredient; no Favourite or Dislike.
- **P3 = A.** Import Review preselects only an exact name match to an existing Base recipe or to a Base recipe in the same file, and the User still confirms; every other marked line waits for an answer.
- **P4 = C.** Scheduled for beta.6.
- **P5 = A.** No "Made it" action yet; a jar or a batch is a Lot added on the Pantry page.
- **P6 = A.** A plannable Recipe may be turned into a Base recipe after a confirm naming what goes (its Planned Meals from today, Pinned and Bought included, and its Slot Rules); Cooked history stays; its Leftovers stay until answered.
- **P7 = B.** Feeder asks whether the Base recipe takes over a same-name Ingredient, naming the Recipes and Stock it affects. Yes: all its lines become Base recipe lines and Stock carries over. No: it is kept apart, the Base recipe gets its own Ingredient, and the old one is linked line by line or by ticking it in the bulk link list, and offered for merge once no line uses it (point 1).

## Considered options

- *Stock as a Stock Lot kind* (`stock_lots.recipe_id`): every Stock path would gain a second kind, in files other beta.5 teams own, and a jar would have no barcode. Rejected for point 1.
- *Always its own Ingredient, never taking over a same-name one* (the original P7 = A): the safest for Recipes, but a jar already in Stock stays on an Ingredient the Base recipe cannot use, and the User must link every line and merge by hand. Rejected: taking over is offered, after asking, with the own Ingredient (non-name key), link and bulk link kept for a No.
- *Taking over a same-name Ingredient silently*: Stock carries over with no merge, but every line of that Ingredient becomes a Base recipe line with no say from the User. Rejected for point 1; it is taken over only after the confirm.
- *Base recipe surplus as a Leftover*: a Leftover is portions of a plannable Recipe that the planner serves; [ADR 0012](0012-leftovers-stay-leftovers.md) already rejected Leftovers as Stock. Rejected.
- *A separate line table for Base recipe lines* (`recipe_base_lines (recipe_id, base_recipe_id, quantity, unit)`): clearer in SQL, but Stock, the picker, Exclusions, Unit Conversions and the Recipe File would each need a second path for "a line that is not an Ingredient". Rejected for point 1.
- *Denormalising the expansion* (store each Recipe's flattened lines and steps, rewritten when a Base recipe changes): faster reads, but a second copy that every Base recipe edit, archive, Ingredient merge and import must keep in step, and it cannot be Stock first, which depends on the day. Rejected for point 2; only total time is cached, as today.
- *Teaching the planner the tree* (`planner.Need.Made`): its projected Stock and Ingredient Overlap would credit a jar in the Pantry. The planner is the busiest package of beta.5 and no user decision needs it; the Shopping List and Cooked are Stock first. Left for later.
- *Base recipe Steps as their own Course block in `cook.Timeline`*: would reuse the multi-Course placement, but blocks are rigid and placed only to end together at the slot time, not before a given Step of another block, and timers would need a scope per Base recipe. Rejected for point 3.
- *Inserting the block always just before the Needed at Step*: simpler, but a Base recipe with a long Passive Step (a ragù) would then delay everything after it. Rejected for the shortest-total placement.
- *Keeping the Recipe's own Step indexes and numbering Base recipe Steps after them*: indexes would never move, but `schedule.Validate` requires `After` to point at earlier Steps, so the list order and the index would have to differ through `schedule` and `cook`. Rejected; indexes move only when a Recipe in the tree is edited, as they already do when a Recipe is edited.

## Consequences

- Migration **1540** (`ALTER TABLE` only): `recipes.base_ingredient_id`, `recipes.yield_unit`, `recipe_lines.needed_at_step`, `recipe_lines.linked_from_ingredient_id`, a partial unique index. Kind rules are checked in Go.
- New package `internal/recipe/baserecipe`; the recipe store gains `NeedTree`, composed `Cook` Steps on `Get`, the cycle check and the kind changes (`/to-base`, `/to-plannable`); the Ingredient store gains guards; line link and unlink, link candidates and bulk link routes; `GET /api/recipes` gains `kind` (default plannable).
- `internal/plan/runner/sources.go`, `snapshot.go` / `courses_c2.go` (`needsFor`), `internal/shopping/shopping.go` and `httpapi/wiring.go`, `internal/cook/service/adapters.go` and `internal/notify/facts/facts.go` change as adapters; `internal/planner`, `schedule` and `cook.Timeline` do not.
- Recipe File v1 gains optional `baseRecipe`, `yieldUnit` (Recipe) and `recipe`, `neededAtStep` (line); the Recipe Assistant's output schema follows by projection, and the Agent Prompt gains two rules.
- A Member's Exclusion of a Base recipe is stored as the Exclusion of its Ingredient.
- The planner's scores see a Base recipe as made from scratch (known limitation).
