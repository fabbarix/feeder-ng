# T12 import-export: design

Scope: functional-spec §13, recipe-file.md in full (Import Review, Images, Agent Prompt), GLOSSARY Recipe File / Import Review / Agent Prompt. Contract: [../architecture.md](../architecture.md). Builds on T2 (Ingredient store, `ingredient.Search`, Unit Conversions), T8 (Recipe store, `internal/imaging`) and `internal/units`. Never copies them.

## Decisions taken
- **Single source for the spec.** `docs/spec/spec.go` (package `spec`) embeds `recipe-file-v1.schema.json`, `examples/recipe-file-example.json` and `recipe-file.md`. Nothing is copied into Go. The Agent Prompt template is cut out of `recipe-file.md` (the four-backtick `text` block under "Agent Prompt") at run time by `recipefile.ExtractTemplate`, so editing the spec edits the app.
- **Schema validation** uses `github.com/santhosh-tekuri/jsonschema/v6` v6.0.3 (pure Go, 2020-12; **adds it to `go.mod`/`go.sum`; also `golang.org/x/text`, indirect**; the Developer runs `go mod tidy` to make it direct). The schema's `$id` resource is registered from the embedded bytes, so no network is used. Errors are flattened into `PathError{path, message}` with paths like `$.recipes[0].ingredients[1].quantity` (a missing required property reports the parent object and names the property), ordered by path, all listed.
- **Version first.** `version` is read from the raw JSON before the schema runs: anything other than the integer `1` is `VersionError` (`422 unsupported_version`), even when the file is also otherwise invalid.
- **Stateful Import Review, held in memory.** Opening a file parses it, resolves every image once (downloads are slow and must not repeat on each answer) and stores `{file, images}` in `recipefile.Sessions` under a 128-bit random id, owned by the User, TTL 1 h idle, at most 5 per User (oldest dropped). A restart drops them (the User uploads again; acceptable for a family app, and no table or migration is needed). **No migration** for this team. The review is a pure function of `(file, existing data, decisions, images)`: every `plan` call recomputes it from the *current* data, and `confirm` recomputes it again inside the write, so nothing stale can be saved.
- **Decisions are sent whole each time** (`{ingredients, conversions, recipes}`), the server keeps none. A decision for a key or index not in the file is ignored.
- **Ingredient matching.** Key = `units.NormalizeName`. Exact key match uses the existing Ingredient. A different Base Unit between the file's definition and the existing Ingredient is a `conflict`: unresolved until the User either *uses* the existing Ingredient (the unit check then prompts for any unit it cannot convert) or *creates* under a new `name` (create without a different name does not resolve it). No exact match: `ingredient.Search` suggestions (score >= 0.6); status `suggested`, **default is to create** from the definition (never silently merge); the User may pick a suggestion. No match and no definition in the file: `undefined`, needs `create` with a `baseUnit` or `use`. An Ingredient used only by skipped Recipes is not listed or created.
- **Existing Unit Conversions win, also at write time.** `store.Apply` adds an `AddedConversion` only if the Ingredient still lacks that unit inside the transaction. If it gained the unit after the review (any `toBase`), the file's/answered one is **skipped**: no overwrite, no error (not `import_stale`), not counted in `ConversionsAdded`, and the Recipes are still validated against what is there. Rationale: the User already chose that factor; failing the whole import for it helps nobody.
- **Existing Unit Conversions win (review time).** For a matched Ingredient, file conversions for units it lacks are added at Confirm; a unit it has with another `toBase` is kept and reported as warning `conversion_differs`. Shelf Life of an existing Ingredient is never changed by an import.
- **Unit check** runs against the resolved Ingredient (existing + added conversions, or the new definition + answers). One `UnitPrompt` per (Ingredient, unit) with all uses in `usedBy`. Answers are validated with `units.ValidateConversion`; an invalid answer is a Problem and leaves the prompt open. Answers are saved as Unit Conversions of the Ingredient (existing: added; new: part of its creation).
- **Recipe conflicts.** Same `units.NormalizeName` as any existing Recipe (archived too) = `conflict`, which needs an explicit `replace | keep_both | skip` (no default, like a Base Unit conflict: the User decides). `replace` overwrites in place (id, archive flag and Member preferences survive); `keep_both` imports as `"<name> (n)"`, n = the smallest number >= 2 not taken (also by other Recipes of the file); `skip` leaves it out. Two Recipes of one file with the same name are a Problem at `$.recipes[i].name`.
- **Recipe checks** reuse `recipe.Input.Validate` (limits and `schedule.Validate`) against the resolved Ingredients, so an imported Recipe can never be one the editor would refuse. First problem per Recipe becomes a `Problem{path "$.recipes[i]."+field}`. Fractional `durationMinutes` / `leadTimeMinutes` (the schema allows numbers) are rounded **up** to whole minutes.
- **Images.** Data URLs go through `imaging.ProcessDataURL` (8 MB, declared type, pixel caps, WebP, 1600 px). `https` URLs go through `recipefile.Fetcher`; any failure (or a missing fetcher, non-https scheme, more than 50 downloads, cancelled context) drops the image and adds warning `image_failed` with its JSON path; the import continues. Files are written to the image store only inside `Apply`, and deleted again if the transaction fails.
- **Image warnings are generic.** The `image_failed` message never contains the fetcher's error text, so a resolved address (or "refused" vs "unreachable") is never revealed; every download failure has the same message (e.g. "the photo could not be downloaded"); the cause is for the server log only.
- **SSRF (`recipefile/imagefetch`).** Own `net.Dialer` flow: parse URL (https only, no userinfo), resolve the host ourselves, require **every** resolved address to be allowed, then dial a validated IP (no second lookup, so no DNS rebinding), with SNI/verification for the original host. Blocked: unspecified, loopback, private (10/8, 172.16/12, 192.168/16, fc00::/7), link-local (169.254/16 incl. the metadata address, fe80::/10), CGNAT 100.64/10, multicast, IPv4-mapped forms, and also 0.0.0.0/8, NAT64 64:ff9b::/96, 6to4 2002::/16, IPv4-compatible ::/96 and site-local fec0::/10 (the whole range, whatever address it embeds). Redirects: at most 3, each hop re-validated (https, address); no proxy (`Transport.Proxy = nil`), no cookies. Response: 200 only, `Content-Type` image/jpeg|png|webp, <= 10 MB (declared and streamed), 15 s total timeout (dial + redirects + body). `Options.Allow`, `LookupIP` and `TLSConfig` exist only so tests can reach `httptest` servers on loopback; production uses the zero value.
- **Single-use Review (Sessions).** `Sessions.Take(userID, id)` removes the Review and returns it atomically (of N parallel Takes exactly one wins); `Sessions.Restore(review)` puts it back (same id and owner, idle timer renewed, counts against `MaxUserReviews`). Confirm does `Take` first, then `BuildCommit` and `Apply`; on **any** failure (not ready, stale, store error) it `Restore`s, so the User can retry; on success the Review stays closed. A second or parallel Confirm gets `404 not_found` (Review already taken) or `409 import_stale`; every Recipe is imported once, even though Recipe names have no UNIQUE constraint.
- **Write-time re-checks in `Apply` (all `ErrStale` -> `409 import_stale`, nothing written).** Inside the transaction: every created or keep_both Recipe name is compared (as `units.NormalizeName`, archived Recipes included, ignoring the Recipe being replaced and names created earlier in the same Commit) with the Recipe names now in the table; a name taken since the review is stale. A Recipe that no longer passes `recipe.Input.Validate` (e.g. a Unit Conversion it needs was removed) is stale too, not a 500.
- **Atomic Confirm.** `recipefile/store.Apply` writes new Ingredients, added conversions and Recipes in one SQL transaction and returns `ErrStale` (-> `409 import_stale`) when a precondition vanished (a Recipe to replace, an Ingredient to use, a name taken since). The Developer adds a small tx-level variant to the existing stores for this (`CreateTx`-style methods on `ingredient/store` and `recipe/store`; additive, listed in the report) rather than duplicating their SQL. `Apply` re-validates through `recipe.Input.Validate` with the just-written Ingredients.
- **Export** is a `GET` (read-only, a plain link downloads it): `?all=1` or `?ids=1,2` (positive integers, no blanks). Body is `recipefile.Marshal(Build(...))`, indented, `Content-Disposition: attachment; filename="feeder-recipes-YYYY-MM-DD.feeder.json"` (clock date), `Content-Type: application/json`. Recipes in id order; archived ones included when asked for by id or `all`. Ingredient definitions: display name, Base Unit, Unit Conversions, Shelf Life, for every Ingredient used on a line or in a Step's `uses`. Images are loaded from the image store and embedded as `data:image/webp;base64,...`. The output is validated against the schema in tests.
- **Agent Prompt is built server-side** (`GET /api/recipe-file/agent-prompt` -> `{prompt}`), so the SPA bundle does not duplicate the schema and the example. The button fetches it and writes it to the clipboard.
- **Auth.** Everyone signed in may import and export (like Recipes). Only `GET /schema/recipe-file-v1.json` is public (the spec says the running app serves it; it is not secret).
- **Limits.** Upload body <= 64 MB (`recipefile.MaxFileBytes`; read with `http.MaxBytesReader`, because `httpx.DecodeJSON` stops at 1 MiB) -> `413 file_too_large`.
- **Placement in the SPA.** Routes `/recipes/import` and `/recipes/export` in the new feature `web/src/features/import`. The agent-prompt slot of `RecipesScreen` (T8's `<div data-slot="agent-prompt" />`) is replaced by `<RecipeFileActions />` (Import / Export links and Copy Agent Prompt). That one-line change in `web/src/features/recipes/screens/RecipesScreen.tsx` is the only edit outside this team's paths.

## API (JSON camelCase; errors `{"error":{"code","message",...}}`)

| Route | Result |
|---|---|
| `GET /schema/recipe-file-v1.json` (public) | the embedded schema bytes, `application/json` |
| `GET /api/recipe-file/agent-prompt` | `{prompt}` |
| `GET /api/recipe-file/export?all=1\|ids=1,2` | the file as a download; 400 `bad_request`; 404 `not_found` (unknown id); 422 `nothing_to_export` (`all` with no Recipes) |
| `POST /api/imports` `{text}` | 201 `{id, plan}`; 422 `invalid_recipe_file` (+ `error.errors:[{path,message}]`), `unsupported_version` (+ `error.version`), `invalid_json`; 413 `file_too_large`; 400 `bad_request` |
| `POST /api/imports/{id}/plan` `{decisions}` | 200 `{id, plan}`; 404 `not_found` (unknown, expired or not yours) |
| `POST /api/imports/{id}/confirm` `{decisions}` | 200 `{recipes:[{index,id,name,action:"created"\|"replaced"}], ingredientsCreated, conversionsAdded}` and the review is closed; 422 `import_not_ready` (+ `error.plan`); 409 `import_stale`; 404 |
| `DELETE /api/imports/{id}` | 204 (idempotent for an owned id; 404 otherwise) |

`plan` = `{ingredients:[IngredientMatch], unitPrompts:[UnitPrompt], recipes:[RecipeStatus], problems:[{path,code,message}], warnings:[{path,code,message}], ready}` (field lists in `internal/recipefile/plan.go` and `web/src/features/import/types.ts`). `decisions` = `{ingredients:[{key,action:"use"|"create",ingredientId?,name?,baseUnit?}], conversions:[{key,unit,toBase}], recipes:[{index,action:"replace"|"keep_both"|"skip"}]}`. Events: Confirm publishes `recipes` `{"id":n}` per Recipe written (the recipes feature's topic), and `ingredients` when Ingredients changed.

## Go layout
- `docs/spec/spec.go` (+ `spec_test.go`): embedded files.
- `internal/recipefile` (pure; imports `ingredient`, `recipe`, `units`, `imaging`, `clock`; no net/http, no database/sql): `file.go` (types), `parse.go` (`Parse`, `SyntaxError`, `VersionError`, `SchemaError`, `PathError`), `export.go` (`Build`, `Marshal`, `ExportFileName`), `plan.go` (`BuildPlan`, `BuildCommit`, `Decisions`, `Plan`, `Commit`, ...), `images.go` (`ResolveImages`, `Fetcher`, `ImageSet`), `prompt.go`, `session.go`. Tests: `parse_test.go`, `export_test.go`, `plan_test.go`, `images_test.go`, `prompt_test.go`, `session_test.go` (the spec example is the fixture, via `spec.Example`).
- `internal/recipefile/imagefetch`: SSRF-safe `Fetcher`. Tests with `httptest` TLS servers: `imagefetch_test.go`.
- `internal/recipefile/store`: `Existing`, `Exportable`, `Apply`, `ErrStale`, `ErrNotFound`. Tests: `store_test.go` (temp SQLite; all-or-nothing, replace keeps the id).
- `internal/recipefile/httpapi` (module `recipefile`) + `internal/modules/recipefile.go`. Handlers are thin. Tests: `httpapi_test.go` (testkit; round trip between two Feeders; SSRF end to end; per-User sessions).
- BDD: `bdd/features/import-export/{schema_and_prompt,export,import_review}.feature`, steps `bdd/steps_import_export_test.go` (`RegisterSteps("import-export")`; state in `w.Vars["rf-*"]`; `<id:name>` placeholders in decision JSON).

## Frontend (`web/src/features/import`)
- `index.ts` routes; `api.ts` (`importApi`); `types.ts`; `strings.ts` (glossary words only).
- `lib/` (pure, tested): `decisions` (immutable answer builders, `parseToBase`), `reviewSummary` (`reviewSteps`, `openCount`, `canConfirm`, `ingredientOptions`), `errors` (`readFileError`), `exportSelection`.
- `hooks/`: `useImportReview` (phase, plan, answers sent to `plan`, last request wins, confirm, reset, cache invalidation of `['recipes']`, `['ingredients']`, `['tags']`), `useExportPicker`, `useAgentPrompt`.
- `components/` (render + wire only, from `ui/` Tile, BentoGrid, Chip, Button): `ImportSource`, `ValidationErrorsTile`, `IngredientMatchTile`, `UnitPromptTile`, `RecipeConflictTile`, `ImageWarningsTile`, `ConfirmTile`, `ExportPicker`, `CopyAgentPromptButton`, `RecipeFileActions`.
- `screens/`: `ImportScreen` (source -> step tiles -> done), `ExportScreen`. Step tiles: errors (alert tone), Ingredients, Units, Recipe conflicts, Images (warnings), Confirm.
- `fixtures.test-helper.ts`: plan builders for the tests (not picked up by vitest).

## Known limits
- Reviews live in memory (a restart or 1 h idle drops them).
- Image downloads happen at upload time, one at a time, up to 50 per file, each limited to 15 s.
- EXIF orientation is not applied (as for uploaded photos).

## Test note: imagefetch timeouts
The two timeout tests no longer assert a wall-clock upper bound; handlers block until the client gives up (or the test ends) and the test checks `context.DeadlineExceeded`, with a 30 s watchdog only to catch a missing timeout.
The slow-body test uses a 2 s timeout and fails unless the response headers were delivered first, so it proves the timeout covers the body read; the implementation (one context for dial, redirects and body) was correct.
