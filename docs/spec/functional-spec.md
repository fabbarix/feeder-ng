# Feeder: functional specification (v1)

Status: **draft for review** (2026-11-09). The terms in **bold** are defined in [GLOSSARY.md](../../GLOSSARY.md). Decisions behind this spec are in [docs/adr/](../adr/), and look and feel in [docs/design/ux-brief.md](../design/ux-brief.md) (direction: Bento). The open points raised while writing this spec were resolved on 2026-11-09 (§15).

## 1. Scope

**In v1:** Household setup; Recipes with timed Steps and images; Ingredients, Products and Shops; Stock tracked as Stock Lots; Courses per Meal Slot and Whole meal Recipes (§3.1); the automatic planner with Leftovers; the Shopping List; in-store and home scanning (offline-capable); Cook Mode; the kitchen board; Recipe File import/export and the Agent Prompt; Web Push reminders; per-User theming; Google sign-in; nightly backups; a Docker image published to GHCR.

**Out of v1:** multiple Households per instance; external product databases; nutrition; calendar (ICS) feeds; receipt OCR; languages other than English (strings are externalised, so translations can be added later).

## 2. Users, roles and access

- Sign-in is Google OAuth only, and only for a verified Google email. A person signs in at once if their email is on the **allowlist** or is the email of a **Member**. Anyone else creates an **Access Request** and sees a "Waiting for approval" page, with no session and no access to any data. Any signed-in User can approve (adding a non-Admin User) or deny it; one approval is enough. A denied email may ask again after 24 hours; a request expires after 14 days. Requests are limited per IP (10 an hour), per email (3 a week) and in total (50 pending), and every approval, denial and expiry is recorded with who did it. Settings lists the pending requests, and a count badge shows on the avatar menu.
- The `FEEDER_ADMIN_EMAIL` environment variable is mandatory: the container refuses to start without it. It seeds the allowlist with the first **Admin**.
- **Admin** manages the allowlist, Members, Meal Slots, Courses, Weight Barcode Rules and household settings, and renames or deletes Shops. Every **User** can do everything else, including adding a Shop and saving its Shop Location (§5).
- A User may be linked to a **Member**. Any User may set any Member's Favourites, Dislikes and Exclusions; the Recipe detail shows the whole Household at once, the linked Member's row first (§4, *Preferences on a Recipe*).
- The Google sign-in redirect URI is `<FEEDER_BASE_URL>/auth/google/callback`.
- Sessions: an HTTP-only, SameSite=Lax cookie with a 30-day sliding expiry. Removing a User from the allowlist ends their sessions immediately.

## 3. Household setup

The Household records the moment it was created in Feeder (never edited, not a setting). It only feeds the zero-waste streak's age cap (§6.1). An install that predates this takes the earliest of its first User, Member or Stock Lot.

| Setting | Default | Notes |
|---|---|---|
| Time zone | from the browser at first setup | All slot times and reminders use it. |
| Planning Horizon | 7 days | 1–28. |
| Default Cool-down | 7 days | Recipes can override it. |
| Default Leftover Use-by | 3 days | Recipes can override it. |
| Frozen Use-by | 90 days | 1–365, Admin. How long a frozen Leftover keeps; a Recipe can override it ([ADR 0012](../adr/0012-leftovers-stay-leftovers.md)). |
| Quiet hours | 22:00–07:00 | No push notifications in this window, except timers. |
| Planner Style | Variety (middle anchor) | A single slider with three anchors: "Use what we have" (boosts perishable use, **Ingredient Overlap** and stock coverage), "Variety" (the default; leans furthest into recency and dampens Favourites) and "Favourites" (boosts Favourites). Each anchor maps to a weight preset, and positions between anchors interpolate linearly (§7.2). |
| Currency | USD | Admin-managed. Used for **Prices**, the estimated cost and price-valued Weight Barcode Rules. |
| Location | none | City or coordinates, set by the Admin. Used to compute local sunset and sunrise for the kitchen board's dark mode (§11). Without one, the board uses 19:00–07:00. |

**Members**: a name, a colour/avatar and a default **Portion Factor** (adult 1.0; any value from 0.25 to 3, in 0.25 steps). A Member may have an email; see §2. The avatar is a **photo**, an **emoji** or the Member's **initials**, the Admin's choice in the Member sheet ("Avatar: Initials, Emoji, Photo"). Wherever the avatar is drawn, the photo is shown first, then the emoji, then the initials; a photo that cannot be loaded falls back to the emoji, then the initials. The photo is added with the shared image picker (a square crop) and is stored as an image id (`photo`, with the read-only `photoUrl`); it is removed with the Member, and with it when the Admin switches the Member to an emoji or initials. Only an Admin can set it, like every other Member field.

**Meal Slots** are defined per weekday. Each has a name (e.g. Lunch), a usual time, the ordered **Courses** it serves (at least one; §3.1) and a default **Attendance** (which Members attend, each with an optional Portion Factor override). The same slot name can exist on several weekdays with different times or attendance. A one-off change for a specific date ("Sam is away Thursday") edits that date's Attendance only. Each Course the slot serves may be marked **optional**, and Members may opt out of a Course (**Course Attendance**, §3.1).

**Editing a Meal Slot on several days** (R15, ui-review-2 §3.7). The Meal Slot editor has an "Apply to" choice of weekdays (seven toggle chips, Monday first, plus the quick picks "All days with <name>", "Weekdays" and "Weekend"); it starts with the day being edited. The change (name, usual time, Courses, usual Attendance; only the fields the Admin changed) applies to the **Matching Meal Slot** on each chosen weekday: the Meal Slot with the same name. A chosen weekday without one is **skipped** (nothing is created). Before saving the editor lists what will happen ("Update Dinner on Mon, Tue, Wed", "Thu skipped: no Dinner"); after saving it says it again ("Updated Dinner on Mon, Tue, Thu. Wed has no Dinner, so it was skipped."). The edit is **all or nothing**: if any matching Meal Slot cannot take the change (for example a rename that clashes with a Meal Slot already on that weekday), none is changed. Adding a Meal Slot uses the same weekday chips. Editing no longer moves a Meal Slot to another weekday: add it there and remove the old one.

**The Meal Slots overview shows who attends.** Each Meal Slot shows its Attendance as Member pills (Member colour, avatar or initials, first name), four at most and "+N" for the rest. A Meal Slot nobody attends shows a "Nobody attending" warning pill that leads to choosing who attends. The overview is **one card per Meal Slot** (decision 45; [meal-slots-redesign.md](../dev/design/meal-slots-redesign.md), option B): the slot's usual time, Courses and Attendance, with the dates that differ from the usual shown read-only ("Dates that differ"); "usual" is the most common value across the weekdays, ties going to the earliest weekday. A plain User sees the cards read-only except **Change a date**, which opens the Date Attendance sheet. Every Meal Slot has an anchor (`/settings/meal-slots#meal-slot-<id>`), which Couldn't plan uses for "Choose who attends".

**Attendance defaults to everyone** (R13, decision 23). A new Meal Slot includes every current Member as attending, each at their own Portion Factor (no override), unless the request names an Attendance explicitly (an explicit empty list means nobody, a deliberate choice). A new Member is added to every existing Meal Slot's usual Attendance, including slots that were left empty. People opt out, in the Meal Slots editor (usual Attendance) or for one date (Date Attendance). Date Attendance overrides are never touched by adding a Member: a date the Household already edited keeps its list. Deleting a Member still removes them from every Attendance. When an existing install is upgraded, a one-off migration gives every Meal Slot that has no attendees all current Members (§15, decision 23); it runs once, automatically, and slots that already have attendees are left alone.

**A Meal Slot on one date** ([ADR 0014](../adr/0014-meal-slot-on-one-date.md)). Any User may, for one date from today on, mark a Meal Slot **Not served**, give it its own **time**, and set **Who's eating** (the date's Attendance, its Course opt-outs and its **Guests**). Settings > Meal Slots keeps the weekly set-up (Admin). A date's time is the slot's *effective time* wherever a slot time is read (§7, §8, §11, §12). **Guests** are a number from 0 to 20; each is one standard portion of every Course the slot serves that date, with no name and no preferences; Reset to usual Attendance sets them to 0 with the date's Members and Course opt-outs, and leaves Not served and the date's time alone. A date saved with no Member and no Guest is Not served (decision 37); a Meal Slot whose *usual* Attendance is empty stays Couldn't plan. A Meal Slot with Guests and no Member is served and planned with no preferences.

**Portions needed** for a Course of a slot = the sum of the Portion Factors of the Members in its **Course Attendance**, plus the date's Guests: the slot's Attendance (usual, or that date's) less the Members who opt out of that Course (§3.1). With no opt-outs, every Course needs the slot's portions. Each Course's Recipe cooks its own Batches for them (a Recipe's Yield is in its own standard portions, so a Side's Yield counts Side portions). Portion Factors stay per Member and slot; there is no portion size per Course.

### 3.1 Courses

A **Course** is one part of what a Meal Slot serves, filled by one Recipe ([ADR 0008](../adr/0008-courses.md)). The Household defines its own Courses, in an order, and flags one as the **main Course**.

- **The list.** Each Course has a name (1 to 40 characters, unique with case and spacing ignored: the key is `course.NameKey`, the name trimmed, inner whitespace collapsed and lower-cased, the same rule as `recipe.TagKey`; accents count, so "Purée" and "Puree" are two names), a position in the household order, the main flag on exactly one Course, and an archived state. At most 20 Courses are in the list (archived ones do not count). A new install, and an upgraded one, starts with **Main** (main), **Side**, **Starter** and **Dessert**, in that order.
- **What the order is for.** The household order is the order of Course chips in every picker and of a Recipe's Courses wherever they are shown. A Meal Slot keeps its own order for what it serves (Dinner = Main, Side), which is the order the Courses appear in on Today, the Plan, the board and in Cook Mode.
- **Settings > Courses** (Admin edits; every User may open it read-only), route `/settings/courses`, linked from the Settings index next to Meal Slots. One row per Course in household order: a drag handle (the shared Sortable, with keyboard moves), the name, a "Main" chip on the main Course, and what uses it ("12 Recipes · 5 Meal Slots"). Each row has an actions menu: **Rename** (inline, the same validation as adding), **Make main** (not on the main Course; moves the flag in one step, nothing else changes) and **Delete**. An **Add Course** field ends the list. Archived Courses sit in a collapsed "Archived Courses" section with **Unarchive**.
- **Delete** opens a crafted dialog. It names what changes: "Side is on 12 Recipes and 5 Meal Slots." It asks for a **replacement Course** (the shared Course select, default the main Course) for the Recipes and Meal Slots that have no other Course ("3 Recipes and 2 Meal Slots have only Side: give them Main"). It lists what goes: Planned Meals in that Course from today on (Pinned ones by date and Recipe) and Slot Rules on that Course. Then:
  - the main Course cannot be removed (`409 course_main`; in the menu, Delete says "Make another Course main first"), and nor can the last Course;
  - Delete is refused for a Course that any Planned Meal or Leftover has ever used (`409 course_planned`); the dialog then offers **Archive**, with the same replacement and the same list. An archived Course leaves the list and every picker, is taken off every Recipe, Meal Slot and Slot Rule, and is ignored by the planner; Planned Meals and Leftovers keep it and show its name in history. **Unarchive** puts it back in the list, last, without restoring it to any Recipe or Meal Slot;
  - a Course that was not planned is removed for good;
  - in both cases unresolved Planned Meals in that Course from today on are removed and the horizon is replanned, all in one transaction.
- **Rename** keeps every reference (all records point at the Course id). Renaming the main Course keeps its flag. A name already used is `409 course_name_taken`. An archived Course keeps its name, so its name cannot be reused either: the 409 then says the name belongs to an archived Course. The Archived Courses list on the same page has Unarchive; the form's own check says "There is already a Course with that name".
- **A Meal Slot's Courses.** The Meal Slot editor has a **Courses** field: the shared ordered Course picker. It shows the household's Courses as toggle chips (household order); the chosen ones are listed below in the slot's order, each with a drag handle and keyboard moves (Move up, Move down). At least one is required ("Choose at least one Course"); the main Course is not required. A new Meal Slot starts with the main Course. With the multi-day edit (R15) the Courses are one of the fields applied to each Matching Meal Slot, and only when the Admin changed them; the preview names removals ("Removes Side from Tue and Thu: 3 Planned Meals and 1 Slot Rule go"). Taking a Course off a Meal Slot removes that slot's unresolved Planned Meals in that Course from today on (Pinned ones are listed before saving), its Slot Rules on that Course and its Couldn't plan reasons for that Course, then replans; adding a Course replans to fill it. Cooked and Not cooked Planned Meals stay as history and still show on their date. The Meal Slots overview shows each slot's Courses under its name ("Main · Side · Dessert (optional)"), and "without Sam" after a Course someone opts out of.
- **Optional Courses** ([ADR 0008](../adr/0008-courses.md), point 7). Each chosen Course in the Meal Slot editor has an **Optional** switch, with the helper "Planned only when a Recipe fits without coming round too soon; otherwise left out, with no Couldn't plan". It belongs to that Meal Slot's Course, not to the Course: Dessert can be optional at a weekday Dinner and expected at Sunday Lunch. At least one Course of a slot stays required ("Keep at least one Course that is not optional"; `422 validation_failed`, `reason: courses_all_optional`); the main Course may be optional when another Course is required. A new Course added to a slot starts required. The multi-day editor applies it with the Courses. What it does is in §7.2 (step 0b).
- **Course Attendance** (ADR 0008, point 8). Under each chosen Course the editor shows **Who eats it**: the slot's usual attendees as Member pills, all on by default; turning one off records that Member as opting out of that Course ("Dessert · without Sam"). Only Members who attend the slot are offered; an opt-out of a Member who no longer attends the slot does nothing and is kept, so it applies again if they come back. A new Member opts out of nothing. The multi-day editor applies opt-outs with the Courses (a Member who does not attend the Matching Meal Slot is ignored there). **For one date**, the Date Attendance sheet (§3, "Sam is away Thursday") gains a **Courses** section when the slot serves more than one Course: per Course, the same pills over that date's Attendance; changing them records that Course's opt-outs for that date, which replace its usual ones on that date only, and **Reset to usual** on a Course drops them. Resetting the whole date (today's **Reset to usual Attendance**) also drops the date's Course opt-outs. Taking a Course off a Meal Slot drops its opt-outs, usual and per date, in the same save; reordering a slot's Courses, or any other edit of it (the multi-day editor included), keeps the opt-outs of every Course it keeps. Archiving or removing a Course drops its opt-outs everywhere, and the replacement Course starts with nobody opting out (it never takes over the removed Course's opt-outs). Course Attendance decides, per Course: its portions and Batches, its Leftover, whose Exclusions, Dislikes and Favourites count (an Exclusion of Sam's does not block a Dessert Sam does not eat), and the portions a Leftover must cover to fill it. A Course nobody eats on a date (everyone attending opts out) is left empty with no Couldn't plan (§7.2, step 0b).
- **Guests and Course Attendance.** Guests are not part of any Course Attendance: they add portions to **every** Course the slot serves on that date, including a Course every Member opts out of (which is then served, for the Guests) and including optional Courses (still planned only within the rules). They add no Exclusions, Dislikes or Favourites ([ADR 0014](../adr/0014-meal-slot-on-one-date.md), amending ADR 0008 point 8).
- **A Recipe's Courses** are set in the Recipe editor (§4). A Recipe has at least one Course.
- **Upgrade.** Migration 1400 seeds the four Courses, gives every existing Recipe and Meal Slot the main Course only (required, nobody opting out), puts every existing Planned Meal, Leftover, Couldn't plan reason and Slot Rule in the main Course, and marks every existing Ready Meal as a Whole meal (§4). It changes nothing else about Courses, so an upgraded Household plans as before until it adds Courses, except that Cool-down and Variety Rules now give way when too few Recipes fit (§7.2, [ADR 0009](../adr/0009-soft-cool-down-and-variety.md)), so cells that were Couldn't plan for those causes are filled.

## 4. Recipes

These fields mirror the Recipe File ([recipe-file.md](recipe-file.md)): name, description, **Yield**, Ready Meal flag, **Courses** (one or more), **Whole meal** flag, **Tags** (§4.1), Cool-down and Use-by overrides, **Reheat time** (optional, 1 to 30 whole minutes), **Frozen Use-by** (optional, 1 to 365 days; not part of the Recipe File), image, source, ingredient lines (for one **Batch**) and **Steps** (active, passive or **Advance Step**, with an optional duration, image, `after` dependencies and `uses`).

- **Total time** is the critical path of the schedule (recipe-file.md, *Steps and timing*), shown on Recipe tiles. Advance Steps show separately ("+4 h marinate").
- **Sort and Last cooked.** The Recipes list has a **Sort** select: Name (default), Last cooked longest ago first, Last cooked most recent first (`?sort=name|last_cooked_asc|last_cooked_desc`, kept in the URL and on the device). A Recipe not cooked yet comes first in "longest ago" and last in "most recent"; ties by name. **Last cooked** is the latest date of a Cooked fresh Planned Meal of the Recipe in any Course (a Planned Meal served from a Leftover does not count; the Planned Meal's date counts, not the day it was marked). Recipe tiles and rows say "Last cooked today / yesterday / Tue / 3 Oct" or "Not cooked yet"; the detail shows it in its facts.
- Recipes can be **archived**: they are excluded from planning but kept for history. Hard delete is only possible if the Recipe was never planned.
- A Recipe's **Reheat time** is optional. It is a whole number of minutes from 1 to 30; blank means not set. The Recipe editor shows it as a compact number field after the Use-by field. It is flat for the Planned Meal (it does not grow with the number of portions) and Reheat clamps it to its own 30 seconds to 30 minutes range. A value outside 1 to 30 is refused with `validation_failed`, `reason: reheat_invalid`, `field: reheatMinutes`.
- **Courses.** The Recipe editor has a **Courses** field after the Ready Meal switch: the shared Course picker in its unordered form (toggle chips in household order). At least one is required ("Choose at least one Course"); a new Recipe starts with the main Course. Recipe tiles and Recipe detail show the Courses as chips, and the Recipes list can be filtered by Course. The API takes `courseIds`; an empty list is `validation_failed`, `reason: courses_empty`, `field: courses`; an unknown or archived id is `reason: course_unknown`. A create without `courseIds` gets the main Course; an update without it keeps the Recipe's Courses.
- **Whole meal.** A switch, **Whole meal**, under Courses, with the helper "Planned as Main, it leaves the slot's other Courses empty" (naming the main Course). It is shown only while the Recipe's Courses include the main Course. While it is not shown, the editor sends back the stored value unchanged (a new Recipe sends `false`), so taking the main Course off a Recipe, or moving the main flag, never clears Whole meal silently; it applies again as soon as the Recipe is planned in the main Course. The server keeps `wholeMeal` as sent; a create without it is `true` for a Ready Meal whose Courses include the main Course and `false` otherwise, and an update without it keeps the stored value. Moving the main flag to another Course changes no Recipe: a Whole meal Recipe covers only where it is planned in the main Course (§7.2).
- **A Recipe that loses a Course.** Saving a Recipe without a Course it had (say Side):
  - its unpinned, unresolved Planned Meals in that Course from today on are removed and replanned (Course fit), the ones served from its Leftovers included;
  - its **Pinned** Planned Meals in that Course stay where they are: a Pinned Planned Meal is the User's choice, and Course fit is checked when a Recipe is placed, not afterwards. The planner never places it there again, and Swap offers only Recipes marked with that Course;
  - Cooked and Not cooked Planned Meals stay as history;
  - Slot Rules **by that Recipe** on that Course are removed in the same transaction (a rule's Recipe must be marked with its Course). The editor names them before saving ("Taking Side off removes the Slot Rule Friday Dinner · Side = rice"), from the Slot Rules it already loads; Slot Rules by Tag are not touched.
- **Ready Meal and Whole meal.** Marking a Recipe as a Ready Meal switches Whole meal on when its Courses include the main Course, unless the User already set Whole meal in this edit; the User can switch it off (a bought dessert or side). Unmarking a Ready Meal leaves Whole meal as it is. A Ready Meal is never Whole meal by rule, only by this default.
- Recipe editor: an ingredient line's unit is validated against the Ingredient's units, and an unknown unit prompts for a **Unit Conversion** inline.
- **Creating an Ingredient from a line.** The Ingredient picker of an ingredient line offers "Create Ingredient '<typed name>'" as its last option when the typed name matches no Ingredient exactly (case, accents and spacing ignored). It opens the New Ingredient sheet over the editor with the name filled in; the Recipe draft is kept untouched, with no navigation. Before creating, Feeder asks "Did you mean Garlic?" for a near match, using the same matching as Import Review, and offers to use the existing Ingredient. Saving creates the Ingredient, selects it on that line and puts focus in the line's quantity. A unit already on the line stays; if it is not convertible for the new Ingredient the usual inline **Unit Conversion** prompt follows on save. The Recipe editor needs a connection to save, so offline the option is shown disabled with the reason "Needs a connection to create an Ingredient".
- **A Ready Meal and its Ingredient.** Feeder keeps an Ingredient with the Recipe's name so the pack can be stocked and bought. Marking a Recipe as a Ready Meal puts that Ingredient on its one line: an existing Ingredient with the same name (case and spacing ignored) is used, never duplicated; otherwise one is created on save, with Base Unit piece and no Shelf Life. The line is 1 piece (an existing same-name Ingredient counted in g or ml is selected with its Base Unit and the quantity left for the User, as Feeder never invents a pack size). The editor says "Feeder adds an Ingredient called '<name>' so you can stock and buy it". The line follows the name until the User edits it. Renaming a saved Ready Meal offers to rename its Ingredient too (never done silently, and not offered if another Ingredient already has the new name). Unmarking a Ready Meal keeps its Ingredient and its line, which become ordinary and editable; a line that was only pending (nothing created yet) is dropped. The API takes a Ready Meal with no lines as "make the pack line": it applies the same rule, in the same transaction as the Recipe, and answers `validation_failed`, `field: lines`, `reason: ready_meal_unit` when the same-name Ingredient is counted in g or ml.
- **Preferences on a Recipe** (PT, [rx-pt.md](../dev/design/rx-pt.md) §5). The Recipe detail's **Preferences** Tile is a table with one row per Member and one column each for **Favourite**, **Dislike** and **Exclusion**, so the whole Household is seen at once; it replaces the "Preferences for" Member select and its three toggles.
  - Each row starts with the Member's Avatar and name; the Member linked to the signed-in User comes first, marked "You", then the others in Members order. Every User may change every row.
  - Each state cell is a toggle button (pressed when set) named "Sam: Dislike". A Member has one state per Recipe: tapping the set state clears it, tapping another replaces it. Changes save at once; a failed save is undone with a Toast ("Couldn't save Sam's Dislike. Try again.").
  - **An Exclusion via an Ingredient** (the Member excludes garlic and this Recipe has a garlic line, optional lines included) shows in the Exclusion column as read-only text, "via garlic", with no button, because it is changed on the Ingredient. When the Member also excludes the Recipe itself, the button stays and the cell adds "also via garlic". Favourite and Dislike stay usable in that row and are kept.
  - It is a real table (caption, column and row headers), works with the keyboard (Tab row by row, Enter or Space toggles) and a screen reader, uses no native control and fits a 360 px phone without horizontal scroll. A link to `/recipes/<id>#preference-member-<memberId>` scrolls to that Member's row and highlights it.
  - With no Members the Tile says so, with **Add Members** for an Admin.
- **Ingredient Exclusions on a Recipe.** Each Ingredient line on the Recipe detail shows the Avatars of the Members who exclude that Ingredient (three at most, then "+N") and a button, "Exclusions for garlic", that opens a dialog, "Who excludes garlic?", with one toggle per Member ("Sam: excludes garlic"). It acts for each Member, not for a chosen one.

### 4.1 Tags

A **Tag** is a name the Household gives Recipes ("fish", "pasta", "roast") so that Slot Rules and Variety Rules can refer to a group of Recipes ([ADR 0010](../adr/0010-tags-as-entities.md)). Each Tag has a **Tag colour**.

- **What a Tag is.** A name (1 to 40 characters; trimmed, inner whitespace collapsed, case kept) and a key, `tag.NameKey`: the name lower-cased, the same rule as `course.NameKey` (accents count, so "Purée" and "Puree" are two Tags). Two names with one key are one Tag. A Recipe carries at most 20 Tags, in its own order. A Tag may have no Recipe: it is still offered in the Tag field's suggestions and in the rule pickers, and it stays when its last Recipe loses it. Only Delete removes it.
- **Where Tags come from.** Settings > Tags (below); the Recipe editor's Tag field, where a typed name that matches no Tag creates one when the Recipe is saved; and Import and the Recipe Assistant, which match each name in the file to a Tag by key and create a missing one. Every new Tag, however made, gets the next colour (below) unless the Tags page chose one.
- **Tag colour.** One of ten: Tomato, Apricot, Mustard, Olive, Sage, Teal, Sky, Blue, Plum, Rose (palette ids `tomato` to `rose`, in that order). The **next colour** is the one the fewest Tags have, ties going to the first in that order, so the first ten Tags differ and colours repeat only from the eleventh. Each colour is a tinted pill with text in the same hue and a leading dot, in light and dark schemes (§14); the text reaches 7:1 against the pill and the dot 3:1. No colour is free-form, and status colours (spoil, leftover, pinned, success, danger) are not among them.
- **Settings > Tags** (any User), route `/settings/tags`, linked from the Settings index after Planning rules ("Tags", "Names and colours of Recipe Tags"). One row per Tag, by name: its pill, then what uses it ("12 Recipes · 1 Slot Rule · Variety Rule"; "No Recipes yet" when none). **Add Tag** ends the list. A Household with no Tags sees an empty state, "No Tags yet", with Add Tag. Tapping a row opens the **Tag sheet**:
  - **Name** and **Colour** (the shared Tag colour picker: ten swatches in a radiogroup, each named, the chosen one ticked) with a live preview of the pill. A new Tag starts with the next colour chosen.
  - **Save.** A name another Tag already has (same key) is refused on Add ("There is already a Tag called Seafood") and, on a rename, asks **Merge fish into Seafood?** (below). A new spelling of the same key ("fish" to "Fish") is an ordinary rename.
  - **Merge into…** opens the shared Tag select (every other Tag), then the same merge confirm.
  - **Delete** opens a crafted confirm (below), whose other action is **Merge instead**.
- **Rename** changes the name everywhere at once: Recipes show the new name, and Slot Rules and the Variety Rule on the Tag follow it in the same transaction (they name the Tag by its key). If rules already name the new key with no Tag behind them (possible until the `tag_unknown` check of §17 is in), they are treated as Merge treats the other Tag's rules: a repeated Slot Rule goes, and the Variety Rule already on the new key wins. Nothing else changes; the Tag keeps its colour. When a rule moved or went, the plan is updated as after a rule change (§7.1).
- **Merge fish into Seafood.** The confirm names what happens, from the impact of both Tags: "fish comes off its 12 Recipes and Seafood goes on instead (4 already have both). Slot Rule Friday Dinner · Main = fish becomes = Seafood. fish's Variety Rule goes, because Seafood has its own." Confirming, in one transaction: every Recipe with fish has Seafood instead, in fish's place in its order, once (a Recipe that had both keeps only Seafood, in Seafood's place); each Slot Rule on fish moves to Seafood, unless the same Meal Slot and Course already has a Slot Rule on Seafood, in which case it goes; fish's Variety Rule moves to Seafood when Seafood has none, and goes otherwise; fish is removed. Seafood keeps its name and colour. The plan is updated as after a rule change when a rule moved or went (unpinned Planned Meals are replanned, §7.1), and as after a Recipe change otherwise.
- **Delete fish.** The confirm names what goes: "fish is on 12 Recipes. Deleting it takes it off them." and, when rules name it, "These go too: the Slot Rule Friday Dinner · Main = fish; the Variety Rule for fish." Actions: **Delete** (danger), **Merge instead** (opens Merge into…) and Cancel. Confirming takes the Tag off every Recipe and removes those rules and the Tag, in one transaction, and the plan is updated: as after a rule change when rules went (unpinned Planned Meals are replanned, §7.1), and as after a Recipe change otherwise. Planned Meals are not touched directly.
- **Where a Tag pill shows, in its colour.** The Recipes list's Tag filter (an unselected filter shows the dot on a neutral chip; a selected one the tinted pill and a tick); Recipe tiles (the first two Tags of the Recipe, then "+N"); the Recipe detail, under the name (every Tag; each one opens the Recipes list filtered by it); the Recipe editor's Tag field (its chips, and a dot beside each suggestion; a typed Tag that does not exist yet shows as a neutral pill marked "New" until the Recipe is saved); the Tags page; and the Planning rules screen (the Tag select's options, and the Tag in each Slot Rule and Variety Rule row, shown by its name). Why chips stay neutral and name the Tag by its name: "3rd fish this week" (§7.2, step 5). The generated Recipe tile is unchanged (§14).
- **Copy.** UI text says Tag, Tags, Tag colour, Merge and Delete, and none of the words GLOSSARY lists under _Avoid_ for **Tag** and **Tag colour**.

## 5. Ingredients, Products, Shops

**Ingredient**: a name, **Base Unit**, Unit Conversions, an optional **Shelf Life** and an optional **picture**. Renaming an Ingredient keeps all its references. Two Ingredients can be merged (references move, conversions combine, and conflicts are shown).

The **New Ingredient** sheet asks for a name, a Base Unit (g, ml or piece, g unless a Recipe line or Scan already gave a unit) and an optional Shelf Life in days; the sheet also has an optional **Picture** (the shared image picker, 4:3 crop); everything else (Unit Conversions) is edited on the Ingredient's page, whose Picture Tile can add, replace, crop or remove it at any time, even while the Ingredient is in use (only the Base Unit locks). The Ingredients list shows the picture as a small thumbnail. A picture is stored as an image id (`image`, with the read-only `imageUrl`); replacing or removing it, merging the Ingredient away or deleting it removes the old file. When two Ingredients merge, the survivor keeps its own picture, or takes the merged-away Ingredient's when it has none. It validates inline instead of disabling its button, and asks "Did you mean ...?" before creating a name close to an existing Ingredient. It is opened from the Ingredients screen, from an ingredient line of the Recipe editor, and from the "what is this?" form.

**Who excludes an Ingredient.** The Ingredient's page has an **Excluded by** Tile (anchor `#exclusions`): one row per Member with a toggle, "Sam: excludes garlic", the same list as the dialog on a Recipe's Ingredient line (§4). A Member who excludes an Ingredient excludes every Recipe with a line of it, optional lines included (§7.2); Review Exclusions links here (§7.4.1).

**Product**: a name, the Ingredient it supplies, its pack size (in the Ingredient's Base Unit), optional global barcodes (EAN/UPC) and the Shops known to sell it. Products are created only through the "what is this?" form during scanning, or from an Ingredient's page.

A Product may also have one optional **Picture** (the same word as an Ingredient's; GLOSSARY: Photo), so a person in the shop can tell "Mutti passata" from "own-brand passata" at a glance. It is added with the shared image picker (4:3 crop) in three places: the **Product sheet** (the form that creates a Product from an Ingredient's page), the **Picture Tile** on the Product page (first Tile; it saves at once and may be changed or removed at any time, also while the Product is bought or archived) and the "what is this?" sheet (§10.1, also when the phone is offline). A scan that merges into an existing Product (§10.3) gives it the form's Picture only if the Product has none, and never replaces one. It is shown as a small thumbnail at the start of every Product row (the Products screen and an Ingredient's Products list) and of the scan line (§10.1); rows without a Picture keep the same empty slot so the names line up. A Picture is stored as an image id (`image`, with the read-only `imageUrl`, both always sent, `""` when none); `POST /api/products` takes `image`, and `PATCH /api/products/{id}` takes it presence-aware (absent keeps it, `""` removes it, an id sets it). An id that is malformed or was never uploaded is `400 invalid_product` on field `image`. Replacing or removing the Picture, or deleting the Product, removes the old file unless some other record still uses it; archiving keeps it. The nightly clean-up keeps every Product Picture (§13, §15).

**Shop**: a name. It has:
- **Shop Barcodes**: a code mapped to a Product, valid only in that Shop;
- **Weight Barcode Rules**: a barcode prefix (e.g. `21`), the digit positions of the item code, the digit positions of the value, whether the value is a weight or a price, its unit, and the decimal places. The unit is configured per rule: for a weight, g (default), kg, oz or lb; for a price, the household currency's minor unit (cents by default). The decoded value = digits ÷ 10^decimal places, in that unit. Internally all quantities are stored in metric Base Units (g, ml or piece) and price per weight is kept per kg. When the value is a price, the weight is derived from that Product's last known price per kg at that Shop. If there is no **Price** history, the app asks the user for the weight once, which also records the price per kg for next time;
- **Prices**: a Price for a Product at a Shop on a date. The latest one prefills the next scan.
- an optional **Shop Location**: where the Shop is (latitude and longitude, WGS84). It lets the phone pick the Shop the User is standing in.

**Adding a Shop.** Any User adds a Shop, from Settings > Catalogue, from the Shop select on the Shop screen ("Add Shop "Lidl"" for what was typed) or from the Scan picker ("Add the Shop I am in"). The User is assumed to be in the Shop: the **Add Shop** sheet asks the phone for its position as it opens and offers it with a switch, on by default, "Save this spot as the Shop's location". A fix less precise than 150 m is not offered ("too rough to save"); with location off or unavailable the Shop is added without one, and "Try again" is offered where a retry can help. Any User can also **Save my current location** on a Shop's page, which replaces the Shop Location. Only the Admin renames or deletes a Shop. `POST /api/shops` takes an optional `location: {lat, lon}`, `PUT /api/shops/{id}/location` saves one, and every Shop carries `location` (null when not saved); a latitude outside −90…90 or a longitude outside −180…180 is `400 invalid_shop`.

**Nearest Shop.** The phone compares its position with the Shop Locations; the nearest Shop within 200 m plus the fix's accuracy (at most 1 km) is the Shop the User is **in**. The position is asked for at once only where the browser already allows it (no prompt on load); otherwise only on a tap of **Find the Shop I am in**. The phone's position is never stored or sent; only a Shop Location the User chose to save reaches the server.
- **Scan picker** (§10.1): that Shop is listed first, marked "You are here · 40 m". A Scan session that started by itself with the last Shop used, while the phone is at another saved Shop, shows "You seem to be at Coop (40 m)." with **Switch to Coop**.
- **Shop screen** (§9): that Shop becomes the Shop the list is priced at, with a toast "Priced at Coop: you are 40 m away" and **Undo**. A tap away from every saved Shop says "No saved Shop is near you" and offers **Add it**.

**Archiving Products.** A Product that was bought (it has a purchase, or Stock Lots refer to it) cannot be deleted; delete answers `409 product_bought` and the UI offers **Archive** instead. A Product never bought can still be deleted. An **archived** Product (like an archived Recipe, §4) can be **unarchived** at any time. While archived it:
- is not shown in Product lists and pickers (the admin/catalogue view can include archived Products);
- is left out of the Catalog and of barcode resolution, so a Scan of its barcode is **unknown**; the online resolve names the archived Product so the app can offer "Unarchive?" before creating a new one;
- is never suggested as the Product last bought (§7.2, §9): the suggestion falls back to the next most recent non-archived Product, or to exact amounts if there is none;
- keeps its purchase history, Prices, barcodes and Shop Barcodes. It still **owns its barcodes**: a new Product (or another Product) cannot claim one of them (`409 barcode_archived`); the user unarchives the owner instead.
A purchase or Price that arrives late for an archived Product (an offline phone syncing) is still recorded.

**Barcode resolution** (at a Shop, in this order): that Shop's Shop Barcode → that Shop's Weight Barcode Rules → global Product barcode → unknown. When scanning at home (no Shop), only global barcodes apply.

## 6. Stock

- Stock is a set of **Stock Lots**. Each holds an Ingredient, a quantity in Base Units, a purchase date and a go-off date (purchase date + Shelf Life, or none). The source is a scan, a Stock-take or a manual entry.
- Lots are **added** by scanning at a Shop (pack size or decoded weight), by Stock-take, or by manual "add".
- Lots are **deducted** only when a Planned Meal is marked **Cooked** ([ADR 0003](../adr/0003-stock-lots-deducted-on-cooked.md)): Batches × ingredient quantity (optional lines excluded), taken from the lot that goes off soonest first, then the oldest, unless the User picks the Lots in **Used from** ([ADR 0011](../adr/0011-cooked-takes-from-picked-lots.md)). Marking as Cooked never blocks. If Stock is short, it warns (e.g. "Stock shows only 300 g chicken thighs, the recipe uses 800 g") and offers a one-tap Stock correction. If the warning is dismissed, Stock floors at 0 and the missing amount is ignored.
- **Storage Places** (the Pantry page). The Household keeps Stock in Storage Places such as Kitchen Pantry, Garage Fridge or Garage Freezer, each of one kind: pantry, fridge or freezer. Any User adds, renames, re-kinds and deletes them in Settings > Storage Places; one may be the **default**. A Stock Lot is in one Storage Place or **not sorted**; deleting a Storage Place leaves its Lots in Stock, not sorted.
  - **Where new Lots go.** A new Lot (scan, Stock-take increase or manual add) goes where that Ingredient was last put (the remembered place), else to the default Storage Place, else nowhere. A manual add may name a Storage Place, which then becomes the remembered one.
  - **Frozen Shelf Life.** An Ingredient may have a **frozen Shelf Life** (1 to 3650 days). A Lot added straight into a Freezer goes off at purchase date + the frozen Shelf Life. **Moving** a Lot into a Freezer (from any other kind, or from not sorted) sets its go-off date to today + the frozen Shelf Life; moving it out of a Freezer sets it to today + the ordinary Shelf Life. Without the Shelf Life that applies, the go-off date is unchanged, and so is any move between non-freezer kinds. Changing a Storage Place's kind moves no go-off date.
  - **Moving.** A Lot, or part of it, moves to another Storage Place (`POST /api/stock/lots/{id}/move` with `storagePlaceId` and an optional `quantity`); a part splits the Lot, the rest staying where it was with its go-off date. More than the Lot holds is refused.
  - **The Pantry page** (the Pantry tab of the bottom bar and side rail, route `/pantry`; `/stock` redirects to it). By default it lists every Stock Lot grouped by Storage Place (by name, "Not sorted" last), each row "1000 g · Good until Thu" with the Ingredient's Picture. Filters: search, All / Use soon / Spoiled, Storage Places (several, including Not sorted) and kinds; sort by good until (default), name, quantity, bought (newest) or Storage Place; a switch turns the grouping off (then each row names its place). "By Ingredient" shows the per-Ingredient totals as before; the device remembers the choice. Tapping a Lot opens it: its facts, **Move to** (a Storage Place and how much) with a note when the Freezer changes its go-off date, and the Ingredient's own sheet.
- **Stock-take** sets an Ingredient's total. A decrease removes quantity from the soonest-to-spoil lots first. An increase adds a new lot dated today.
- **Editing and deleting a Lot.** The Lot sheet has **Edit** (Quantity, Bought on not after today, Good until not before Bought on; changing Bought on suggests Good until again from the Shelf Life of the Lot's Storage Place kind, a Freezer using the frozen Shelf Life, unless Good until was changed in the same edit) and **Delete** ("for a mistake, like a double Scan; it does not count as waste"). An edit is a correction: no waste, no Keep; moving the Good until of a Lot that went off to a later day removes that go-off (the streak is recomputed), moving it earlier can make the Lot spoiled now. Delete removes the Lot and, like the Undo of a Scan, its go-off record (§6.1) and the Bought records of that Lot (§9). Storage Place is changed with Move to, not Edit.
- **By Ingredient** expands each Ingredient in place to its Lots in Deduction order ("Chicken thighs · 1300 g · 2 Lots"), each opening the Lot sheet.
- **Frozen Leftovers on the Pantry page.** A frozen Leftover (§8) shows in its Freezer's group, after its Lots, in the leftover tone ("Chilli · 3 portions · Use by 9 Feb"); a **Leftovers** filter chip shows only them; they are not in By Ingredient, Use soon or Spoiled, and sort by Use-by. A frozen Leftover whose Storage Place was deleted shows under "Not sorted". Tapping one opens the Leftover sheet. They are not Stock.
- Lots past their go-off date are listed as **spoiled** on Today ("Throw out or keep?"). "Throw out" removes the lot and records the waste. "Keep" pushes the lot's go-off date out by 1 day from its existing go-off date (not from today) and records the day it was chosen. Both feed the zero-waste streak (below). Throw out and Keep are offered only for a Lot that has gone off.

### 6.1 Zero-waste streak
The streak is the number of whole household days (household time zone, §3) since the last **waste event**, never more than the Household's age. It is shown on Today and on the Kitchen board (§11); both show the same number.

- **Go-off day.** A Lot is still fine on its go-off date; it **goes off** on the next household day (go-off date + 1), the first day it is listed as spoiled. A Lot with no go-off date never goes off.
- **Wording (GW).** Copy before the Lot has gone off names the last good day, the go-off date: "Good until today", "Good until tomorrow", "Good until Thu" (two to six days ahead; "Good until 20 Nov" from seven days ahead). This applies to Stock rows and Stock Lot chips, the Today Use soon tile ("Spinach · good until Thu") and the Stock about to spoil notification. Once the Lot has gone off, copy says "Went off today" (go-off date yesterday), "Went off yesterday", "Went off N days ago". Never write "goes off" for the go-off date itself.
- **Waste events.** A waste event counts on one household day:
  1. *A Lot going off.* The day it went off, whether or not anyone has acted on it yet. It counts the moment the day starts, so a Lot that went off today makes the streak 0 today.
  2. *A Throw out of a Lot that had already gone off* is the same event as (1): it counts on the day the Lot went off, **not** on the day of the Throw out. It is never a second event. So a Lot that went off Monday and is thrown out on Thursday resets the streak on Monday.
  3. *Waste of anything not covered by (1)*: a Leftover **thrown out** by hand (§8) counts on the day of the Throw; one answered *Threw it out* after its Use-by counts on the day after its Use-by; an unanswered one counts nothing, and *Had it* and *Wasn't there* are not waste; a Lot thrown out that was **not** an unforgiven go-off (see Keep) counts on the day of the Throw out. Waste of such a Lot on the day it is recorded makes the streak 0 that day.
- **The go-off persists.** Once a Lot has gone off unforgiven, the event stays on its day however the Lot later leaves Stock: Throw out (see 2), used up by a Cooked meal (Cooked deducts the soonest-to-go-off Lot first, so spoiled Lots go first), counted away by a Stock-take, or any other removal except Undo of a scan (a correction, not a go-off). A partly used Lot still counts once. The event is kept as a go-off record with no quantity: it is not waste and does not appear in waste lists or reports.
- **Keep.** Choosing Keep means the Lot did not go off: every go-off of that Lot up to and including the day of the Keep is forgiven, even when the pushed go-off date is still in the past (Keep moves it by one day only, so the Lot stays on the spoiled list and may be kept again). If the Lot then goes off again after the day of the Keep, that is a new waste event on that new go-off day. Throwing out a Lot whose go-off was forgiven counts as in 3, on the day of the Throw out.
- **Household age cap.** The streak is at most the number of days since the Household was created in Feeder (household date of creation, in the household time zone). Go-offs and waste dated before the Household existed (backdated purchase dates, imported dates) do not reduce it below the cap and never raise it above it. Purchase dates alone never lengthen the streak.
- **No Lots at all.** The streak is the Household's age: days since creation (0 on the creation day). Having no Stock is not waste.
- Waste events dated in the future are ignored. All dates are household dates, so around midnight the same instant can be two different days for two time zones.

## 7. The planner

### 7.1 When it runs
- Every night at 03:00 (household time), it fills the Planning Horizon.
- Immediately after any change that invalidates a plan: a Recipe edited or archived (its Courses and Whole meal flag included), Attendance or Course Attendance changed, a Meal Slot's Courses (or their optional flags) changed, a Course archived or removed, the main flag moved to another Course, a Planned Meal unpinned, a Cooked confirmation that changes the Leftover count, a Stock-take, a date marked Not served or served again, a date's time or Guests changed, a Leftover had, thrown out, frozen or taken out by hand, or a Lot edited or deleted.
- On demand: **Regenerate** redoes every unpinned, unresolved Planned Meal in the horizon.

It never changes **Pinned** or **Cooked** Planned Meals, and leaves **Bought** ones alone except on Regenerate ([ADR 0013](../adr/0013-bought-planned-meals-held.md)). A Planned Meal becomes Pinned when a User sets, swaps or confirms it.

### 7.2 Algorithm
The planner walks the empty **cells** in order, keeping a **projected Stock** (current lots, plus planned purchases, minus planned consumption) and a list of **pending Leftovers**. A cell is one Course of one Meal Slot on one date, the key of a Planned Meal: `(date, Meal Slot, Course)` ([ADR 0008](../adr/0008-courses.md)). Slots are taken in chronological order; within a slot, the **main Course** comes first when the slot serves it (it decides covering), then the slot's other required Courses in the slot's order, then its **optional** Courses in the slot's order (so an optional Course never takes what a required one could use). Everything below that says "slot" for a Planned Meal means its cell, and "attending" means the cell's **Course Attendance** (§3.1): the portions, Exclusions, Dislikes and Favourites of a cell are those of the Members who eat that Course.

For each cell:
0. **Covered.** If the slot's main Course on this date holds a Planned Meal (any state, fresh or from a Leftover) whose Recipe is a **Whole meal**, the planner removes the unpinned, unresolved Planned Meals in the slot's other Courses, and every other Course that then holds no Planned Meal is **covered**: the planner leaves it empty and records no Couldn't plan reason. A Pinned, Cooked or Not cooked Planned Meal in another Course stays as it is (a User may also set one there by hand), and that Course is **not covered**: it is shown, counted on the Shopping List and reminded about like any other Planned Meal, and it has no Couldn't plan reason because it is filled. If that Planned Meal is removed later (unpinned, or the Course is taken off the slot), the Course is covered again. A slot that does not serve the main Course is never covered.
0a. **Held cells.** A **Bought** Planned Meal (§9) is walked like a Pinned one (applied, not checked) unless the walk is Regenerate: the keep check and Slot Rule reservations pass over it (its relaxed flag and chip are recomputed, never replaced), `clearAll` keeps it, a Whole meal is not picked for the main Course beside a Bought Planned Meal in another Course, and one set by hand leaves it as a Course that is not covered. Batches follow portions (step 4).
0b. **Not served.** A cell is left empty with **no** Couldn't plan reason (`unserved` in the API, §16, §18), and any unpinned, unresolved Planned Meal in it is removed, when:
   - **the slot is Not served on that date** (marked by a User, or its date Attendance has no Member and no Guest): every cell of the slot is left empty (`unserved: "not_served"`) and its unresolved Planned Meals are removed, Pinned and Bought ones included after the dialog names them. Slots are walked in order of their effective time;
   - **nobody eats the Course**: the slot has attendees but every one of them opts out of this Course on this date and the date has no Guests (`unserved: "no_course_attendance"`); a Bought Planned Meal in such a Course is kept and shown, like a Pinned one. A slot nobody attends is not this case: each of its Courses is Couldn't plan with `no_attendance`, as before;
   - **an optional Course finds nothing within the rules**: steps 1 and 2 leave no Leftover and no strict candidate (`unserved: "optional"`). An optional Course is never filled by a relaxed pick (step 2b), and `no_course_recipes` is never recorded for it.
   A Pinned, Cooked or Not cooked Planned Meal in such a Course stays and is shown, as in step 0.
1. **Leftover first.** Take the pending Leftovers (not frozen, and not waiting for an answer after their Use-by, §8) whose Recipe is marked with the cell's Course (**Course fit**), that fully cover the slot's portions, are still before their Use-by, and have no attending Member with an Exclusion on that Recipe or its Ingredients. A Leftover is not tied to the Course it was cooked in: a soup cooked as Monday's Main may be Wednesday's Starter. If one exists and no Slot Rule claims the slot, place the one with the soonest Use-by. A Leftover may also fill a slot claimed by a Slot Rule if the Leftover's Recipe satisfies that rule (it is the named Recipe, or carries the Tag the rule names); otherwise the Slot Rule wins. Among several such Leftovers, the one with the soonest Use-by is placed. Dislikes are ignored for Leftovers. Two rules of step 2 apply to Leftovers too: a Leftover whose Recipe is already planned in another Course of the same slot on the same date is skipped (one Recipe fills at most one Course of a slot), and in the main Course a Leftover of a **Whole meal** Recipe is skipped while another Course of the slot on this date holds a Pinned, Cooked or Not cooked Planned Meal.
2. **Candidates.** Start from the non-archived Recipes marked with the cell's Course (**Course fit**), or only those of them a Slot Rule on this cell's Course names (by Recipe or Tag). If no non-archived Recipe is marked with the Course at all, a required cell stays empty with reason `no_course_recipes` (an optional one is not served, step 0b). Then apply the filters in this order ([ADR 0009](../adr/0009-soft-cool-down-and-variety.md)). **Hard** filters, which the planner never breaks:
   - already planned in another Course of the same slot on the same date (one Recipe fills at most one Course of a slot);
   - a **Whole meal**, when the cell is the main Course and another Course of the slot on this date holds a Pinned, Cooked or Not cooked Planned Meal (the User's choice there wins, so the planner does not cover it);
   - an Exclusion for a Member who eats this Course (on the Recipe or any of its Ingredients);
   - an Advance Step whose lead time has already passed for this slot.
   **Soft** filters, which give way in step 2b:
   - within its Cool-down (counted from the last planned or cooked date, in any Course);
   - would break a Variety Rule ("per week" means the ISO week, Monday to Sunday; every Course counts, so a fish Starter and a fish Main on one day are two; Leftovers don't count towards Variety Rules);
   - **reserved** for a later Slot Rule cell (see *Slot Rule reservation* below).
   Eliminations are counted by the first filter that removes a Recipe, in the order Exclusion, Advance Step, Cool-down, Variety Rule (reserved Recipes are not counted, as before). The Recipes that pass every filter are the **strict candidates**; if there are any, go to step 3.
2b. **Relaxed pick** (required Courses only). When no strict candidate is left but some Recipes passed the hard filters, the planner still fills the cell: it takes, from those Recipes, the first in this order, and marks the Planned Meal **relaxed**:
   1. not reserved for a later Slot Rule cell, before reserved;
   2. outside its Cool-down (only a Variety Rule is in the way), before inside it;
   3. among those inside their Cool-down: the longest gap in days to that Recipe's nearest fresh cook, before or after this cell, in any Course; then the fewest days of its Cool-down left;
   4. the fewest Variety Rules it would break;
   5. the highest score (step 3, jitter included);
   6. the lowest Recipe id.
   A relaxed pick is placed like any other (step 4) and counts towards later cells' Cool-down, recency and Variety Rules. Its why chips are step 5's, plus the relaxed chip. Only if no Recipe passes the hard filters does the cell stay empty (Couldn't plan, §7.4). So Cool-down and Variety Rules never leave a required Course empty; as the Household adds Recipes, step 2 finds strict candidates again and they hold.
   - **The keep check.** On every replan (not Regenerate, which redoes every unpinned Planned Meal anyway) the planner checks **every** unpinned, unresolved fresh Planned Meal it would keep, relaxed or not, **before the walk**: after Slot Rule reservations have dropped the kept Planned Meals they block, and once the remaining ones have joined the Cool-down, recency and Variety history. Each is checked against that history **with its own cook left out** (its own date must not count as a cook inside its own Cool-down, nor towards its own Variety Rule count), in walk order:
     - if it keeps every soft rule, it stays and is **not** relaxed (a former relaxed pick loses the flag and its relaxed chip);
     - if it breaks a soft rule and its cell has a strict candidate in that history (step 2's filters, with the same exclusion), it is dropped: its own cook leaves the history before the next one is checked, and the walk refills the cell (steps 1 to 4; if the walk's earlier picks have used up the strict candidates, the refill is a relaxed pick as usual);
     - otherwise it stays and is marked **relaxed**, with its relaxed chip computed from that history, so the why chip is always true.
     So the plan does not change for nothing, and a Planned Meal kept from an earlier plan never claims a rule it now breaks. A Pinned Planned Meal is never relaxed, even one chosen from a relaxed Swap alternative.
**Slot Rule reservation.** A Slot Rule's Recipe is kept for its cell. While the planner walks an earlier cell, it removes a Recipe R from the candidates if R is *reserved* for a later cell S and placing R here would put S inside R's Cool-down (the gap in days between the two cells is less than R's Cool-down; cells on the same day, and other Courses of the same slot, count as a gap of 0). S is a cell: the Meal Slot on a date and the Course the rule targets. A covered cell is not open, so it reserves nothing.
- **Which reservations exist.** S reserves R when S has a Slot Rule and R is the only Recipe it can still take: the rule names R directly, or the rules' Recipes and Tags together match exactly one eligible Recipe (not archived, marked with S's Course, no Exclusion for a Member attending S). When several eligible Recipes match (a Tag carried by two Recipes), nothing is reserved, because the others can fill S. S must still be open: a Pinned, Cooked or skipped meal in S reserves nothing. An unpinned Planned (kept) meal in S counts as open: it is replaced if the rule calls for it, so it still reserves.
- **Window.** The Cool-down of R before S, anywhere in the Planning Horizon, including slots whose meal Plan would otherwise keep: an unpinned Planned Meal of R inside the window is replanned, and its slot takes another Recipe. Regenerate behaves the same.
- **Pinned wins.** A Pinned or Cooked Planned Meal of R (or a cook before the horizon) already inside S's Cool-down means the rule cannot be met strictly, so no reservation is made and nothing else is held back. S is then filled by a **relaxed pick** of R (step 2b: R meets the rule and comes round sooner) instead of staying Couldn't plan (decision 30, amending decision 22). S is Couldn't plan only when R fails a hard filter (an Exclusion, or too late for an Advance Step). If two open Slot Rule slots reserve the same Recipe inside each other's Cool-down, the earlier slot gets it with a strict pick and the later slot gets a **relaxed pick** of it (step 2b: it is the only Recipe the rule allows, now inside its Cool-down), with its relaxed chip ("Again soon: had Tue"); the later slot is Couldn't plan only when the Recipe fails a hard filter there.
- **Swap.** Swap applies the reservation too: it does not offer R as an alternative for a slot where it would block S. For S itself Swap still ignores the Slot Rule (§7.3). Choosing a Recipe elsewhere (pinning it) always works, as above.

3. **Score** each candidate. The weights come from the **Planner Style** preset (table below). They stay internal (in code and tests); the household only sets the slider (§3), and positions between anchors interpolate linearly. Terms:
   - per attending Member's **Favourite**, per **Dislike**;
   - **× perishable use**: the share of the Recipe's base-unit needs covered by projected lots that go off before the next time those lots could be used, which rewards spending what would spoil;
   - **× Ingredient Overlap**: the share of needs covered by remainders of packs already planned for purchase in the horizon (e.g. the 600 g left from a 1 kg chicken pack);
   - **× stock coverage**: the share of needs covered by projected Stock overall;
   - **Leftover fits later slot / wasted**: + if the Batch surplus would fit a later cell as a Leftover (a Course the Recipe is marked with); − if it would be wasted (no cell fits before its Use-by);
   - **recency (per unit)**: weight × recentness, where recentness = 1 − min(days, 28) / 28 and days is the gap to the most recent fresh cook of that Recipe before the slot, in any Course (never cooked → 0 recentness). The weight is negative, so recently cooked Recipes lose points;
   - **jitter**: ± a random amount, seeded per generation and per cell (the Course is part of the seed) so that Regenerate gives a genuinely different plan.

   | Weight | Use what we have | Variety (default) | Favourites |
   |---|---|---|---|
   | per attending Member's Favourite | +2 | +2 | +5 |
   | per Dislike | −2 | −2 | −3 |
   | × perishable use | 6 | 3 | 2 |
   | × Ingredient Overlap | 3 | 1.5 | 1 |
   | × stock coverage | 2 | 0.75 | 0.5 |
   | Leftover fits later slot / wasted | +1 / −1 | +1 / −1 | +1 / −1 |
   | recency (per unit) | −0.25 | −1 | −0.25 |
   | jitter | ±0.5 | ±0.75 | ±0.5 |
4. **Pick** the top-scoring candidate. Batches = ceil(portions needed ÷ Yield), portions including the date's Guests. **Batches follow portions** for every unresolved fresh Planned Meal, unpinned, Pinned or Bought, whose Batches no longer cover its Course's portions (Guests, a Member joining, a Portion Factor change, Course opt-outs): it keeps its Recipe and gets Batches = ceil(portions ÷ Yield); fewer portions never lower Batches (the extra becomes Leftover). The surplus (Batches × Yield − portions needed) becomes a pending Leftover with its Use-by. Projected Stock is updated, and any shortfall is recorded as a planned purchase in pack units of the Product last bought for that Ingredient (at the chosen Shop if known). If no Product has been bought yet, exact amounts are assumed, with no pack remainder.
5. **Why chips** are the 1–3 largest positive score terms, phrased for people: "uses Monday's chicken", "Anna's favourite", "uses spinach by Thu" (the go-off date is the last good day), "Slot Rule: Friday", "leftover from Tue". A relaxed pick (step 2b) also carries one **relaxed chip**, which names the fact, never a vague quality ("best available" was dropped in QA round 1 for saying nothing): `cooldown_relaxed` with the nearest fresh cook's date, phrased "Again soon: had Tue" (before) or "Again soon: also on Thu" (after); or, when only a Variety Rule was broken, `variety_relaxed` with the Tag and the count or the adjacent day, phrased "3rd fish this week" or "fish two days running". Where it shows is in §7.5.

If no Recipe passes the hard filters, a required cell stays empty with a recorded reason (§7.4), keyed by date, Meal Slot and Course. The planner's reasons are `no_attendance`, `no_course_recipes` (new: no non-archived Recipe is marked with the cell's Course) and `no_candidates` (with the counts removed by Exclusion and Advance Step, and whether a Slot Rule claimed the cell; the Cool-down and Variety Rule counts are still sent but are always 0, because a Recipe removed only by them is a relaxed candidate). `no_attendance` is recorded for each Course of a slot nobody attends. Cells left empty by step 0 (covered) or step 0b (not served) have no reason.

**Courses in the planner, in short** (decision 29):

| Question | Rule |
|---|---|
| Which Recipes may fill a Course? | Only Recipes marked with that Course, fresh or as a Leftover (Course fit). |
| Variety Rules, Cool-down, recency | Per Recipe, across Courses. One Recipe fills at most one Course of a slot on a date. Cool-down and Variety Rules are soft: a required Course that only they would leave empty gets a relaxed pick (step 2b). |
| Optional Course | Planned from a Leftover or a strict candidate; otherwise left empty, no reason, never a relaxed pick. Walked after the slot's required Courses. |
| Slot Rules | Target one Course of a Meal Slot; the main Course unless the rule names another. A rule's Recipe must be marked with that Course. |
| Leftover first | Per cell, with Course fit on the Leftover's Recipe; not tied to the Course it was cooked in. |
| Reservations | Per cell (the rule's Course); other Courses of the same slot count as the same day. |
| Whole meal in the main Course | The slot's other Courses are covered on that date: not planned, not Couldn't plan. |
| Whole meal in another Course | An ordinary Recipe. |
| Attendance and portions | Course Attendance: the slot's Attendance less that Course's opt-outs; it gives the Course's portions, Batches, Leftover, Exclusions, Dislikes and Favourites. A Course nobody eats on a date is left empty, no reason. |
| No Recipe has the Course | Couldn't plan for that cell, cause "No Recipes for this Course" (§7.4); nothing for an optional Course. |
| Ingredient Overlap, projected Stock | Shared by all Courses: the walk order above decides which Course sees a remainder first. |

### 7.4 Couldn't plan (what the Household sees)
A required Course of a slot the planner left empty is something to set up or a conflict between rules, not an error. Reasons are recorded per cell (date, Meal Slot, Course); a covered Course (§7.2, step 0) and a Course not served (§7.2, step 0b: optional and nothing fits within the rules, or nobody eats it) have none. Cool-down and Variety Rules never leave a required Course empty ([ADR 0009](../adr/0009-soft-cool-down-and-variety.md)), so they are not causes any more. Today, the Plan and the kitchen board show it as a designed state:

- **Grouped by cause, never one line per slot.** Each cause is one compact tile: "Couldn't plan 9 Meal Slots. Nobody is set to attend." The affected Meal Slots are a short summary ("Every dinner this week, plus weekend breakfasts") with a "Show all 9" control that lists each one. For a cause that hits only some Courses of a slot, the list and the summary name the Course ("Friday Dinner · Side", "Side at every dinner this week"); a slot whose every Course has the same cause is named once, without Courses. Counts are of Meal Slots when the cause is Nobody attends (Attendance is per slot) and of Courses otherwise ("Couldn't plan 5 Sides"). "Every" is measured only over slots that still count (a Planned Meal or a recorded reason): a slot whose time has gone is not part of the week. A Household with several causes sees one tile per cause.
- **One fix action per cause**, a button that goes where the cause is fixed:

  | Cause | Shown when | Tone | Fix action |
  |---|---|---|---|
  | Nobody attends | reason `no_attendance` | info | **Choose who attends** (Meal Slots, Attendance) |
  | No Recipes | `no_candidates` and no Recipe was considered | info | **Add Recipes** |
  | No Recipes for this Course | `no_course_recipes` | info | **Mark Recipes as Side** (the Recipes list, filtered to Recipes not marked with that Course; each Recipe is marked in its editor) |
  | Slot Rule unmet | `no_candidates` and a Slot Rule claimed the slot | warn | **Review Slot Rules** |
  | Excluded | most options removed by an Exclusion | warn | **Review Exclusions** (the page that names the Exclusions, §7.4.1) |
  | Advance Step too late | most options removed by an Advance Step | warn | **Choose a Recipe** (pin one by hand) |
  | No fit | `no_candidates` with nothing counted | warn | **Choose a Recipe** |

  A slot is filed under one cause: the filter that removed the most options (ties: Exclusion, Advance Step). The former Cool-down and Variety Rule causes (and the **Review Cool-down** fix) are gone: their counts are always 0, and an SPA that still receives a non-zero one from an old stored reason ignores it until the startup replan rewrites the reasons.
- **Tone.** Missing setup and rule conflicts use the info and warn tones with an icon, never the danger colour; danger is for real failures (a request that failed, spoiled food).
- **A date emptied by hand is Not served, not Couldn't plan** (decision 37): "Nobody attends" applies to a Meal Slot whose *usual* Attendance is empty (set-up). A date saved with no Member and no Guest is Not served; a date with Guests and no Member is served.
- **On Plan** the grouped notice sits at the top and each affected day tile shows a small inline "Not planned" chip with the cause, on the Course's row. **On Today** the notice is a tile in the grid. **On the board** (read-only) an unplanned Course tomorrow shows "Not planned" on its row; there is no action.
- **First run.** While the Household is new and nothing can be planned (no Planned Meal and a setup step missing), Today shows a setup checklist instead of Couldn't plan: **Members**, then **Meal Slots and attendance**, then **Recipes**, then the first plan ("1 of 4 steps set up"). It goes away once a Planned Meal exists. Optional Courses and Course Attendance never make a step look missing: the Recipes step is done when any Recipe exists, as before.
  - **Exception (accepted at review).** When Members and Recipes exist and only attendance is missing, the checklist is not shown: Today shows Couldn't plan ("Nobody is set to attend", with **Choose who attends**), which names the missing step and fixes it directly. This is part of the checklist's visibility rule (one rule, so the tile and the Today layout cannot disagree).
- **Who can fix it.** Fixes that lead to an Admin-only page (Choose who attends, and the Members and Meal Slots checklist steps) are not offered to a plain User; the tile says "Ask an Admin".
- **After an upgrade.** Migration 1230 gives existing slots their attendees, but reasons recorded earlier would stay until the next replan, so the planner replans once at every startup (reason: Startup) and clears them.

### 7.4.1 Review Exclusions

**Review Exclusions** (RX, [rx-pt.md](../dev/design/rx-pt.md) §2 to §4) opens a page, `/plan/couldnt-plan/excluded`, that says which Exclusions left each Course empty and links each one to where it is changed. Every User may open it and follow its links (preferences are not Admin-only).

- **What the planner records.** For a cell it leaves Couldn't plan with Recipes removed by an Exclusion, the planner keeps, next to the counts, who excluded what: one record per Member and Ingredient ("Sam excludes garlic") and one per Member for Recipes excluded directly ("Alex excludes Fish pie"), each with the Recipes it rules out in that cell and how many. Only the Members who eat that Course count (its Course Attendance, §3.1): a Member who opts out of the Course is never named. A Recipe that two Exclusions rule out is under both. At most 8 records per cell (then "and N more Exclusions"), and at most 5 Recipes named per record (then "and N more"). Every replan rewrites it, so it follows every preference change.
- **The page.** A summary Tile repeats the Excluded tile's headline ("Couldn't plan 3 Sides. Every Recipe is excluded for someone who eats it.") and offers **Open the Plan** to choose a Recipe by hand. Then one Tile per explanation: cells explained by exactly the same Exclusions, for the same Members, share a Tile, named as the Couldn't plan summary names them ("Side at every dinner this week"), with "Show all N" listing each one ("Fri 13 Nov · Dinner · Side"). Each Tile shows **Who eats it** (Member pills) and, when someone opts out, "Kim opts out of Side, so Kim's Exclusions don't count here."; then the Exclusions, one row each, with the Member's Avatar:
  - "**Sam** excludes **garlic**: rules out 4 Recipes (Bolognese, Garlic bread, Pesto pasta and 1 more)", with **Review garlic**, a link to the Ingredient's *Excluded by* Tile (§5);
  - "**Alex** excludes **Fish pie**" (or "excludes 3 Recipes: Fish pie, Lasagne and Paella"), each Recipe a link to that Member's row of the Recipe's preference table (§4).
- **Which cells.** The cells filed under Excluded (§7.4: Exclusion removed the most options). The tile's "Show all" lines of the Excluded cause link to their cell on the page. Before the first replan after the upgrade a cell may have no detail yet; the page then says "Feeder is still working out which Exclusions these are. Check again in a moment."
- **Once it is put right.** The page follows plan changes live; when no Course is held back by Exclusions any more it says "No Course is held back by Exclusions now." with **Open the Plan**.
- **Other causes** have no such page (decided): Nobody attends and No Recipes for this Course already go straight to their fix, Slot Rule unmet names its rules, and Advance Step too late is solved by choosing a Recipe. Cool-down and Variety Rules are not causes ([ADR 0009](../adr/0009-soft-cool-down-and-variety.md)).

### 7.3 Swap
**Swap** works on one Course of a slot. Swapping a Bought Planned Meal is allowed; the sheet notes "You bought chicken thighs for this; it stays in Stock." It shows the top 3 alternatives under the same scoring (only Recipes marked with that Course; excluding the current Recipe, Recipes planned in another Course of the same slot and date, and any Recipe reserved for a later Slot Rule cell, §7.2), each with its why chips. The strict candidates come first; when there are fewer than 3, the list is filled with relaxed ones in the relaxed order (§7.2, step 2b), each with its relaxed chip ("Again soon: had Tue"), on every Course, optional ones included (the User is choosing). Exclusions and Advance Steps still apply. A chosen alternative is Pinned, never relaxed. On the main Course a Whole meal alternative carries a "Whole meal: no Side" chip naming what it covers. Choosing one pins it and replans the downstream unpinned cells, because Leftovers and Overlap may change. Choosing a Whole meal for the main Course removes the unpinned, unresolved Planned Meals in the slot's other Courses; Pinned, Cooked and Not cooked ones stay. Swapping a Whole meal in the main Course for an ordinary Recipe uncovers the other Courses, and the replan fills them.

### 7.5 Courses on Today, the Plan and the board
- **One Course looks as before.** A Meal Slot that serves one Course shows its Planned Meal exactly as it did, with no Course name.
- **Several Courses** show as one slot block: the slot name and time once, then one row per Course in the slot's order, each with the Course name as a small caption, the Recipe photo, name, state (Planned, Pinned, Cooked, Not cooked), why chips and its own actions (Swap, Pin, Mark as Cooked). The main Course row is the larger one. On Today the Tonight tile is the slot block; its main Course takes the hero picture and the other Courses are compact rows under it. **Cook** is one action of the slot block (it opens the slot's cooking timeline, §11), and the hero's "start 18:45" is the start of that timeline.
- **Course Attendance.** A Course row whose Course Attendance differs from the slot's says who does not eat it, after the Course caption: "Dessert · without Sam" ("without Sam and Ada"; "without 3" past two names). Its portions and Batches in the Planned Meal sheet are the Course's, and the sheet's Attendance avatars are the Course's attendees. A Course nobody eats on that date shows no row.
- **Optional and not served.** An optional Course left empty, and a Course nobody eats, show no row on Today, the Plan or the board, and no Couldn't plan chip. The slot menu (Plan and Today) offers **Add <Course>** for each Course the slot serves that is empty without a reason on that date (covered, optional or nobody eats it), which opens Choose a Recipe for that Course and pins the choice.
- **Relaxed picks.** The relaxed chip (§7.2, step 5) is a neutral why chip, never the warn or danger tone. The day tile's one chip shows it only when the Planned Meal has no other chip; the Today hero shows it after the positive why chips (at most 2, as now); the Planned Meal sheet always shows it, and adds one line under the chips: "Few <Course> Recipes, so this comes round sooner. Add <Course> Recipes for more variety." with **Mark Recipes as <Course>** (the Recipes list filtered to Recipes not marked with that Course, as the "No Recipes for this Course" fix) or, on a slot that serves one Course, **Add Recipes**. When only a Variety Rule gave way the line reads "Few Recipes without <Tag> fit here, so this breaks a Variety Rule." with **Review Variety Rules**. The board shows no chips, as now.
- **A covered slot** shows the main Course row with a "Whole meal" chip, and the covered Courses do not appear: no empty rows and no Couldn't plan chips. A Course of that slot that holds a Pinned, Cooked or Not cooked Planned Meal is not covered and shows as its own row, as in any slot.
- **A Course the slot no longer serves** still shows on a date where its Planned Meal was Cooked or Not cooked, as history.
- **Per-date slot controls.** The slot block's menu (Plan, from today on, and Today's Tonight tile; every slot, one-Course slots included) shows **Who's eating** (the Date Attendance sheet with its Courses section and the Guests stepper, date fixed), **Not served** and **Time today** / **Time on Thu**, whenever a per-date choice applies, beside Mark all Cooked, Not cooked: whole slot and Add <Course>. **Not served** asks first when something is planned there ("Not serving Thu Dinner? ... These go: ...", naming Pinned and Bought Planned Meals and what was bought), is offered only while no Course of the slot is Cooked or Not cooked, and toasts "Thu Dinner is not served. Undo"; the block then shows one row "Dinner · Not served" with **Plan Dinner again**, no Course rows and no why chips. **Time** shows "20:15 · usually 19:30" with **Back to 19:30**. Attendance pills end with "+2 Guests" and the sheet's attendees line reads "Anna, Sam + 2 Guests". Offline, the choices show "Needs a connection".
- **Bought.** A Bought Planned Meal shows a neutral **Bought** chip (only when the row has no other chip) and, in its sheet, "Bought for it: chicken thighs, cream. Automatic plan changes leave it as it is."; when it now breaks a hard rule (a new Exclusion, an archived Recipe, the Recipe lost that Course) its sheet says so ("Sam now excludes garlic, which this uses. Swap it to change it."), for Pinned ones too. Regenerate's confirm names the Bought Planned Meals it replaces.
- **The Planned Meal sheet** (Plan and Today) is per Course; its header names the slot and the Course ("Tue Dinner · Side"). The slot block has a slot menu with **Not cooked: whole slot** (every unresolved Course of that slot, "we had takeaway") next to each Course's own Not cooked.
- **Kitchen board:** the tonight tile lists the slot's Courses as rows in slot order (main Course first in size); tomorrow's tile writes each slot as "Dinner: Roast chicken + green beans"; a covered slot shows its Whole meal alone, plus any Course of it that holds a Planned Meal. The big Cook Mode button opens tonight's slot's cooking timeline (§11).
- **Slot Rules editor** (Plan > Rules): a rule picks a Meal Slot and then a Course of that slot (the shared Course select, limited to that slot's Courses, default the main Course); a Recipe rule offers only Recipes marked with that Course. A rule list row reads "Friday Dinner · Main = pizza".

## 8. Cooked and Leftovers

Everything in this section works on one Planned Meal, which is one Course of a slot (§7.2): each Course is marked Cooked or Not cooked on its own, deducts its own Stock, records its own Leftover (whose source is the date, Meal Slot and Course of the Cooked Planned Meal) and has its own Reheat.

- **Mark as Cooked** (from Cook Mode, Today or the Plan) shows the proposed Leftover portions (Batches × Yield − the Course Attendance's need), which the User can edit with a ± control. Confirming:
  1. deducts Stock (§6), from the Lots picked in **Used from** first: a collapsed row of the Mark as Cooked and Mark all Cooked sheets (per Course), "Soonest to go off first" by default, which lists each required Ingredient line with its Lots (with their Storage Places) in Deduction order so the User can pick the Lots and amounts actually used; the rest follows the default order;
  2. records the actual Leftover with its Use-by = cooked date + the Use-by days;
  3. replans: if the actual Leftover is smaller than what was already placed, the affected Leftover meals are unpinned and replanned; if it is larger, the extra becomes a pending Leftover.
- **Not cooked** ("we had takeaway") marks the Planned Meal as skipped: no Stock change and no Leftovers, and the Planned Meals served from its Leftover are replanned. **Not cooked: whole slot** does the same for every unresolved Course of that slot on that date, in one step. Not cooked on a Whole meal in the main Course does not uncover the other Courses: the slot was not eaten from the plan.
- A Planned Meal served from a Leftover that is due today offers **Reheat** on Today. Reheat opens a screen with a reheating timer scoped to that Planned Meal. The timer starts at the Recipe's Reheat time when it has one; otherwise at 2 minutes for one portion plus 1 minute for each further portion, at most 10 minutes. Either start is adjustable by 30 seconds, from 30 seconds to 30 minutes. Mark as Cooked then takes the portions off the Leftover and leaves Stock unchanged (Stock was deducted when the Batch was Cooked); like any Cooked or Not cooked, it cancels the Planned Meal's timers, the Reheat timer included. Leaving the screen early keeps the timer running and consumes nothing.
- A Planned Meal that is still unconfirmed 2 h after its slot time appears in Today's "To confirm" tile and triggers a reminder. The tile groups a slot's Courses under one heading ("Tue Dinner: Roast chicken, green beans"), each confirmed on its own, plus **Mark all Cooked**, which opens one sheet with each fresh Course's proposed Leftover (± each) and confirms them together. The same sheet ends the cooking timeline in Cook Mode (§11).
- **Leftovers by hand** ([ADR 0012](../adr/0012-leftovers-stay-leftovers.md)). From Today's Leftovers tile, the Planned Meal sheet and the Pantry (frozen ones), a User can: **Had it** (portions had outside the plan; not waste), **Threw it out** (waste dated today), **Freeze it** (to a Freezer; the default Storage Place if it is a Freezer, else the first by name; the Leftover or the part split off gets Use-by = today + its **Frozen Use-by**; not offered after the Use-by or without a Freezer) and, for a frozen one, **Take out** (not frozen; Use-by = today + the Recipe's Use-by days; it leaves the Pantry). When fewer portions are left than Planned Meals served from it need, the sheet names them and they are unpinned and replanned (rule 3 above).
- **Frozen Leftovers are not planned automatically.** They are used only when picked: Choose a Recipe lists them under "From the freezer"; choosing one pins it as a Leftover Planned Meal. Mark as Cooked takes the portions used and the rest stays frozen with its date.
- **Asking before waste.** Nothing is discarded at 03:00. A Leftover past its Use-by with portions left is **to answer**: the planner ignores it, and it heads Today's Leftovers tile ("Chilli was to be used by Tue. Had it, threw it out, or wasn't there?"): **Had it** (every portion left was had; not waste), **Threw it out** (waste dated the day after the Use-by) or **Wasn't there** (removed; not waste). It stays until answered and counts nothing, nor resets the streak, meanwhile. The Pantry badges frozen ones; the board shows "Chilli, Use-by passed" with no actions.

## 9. Shopping List

- **Range:** uncooked, non-skipped Planned Meals, including those whose slot has passed and that are not yet marked Cooked or Not cooked (a line whose need includes one says "Includes Tue Dinner, not marked Cooked yet" with **Mark it**, which opens that slot's Mark as Cooked sheet, or Mark all Cooked when it serves several Courses), up to a date the User chooses (default today + 7 days, capped at the horizon). Every Course counts: each Course is its own Planned Meal, so the Shopping List sums them all with no Course-specific rule. A covered Course has no Planned Meal and needs nothing; a Planned Meal kept beside a Whole meal (§7.2, step 0) is not covered and counts as usual.
- **Need** per Ingredient = the sum, over those meals, of Batches × quantity (converted to Base Unit, optional lines excluded). Leftover meals need nothing.
- **Available** = projected Stock lots still within their go-off date on the date each meal needs them.
- **Line** = need − available, if positive. Display: the quantity in Base Unit, plus a pack suggestion from the Product last bought for the Ingredient (at the selected Shop if known), e.g. "1400 g · 2 × Mutti 700 g". Packs are rounded up, and the expected remainder feeds Ingredient Overlap. If no Product has been bought yet, the line shows the exact amount with no pack remainder.
- **Manual extras:** a free-text line (e.g. "toilet paper"), or an Ingredient with a quantity. Neither is tied to the plan, and a manual extra stays until it's ticked or deleted.
- **Estimated cost:** the sum of suggested packs × the latest Price at the selected Shop (or any Shop if there's none at the selected one). Lines without a price show "—".
- The list recomputes live as the plan or Stock changes. Ticked state is kept per Ingredient for the current list range.
- **Tick by hand** (for weighed produce without a barcode, or items scanned elsewhere): it asks "how much?", prefilled with the line quantity, and adds a Stock Lot.
- **Not needed.** A line's menu has **Not needed**: the line leaves the list for the current range, adds no Stock and is not a purchase; a collapsed group "Not needed (2)" at the end lists them with **Needed after all**. They count neither in the progress nor in the estimated total and do not stop Shopping list complete. A new range shows the line again. A Scan of a Not needed Ingredient adds the Lot off-list; the line stays Not needed.
- **Bought for a Planned Meal** ([ADR 0013](../adr/0013-bought-planned-meals-held.md)). A purchase is a Stock Lot added through the list in Shop mode (a Scan that matched a list line, or a Tick by hand). The list is derived twice with the same range, without and with the new Lot, and the purchase is bought for each Planned Meal **whose slot (at its effective time, §3) has not yet passed** in the range by the amount its own shortfall went down, in date and time order. A fresh unresolved Planned Meal with such a record is **Bought** until it is resolved, removed or its Recipe changes, or the purchase is undone (Undo of the Scan, unticking, Delete of the Lot). Optional lines and Leftover-served Planned Meals are not bought for; purchases before the upgrade have no record.

## 10. Scanning

### 10.1 Shop mode
Started from the centre **Scan** button. It picks the Shop (the last one used, or one chosen from a list that leads with the Shop the User is in and lets any User add one, §5), then shows the compact viewfinder strip above the live Shopping List. Scanning is continuous; each successful read gives a short beep and a haptic buzz, with a per-device mute toggle. iOS Safari has no vibration API, so the beep is the confirmation there.

On a resolved barcode:
1. A Stock Lot is added (pack size, or the decoded weight).
2. The Product is recorded as sold at this Shop.
3. The matching Shopping List line's remaining quantity is reduced, and the line is ticked and slides away when it reaches ≤ 0.
4. A toast shows "Passata +700 g · $1.59 ✎ · Undo". The price is prefilled from the last Price at this Shop. Tapping ✎ edits it, and leaving it as is confirms it. Undo reverses steps 1–3.
5. Off-list items (including an Ingredient taken off the list as Not needed) are added to Stock just the same, with a toast saying "not on the list".

On an **unknown barcode**, a bottom sheet asks:
- which Ingredient it is (searchable, or create a new one);
- the pack size and unit;
- a Product name (prefilled as "<Ingredient> <size>");
- whether it's a global or a Shop-only barcode;
- an optional **Picture** of the pack (the shared image picker, 4:3). While the phone is offline the field stays: the picture is shrunk on the phone (long edge 1600 px, at most 2 MiB; no link, because the server fetches links), kept with the queued scan and uploaded when the phone syncs (§10.3).

Saving creates the Product (and Shop Barcode) and then proceeds as for a resolved barcode. A scan line shows the Product's Picture as a small thumbnail before its text: the scan result carries it (`productImageUrl`, absent when none) and the phone's offline data carries it per Product (`imageUrl`) so a queued scan shows it too. If the barcode was meanwhile created by someone else, the scan is merged into the existing Product (§10.3): the form's Picture fills it only when that Product has no Picture, and never replaces one; the notice then says the picture was added. A barcode matching a Shop's Weight Barcode Rule prefix whose item code is unknown asks only for the Ingredient and Product name.

When the list is empty, the **Shopping list complete** celebration appears with the number of items, the total spent and the number of Stock Lots added.

### 10.2 Stock-take mode
This is the same scanner without a Shop. Each scan opens a sheet with the Product and current Stock, plus **+1 pack**, **−1 pack** and **Set total**.

### 10.3 Offline and sync
- The PWA caches the app shell, the current Shopping List, Products with their barcodes, Shop Barcodes and Weight Barcode Rules.
- Scans made offline are queued with a client UUID and a timestamp, and applied in order when back online. The server is idempotent on the UUID.
- Unknown-barcode forms filled in offline are created on sync. If two people created the same barcode, the second is merged into the first, with a notice.
- A Picture picked on an unknown-barcode form while offline is queued with the scan (as a Blob in the phone's database, not in the scan itself). On sync, for each queued scan with a Picture, in order, the phone uploads the Picture first and then sends the batch with the returned image ids. An upload that cannot reach the server is retried with the same growing waits as a failed sync (1 s, 2 s, 4 s ... 30 s), and nothing is sent until it works. A Picture that can never be uploaded (too large, not a supported image, refused, or gone from the phone) is given up: the scan syncs without it and a notice says "The picture of <Product> ... so it was added without one". A scan whose uploaded Picture no longer exists on the server (cleaned up before the scan synced) is applied without the Picture too, never rejected. A phone with no room for the Picture queues the scan without it and says so.
- Live updates use Server-Sent Events (Shopping List, plan, Stock, timers), so two shoppers see each other's ticks within about 1 s.

### 10.4 Camera
The camera uses the `BarcodeDetector` API where available, otherwise a WASM fallback (e.g. ZXing). It needs HTTPS. A torch toggle is shown when the camera supports one. Formats: EAN-13, EAN-8, UPC-A, UPC-E, Code 128, QR and DataMatrix. QR/DataMatrix payloads that are GS1 Digital Link URLs are parsed for their GTIN (AI 01) and treated like an EAN/UPC. Other QR content is ignored with a "not a product code" toast.

## 11. Cook Mode and the kitchen board

- **Cook Mode opens for a Meal Slot on a date** (Cook on Today and the Plan, the board's button, the Start cooking reminder), or for a Recipe with a chosen Batch count (as before). For a slot it shows the **cooking timeline** ([ADR 0008](../adr/0008-courses.md), point 9): the Steps of every fresh Course still to cook (not Cooked, not Not cooked), plus the Reheat of each Leftover Course, interleaved into one sequence so that everything is ready together. A slot with one fresh Course and no Leftover Course shows that Recipe's own schedule (`schedule.Compute`), unchanged: the same Steps in the same order, the same planned times relative to the start, the same total time and so the same Start cooking time, as before. A slot whose unresolved Courses are all Leftovers opens Reheat (§8) instead, as before. Steps are shown one at a time, with the `uses` amounts scaled to the Course's Batches; each Step tile names its Course and Recipe in a small caption when the timeline has more than one Course ("Side · Green beans") and its planned clock time ("18:52", counted back from the slot time). The clock never holds Next: the cook may get ahead of the plan or fall behind it.
- **How the timeline is built** (`cook.Timeline`, a pure function in `internal/cook` with its own tests; the server sends the result, the SPA does no scheduling):
  1. *Items.* Each non-Advance Step of each fresh, unresolved Course, with its Course, its Recipe Step index, kind and duration. Each unresolved Leftover Course adds one **Reheat** item: passive, lasting its Reheat start (§8: the Recipe's Reheat time, else the portions rule). A fresh Course whose Recipe has no non-Advance Steps (a Ready Meal without Steps) adds one **Serve** item: active, no duration ("Tiramisu: ready to serve").
  2. *Rules:* the Recipe File scheduling rule ([recipe-file.md](recipe-file.md), *Steps and timing*) with one cook across Courses. Within a Course, a Step starts no earlier than the previous Step of that Course has finished (Active) or started (Passive), and no earlier than every Step in its `after` has finished. Across Courses, **no two Active Steps overlap**: there is one cook. Passive Steps and Reheat items overlap anything.
  3. *Each Course keeps its own schedule.* A fresh Course's Steps are placed exactly as `schedule.Compute` places them for its Recipe on its own (as soon as possible from its first Step), as one rigid block: the timeline only moves the whole block in time, never one Step inside it. A Course's **length** is its Recipe's total time (`Compute`'s total). A Reheat item and a Serve item are blocks of one item.
  4. *Placing the blocks, ready together.* All times are in seconds (Compute's minutes × 60; a Reheat moves in 30-second steps). The common end E is the slot time. Blocks are placed one at a time in this order: Reheat items first, then fresh Courses by longer length first, then the slot's Course order. Each block gets the **latest** position whose end is at most E and at which none of its Active items overlaps an Active item already placed (items are half-open intervals, so an Active item that ends when another starts does not overlap it, and a zero-length Serve item overlaps nothing). So the first fresh Course ends exactly at E, a Reheat item and a Serve item always end at E, and a Course whose Active Steps would clash with a Course placed before it is moved earlier, as a whole, by just enough to clear the clash. Such a position always exists (in the worst case the block sits wholly before every block already placed). The result is shifted to start at 0; its length is the slot's **timeline total**.
  5. *Guarantees:* (a) within each Course every Step keeps its planned time relative to that Course's other Steps exactly as `Compute` gives it, so Recipe order, `after` and the cook-free rule of the Recipe File hold inside each Course; (b) the cook never has two Active Steps at once (`Compute` never overlaps the Active Steps of one Recipe, and rule 4 never overlaps those of two); (c) no item ends after E; the first fresh Course, every Reheat item and every Serve item end at E, and every other Course ends as late as the Courses placed before it allow (one second later would end after E or clash); for example, when two Courses both end on an Active "serve" Step, the Course placed first ends at E and the other ends as that serve Step starts; (d) **with one fresh Course and no Leftover Course it is exactly `Compute`'s schedule**, shifted to end at E: the same planned times relative to the start, the same Step order on screen (Compute's starts never decrease in Recipe order) and the same total time, so a single-Course Household sees no change in Cook Mode, the Next gate or Start cooking; (e) it is deterministic. It does not promise the shortest total, and a Course may be moved earlier than a Step-by-Step interleaving would need: keeping each Course's own schedule whole is what makes (a) and (d) hold.
  6. *Why whole Courses, not single Steps.* Moving a single Step earlier would change its Course's planned times relative to `Compute` (the Recipe tile's total time, the Step's caption time, the gaps between a Passive Step and the Active Step that follows it), and a Step moved before the Step it follows in Recipe order would show out of order. Moving whole Courses keeps every Course's schedule as the Recipe defines it and still gives one cook and a common end.
  7. *Order on screen:* by planned start; ties by the slot's Course order, then the Recipe Step order. "Step 4 of 11" counts the whole timeline.
- **One Course on its own.** Under the header, filter chips list **All** and each Course in the timeline ("All · Main · Side"); All is the timeline. Choosing a Course shows only its Steps in Recipe order with its own position (what the single-Course Cook Mode was); the last of them offers **Mark as Cooked** for that Course. Every timer of the slot stays in the timer strip whichever chip is chosen. `/cook/meal/<date>/<slotId>` opens the timeline and `/cook/meal/<date>/<slotId>/<courseId>` opens it on that Course. This replaces the earlier Course switcher.
- **Timers and marks stay per Course.** A Passive Step's timer, and an Advance Step's done mark, use the scope of the Step's Course (`meal:<date>/<mealSlotId>/<courseId>`) and its Recipe Step index; the timeline has no scope of its own. So the same timer shows in the timeline and in the single-Course view, and reaching a Step on two devices still starts it once. A timer's label names the Recipe when the timeline has more than one Course ("Green beans · Simmer"). A Reheat item starts the same Reheat timer as the Reheat screen (§8), so the two never run twice.
- **Advance Steps** of every Course in the timeline are listed above it, grouped by Course, done ones as done and ones not done with a warning; they stay outside the timeline.
- **Cooked from Cook Mode.** The timeline's last item offers **Mark all Cooked**: the sheet of §8 (each fresh Course's proposed Leftover, ± each, and each Leftover Course's portions), confirmed together through `…/all/cooked`. The Course menu in the header offers **Mark <Course> as Cooked** and **Not cooked** for one Course at any time (a Side done early); that Course's remaining items leave the timeline and, as with any Cooked or Not cooked, its timers are cancelled. Cooked, Not cooked, Stock and Leftovers stay per Course (§8).
- Passive Steps start a **timer** when the Step is reached. Timers keep running across Steps and are shown as tiles, with an alarm sound plus a push notification when one ends. Timers are synced, so the phone and the tablet show the same timers.
- **Navigation:** Back/Next tiles; on a tablet, tapping the left or right half of the step tile also works. A Step starts only once every Step in its `after` has finished ([recipe-file.md](recipe-file.md)): while a timer of such a Step is still counting down (running or paused), **Next is held** (the tile, the tablet tap zone and the "next" voice command) and a line says what it waits for and how long is left, e.g. "Next waits for Step 1 · Pre-heat the oven: 4:12 left. Cancel its timer to go on now." A finished, dismissed or cancelled timer, or one that never started, holds nothing. The Cook view sends each Step's `after` (Recipe Step indexes) and, in the timeline, its Course's scope: Next is held only by timers of the same Course's `after` Steps (a Step never waits for another Course's Step; the cook-free rule across Courses is the plan, not a hold). Optional voice commands ("next", "back", "repeat", "start timer", "pause timer") use the browser's speech recognition where available, and are off by default.
- The screen stays awake (Wake Lock). The last Step offers **Mark as Cooked** (§8).
- **Kitchen board** (tablet, the `/board` route; Courses as in §7.5): a Bento grid with the clock, tonight's Planned Meals, the next Advance Step, Leftovers, use-soon lots, running timers, tomorrow's meals and the zero-waste streak. It refreshes live, switches to dark at local sunset and back at sunrise (computed from the household Location in §3, falling back to 19:00–07:00 if none is set), and has a big button to start Cook Mode.

## 13. Import and export

- **Export:** pick one or more Recipes, or all of them, and download a `.feeder.json` file with images embedded ([recipe-file.md](recipe-file.md)).
- **Import:** upload or paste JSON, then go through Import Review (recipe-file.md, *Import Review*).
- **Read a recipe from photos (Recipe Assistant).** On the Photo choice of "Read a recipe" a User adds 1 to 4 photos of a cookbook page or a handwritten card, in page order. On a phone, **Take photo** opens the phone's own camera app and **Choose photos** opens the photo library or files (several at once); Feeder shows no live camera view here. On a computer, photos are chosen from files, dropped or pasted (a pasted https link to a picture is also accepted). The photos are kept on the device, and sent nowhere before Read recipe, until the read is finished, so they come back if the phone unloads the page while the camera app is open; removing a photo clears it, and leaving the Import Recipes page or signing out clears them all. After each photo is added it opens in an editor, shown upright (its EXIF orientation applied): **Rotate left** and **Rotate right** turn it a quarter turn at a time, and a crop box of any shape is dragged by its edges and corners or moved and resized with the arrow keys (Shift for larger steps); a crop is at least 160 px on each side. **Use photo** keeps it; **Retake** (a photo just taken) or **Cancel** leaves it out or as it was. The photos are listed in page order; each can be moved (drag handle or keyboard), edited again from the photo as it was added, or removed. With 4 photos listed nothing more can be added; a pick of more than fit keeps the first ones and says so. **Read recipe** sends the photos as edited, in list order, each turned, then cropped, then shrunk so its longest side is at most 2,576 px, as JPEG (quality 0.9, lowered to no less than 0.6 while over 8 MB). A photo whose longest side is under 1,000 px is sent with a warning that its text may be hard to read. A picture the browser cannot show (a HEIC photo outside Safari) is accepted as it is, up to 8 MB: it is listed without a preview, skips the editor (it cannot be edited) and is sent as it is; the server turns it upright. A picture over 30 MB or 50 megapixels is refused. The server checks again (1 to 4 photos, each at most 8 MB) and keeps none of them unless the User chooses one as the Recipe's Photo in Import Review ([ADR 0006](../adr/0006-recipe-assistant-calls-anthropic-from-the-server.md), [ADR 0007](../adr/0007-heic-decoding-with-h265.md), [photo-read.md](../dev/design/photo-read.md)).
- **Tags in a Recipe File** stay names (`tags`, version 1): export writes each Tag's name, never its colour. Import matches each name to a Tag by `tag.NameKey` and creates a missing Tag with the next colour (§4.1); Import Review does not ask about Tags. The Recipe Assistant's schema and prompt do not change ([ADR 0010](../adr/0010-tags-as-entities.md), point 10).
- A Recipe's Reheat time travels in the Recipe File as the optional `reheatMinutes`; files without it stay valid (the format is still version 1).
- **Courses and Whole meal in a Recipe File** (decision 29; schema and recipe-file.md change with the code, team E of [crs-plan.md](../dev/design/crs-plan.md)). A Recipe gains two optional fields; files without them stay valid (still version 1):
  - `courses`: an array of Course **names** (strings, 1 to 40 characters, unique), written by the Recipe File in household order. Import matches each name to the Household's Courses by `course.NameKey` (case and spacing ignored, §3.1), archived Courses included (Import Review then offers to unarchive). **An unknown name** is shown on the Recipe's row in Import Review ("Soup is not one of your Courses") with the shared Course select: use an existing Course (default: the main Course), skip it, or, for an Admin only, **Add Soup as a Course**. Import does not create a Course without that choice. A Recipe left with no Course gets the main Course. A file without `courses` gives each Recipe the main Course.
  - `wholeMeal`: a boolean or `null`, with no schema default (like `cooldownDays`). Absent or `null` means `true` for a Ready Meal whose Courses (after matching) include the main Course, and `false` otherwise, the same default as the Recipe editor and the upgrade. An explicit `false` or `true` is kept.
  - The Agent Prompt gains two rules: list the household's Course names (the copied prompt fills them in; `{{COURSES}}`) and ask the AI to pick one or more of them for each Recipe; and set `wholeMeal` true only for a Recipe that needs no other Course beside it (a one-pot Recipe, a Ready Meal that comes with its sides), false for a bought dessert or side, and null when the source does not say.
  - **Recipe Assistant.** Its output schema is the projection of the Recipe File schema, in which every property is required ([ADR 0006](../adr/0006-recipe-assistant-calls-anthropic-from-the-server.md), `internal/recipeassistant/outputschema.go`). So the projection gains `courses` (array of strings) and `wholeMeal` (`anyOf` boolean or null, projected from the canonical `["boolean","null"]`) as required on each Recipe, with no enum (the schema stays the same for every Household; the household's names reach the model through the prompt). The model's "none" for them is `[]` and `null`; `pruneNone` (`internal/recipeassistant/none.go`) drops both, because both fields are optional in the canonical schema, so the import defaults apply. A `false` is not "none" there (`isNone` treats only null, blank text, empty lists and objects and a plain-number 0 as none), so it is kept as an explicit "not a Whole meal". The addendum's "none" sentence stays as it is (it already covers lists and nullable fields).
- A Product's Picture is not part of a Recipe File (it holds Recipes and their Ingredients, not Products).
- An Ingredient's picture travels in the Recipe File as the optional `image` of its definition (a data URL on export, a data URL or https URL on import, handled like a Recipe photo); files without it stay valid (still version 1). Import gives the picture to an Ingredient it **creates**, and to an Ingredient the Household already has that has **no picture**; an existing picture is never replaced. Import Review says so on the row ("Adds a picture to Garlic"). Nothing else about an existing Ingredient changes except the missing Unit Conversions it adds. A picture that cannot be fetched is dropped with an `image_failed` warning at `$.ingredients[i].image`. Member photos are not part of a Recipe File.
- **One image path.** Every image field (Recipe photo, Step photo, Ingredient picture, Product picture, Member photo) uses the same image picker and the same server endpoints (`/api/images`); a scripted guard (`image-input` in `scripts/check-ui.sh`) fails the build when a screen builds its own image input. The nightly clean-up keeps every image that a Recipe, Step, Ingredient, Product or Member uses (§15, decision 25).
- **Copy Agent Prompt:** copies the prompt template with the schema and example inlined.

## 19. Base recipes (Scheduled for beta.6)

**Scheduled for beta.6. Nothing in this section is in beta.5**, and §1 to §18 describe beta.5 without it. When beta.6 ships, this section is folded into §4, §6, §7.2, §8, §9, §11 and §13. Decision 46; [ADR 0015](../adr/0015-base-recipes.md); design: [base-recipes.md](../dev/design/base-recipes.md).

**What a Base recipe is.** A Recipe marked **Base recipe** in the Recipe editor. Its **Yield** is an amount with a unit (`g`, `kg`, `ml`, `l`, `dl`, `cl`, `tsp`, `tbsp`, `cup`, `piece` or `portion`; 0 < Yield ≤ 100000). It has no Courses, Whole meal, Ready Meal, Cool-down, Use-by, Reheat time or Frozen Use-by; Tags are allowed. It is never planned, chosen, swapped, Pinned or named by a Slot Rule (it fits no Course). The Recipes list hides Base recipes unless the **Base recipes** filter is on (`?kind=base`); they have no Last cooked and no sort.

**Its Ingredient.** Feeder keeps an Ingredient for each Base recipe (told apart from a same-name Ingredient by a Base recipe badge). When a plain Ingredient already has the Base recipe's name, Feeder asks whether the Base recipe takes over that Ingredient, naming the Recipes it is on and its Stock: Yes makes all its lines Base recipe lines and Stock carries over; No keeps it apart, and the Base recipe gets its own Ingredient. Not offered when that Ingredient is already some Base recipe's, or is a Ready Meal's Ingredient: there is no take-over and the new Base recipe must get a different name (refused with `ready_meal_base_recipe` or `base_recipe_name_taken`). A Base recipe's Ingredient, taken over or its own, is keyed by its Base recipe and not by its name, so a plain Ingredient with the same name can exist beside it, also after a Yes; the picker, quick create and Import Review find both, the User always confirms, and only an exact name match is preselected (the Base recipe preferred). Marking a Recipe as a Ready Meal whose name matches a Base recipe's Ingredient is refused (`422 ready_meal_base_recipe`, "A Base recipe already uses that name"); a Ready Meal cannot be turned into a Base recipe. Renaming a Base recipe to the name of an existing plain Ingredient asks the same question, with the same confirm: Yes takes that Ingredient over and merges the Base recipe's former Ingredient into it (its Stock carries over); No keeps them apart, and since the Base recipe's Ingredient does not key on the name there is no name collision. The Ingredient has a `batch` Unit Conversion equal to the Yield. A bought jar or a frozen batch is a Stock Lot of that Ingredient (Scan, Stock-take, Products, Shelf Life, Storage Places and Used from work as for any Ingredient). The Ingredient follows the Base recipe's name and cannot be deleted or merged away; another Ingredient may be merged into it.

**Base recipe lines.** A line of a Base recipe's Ingredient, for one Batch, in any unit that converts ("500 ml", "1 batch"). In the Recipe editor a Base recipe is picked in the same ingredient picker, shown with a **Base recipe** badge; the detail links to it. Its Base recipe's Ingredients scale by amount ÷ Yield; the Recipe's Batches multiply on top; Step durations are not scaled. A Base recipe may call for other Base recipes; a cycle is refused (`422 base_recipe_cycle`, "Béchamel calls for Roux, which calls for Béchamel"). A Base recipe with no Ingredients yet counts as its own Ingredient everywhere.

**Linking existing lines.** A plain line gets **Link to a Base recipe** (editor and detail): a picker with search lists Base recipes, name matches first, offers to add a new Base recipe from the line's name, and lists Recipes the Household plans, which are turned into Base recipes only after a confirm. Quantity and unit carry over; the old Ingredient is kept and remembered, so **Undo** and **Use as a plain Ingredient** restore the line. When a Recipe becomes a Base recipe and did not take over a same-name Ingredient, Feeder lists the other Recipes with an Ingredient of the same name, nothing ticked, and links only the ticked lines; once no line uses the old Ingredient it offers to merge it. Nothing is linked silently.

**Exclusions and the planner.** Every Ingredient inside a Base recipe, at any depth, counts for Exclusions, Review Exclusions and Leftover first as if it were on the Recipe. A Base recipe's Preferences offer only **Exclusion**, stored as the Exclusion of its Ingredient. The planner's scores treat a Base recipe as made from scratch.

**Stock first.** The Shopping List draws a Base recipe line from Stock of its Ingredient first and lists only the Ingredients of the part Stock does not cover. **Mark as Cooked** deducts the same way (Used from can pick the jar).

**Cooking timeline.** A Base recipe's Steps join the Recipe's Steps in Cook Mode, labelled with its name, placed where the Recipe's total time is shortest and ending before the Step they are **Needed at** (by default the first Step that uses or names it, else the first Step; the editor can pick another). A part covered by Stock shows no Steps. Total time on Recipe tiles includes Base recipes made from scratch.

**Turning a Recipe into a Base recipe** (and back). After a confirm that names them, its Planned Meals from today (Pinned and Bought included) and its Slot Rules are removed; Cooked history stays; its Leftovers stay until answered. A Base recipe that any Recipe calls for cannot become plannable again or be deleted (`409 base_recipe_in_use`); it can be archived and keeps working inside those Recipes.

**Import.** Recipe File v1 gains optional `baseRecipe`, `yieldUnit`, and on lines `recipe` (`{ name, cue }`) and `neededAtStep` ([recipe-file.md](recipe-file.md), *Scheduled for beta.6*). The Recipe Assistant marks lines that call for another recipe; Import Review asks for each such line, and for lines named like an existing Recipe, whether to use a Base recipe, use one from the same import, add a new one, turn a planned Recipe into one (after a confirm) or keep a plain Ingredient (a name that matches both a Base recipe and a plain Ingredient offers both). Only an exact name match is preselected (the Base recipe preferred), and Confirm waits for every other answer.

**API.** `GET /api/recipes?kind=plannable|base|all` (default `plannable`); Recipe `baseRecipe`, `yieldUnit`, `usedBy`, `within`; line `id`, `baseRecipe`, `neededAtStep`, `neededAt`; `POST /api/recipes/{id}/to-base` (`?dryRun=1`), `POST /api/recipes/{id}/to-plannable`; `POST|DELETE /api/recipes/{id}/lines/{lineId}/base`; `GET /api/recipes/{id}/link-candidates`, `POST /api/recipes/{id}/link`, `POST /api/recipes/{id}/unlink`; Ingredients gain `baseRecipe`; cook Steps and timeline items gain `baseRecipe`. Errors: `base_recipe_cycle`, `base_recipe_in_use`, `base_recipe_ready_meal`, `ready_meal_base_recipe`, `base_recipe_name_taken`, `ingredient_name_taken` (when a Base recipe turned plannable again would share a plain Ingredient's name), `base_recipe_field`, `yield_unit_invalid`, `needed_at_step_invalid`, `base_unit_in_use`, `line_not_plain`, `line_not_base`, `base_recipe_ingredient`. Details: [base-recipes.md §10](../dev/design/base-recipes.md#10-api).
