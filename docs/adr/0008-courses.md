# A Meal Slot serves ordered Courses, each its own Planned Meal; a Whole meal in the main Course covers the rest

Status: **Accepted** (2026-11-11). Spec: [functional-spec §3.1, §7, §8, §16 and decision 29](../spec/functional-spec.md). Plan: [docs/dev/design/crs-plan.md](../dev/design/crs-plan.md).

Until now a Meal Slot on a date held exactly one Recipe: one Planned Meal per `(date, Meal Slot)`. A Household that eats a Main with a Side, or a Starter and a Dessert at Sunday Lunch, had to fold them into one Recipe or leave them out of the plan, the Shopping List and the Stock maths. Feeder now has **Courses**:

1. **One Planned Meal per `(date, Meal Slot, Course)`.** The Household defines its Courses in Settings, with an order (seeded: Main, Side, Starter, Dessert). A Recipe is marked with one or more Courses; a Meal Slot lists the Courses it serves, in its own order (Dinner = Main, Side). Each Course of a slot on a date is its own Planned Meal: planned, swapped, Pinned, marked Cooked or Not cooked, and with its own Batches, Leftover and Reheat. The Planned Meal key gains the Course, and so do every record keyed by it: Leftover sources, Couldn't plan reasons, Slot Rules, Cook Mode timers and Advance Step marks, and the reminder keys. A Course is filled only by a Recipe marked with that Course (**Course fit**), fresh or as a Leftover.
2. **Whole meal.** A Recipe may be marked **Whole meal** (a one-pot Recipe, most Ready Meals): a Recipe that needs no other Course beside it. When the Planned Meal in a slot's **main Course** is a Whole meal (fresh or from its Leftover), that slot's other Courses **that hold no Planned Meal** are **covered** on that date: the planner leaves them empty, removes any unpinned, unresolved Planned Meal there first, and records no Couldn't plan for them. Covered is derived from the main Course's Planned Meal and the other Course's emptiness; it is not stored. Pinned, Cooked and Not cooked Planned Meals in the other Courses stay (a User's choice wins), and a User may still set (and so pin) a Recipe in one of them. Such a Course is **not covered**: it is shown, counted on the Shopping List and reminded about like any other Planned Meal, and it never has a Couldn't plan reason. While one exists the planner does not pick a Whole meal (fresh or Leftover) for that slot's main Course. In any Course other than the main Course a Whole meal Recipe is an ordinary Recipe.
3. **A Ready Meal maps to Whole meal by default, not by rule.** Ready Meal does **not** imply Whole meal, for two reasons: the flag is needed anyway for one-pot Recipes that are not Ready Meals (a stew, a traybake), so it exists on its own; and a Ready Meal in the main Course may still want a Side (a frozen pizza with a salad), which a rule would make impossible to plan. So Whole meal is its own stored flag, and marking a Recipe as a Ready Meal switches it on when the Recipe's Courses include the main Course; the User can switch it off. On upgrade every existing Recipe gets the main Course, and every existing Ready Meal is marked Whole meal, because until now a Ready Meal was the whole slot. A Recipe File without `wholeMeal` follows the same default.
4. **The main Course is a flag on one Course.** Exactly one Course carries it (a partial unique index), seeded on Main. It is what Course-less data falls back to (existing Recipes, Meal Slots and Slot Rules on upgrade; a Recipe File without `courses`; an unknown Course name at Import Review, unless the User picks another) and where Whole meal applies. **Renaming** it changes nothing else: every record points at the Course id. It **cannot be removed** while flagged (`409 course_main`): the Admin first gives the flag to another Course (**Make main**), which moves the flag in one step and changes no Recipe, Meal Slot or Planned Meal. Whole meal Recipes then cover only when planned in the new main Course.
5. **Removing a Course** (Admin, Settings > Courses) follows the Archived pattern of Recipes and Products:
   - The main Course and the last Course cannot be removed.
   - A Course that **any Planned Meal or Leftover** refers to (any state, past ones included) cannot go for good: Delete answers `409 course_planned` and the UI offers **Archive** instead. An archived Course leaves the Courses list, every picker and the planner, and is taken off every Recipe, Meal Slot and Slot Rule; its history keeps its name, and it can be unarchived (it comes back to the list, not to the Recipes and Meal Slots it was taken off).
   - A Course that was not planned is removed for good.
   - In both cases the Admin picks a **replacement Course** (default: the main Course) for the Recipes and Meal Slots that would be left with no Course; Recipes and Meal Slots with other Courses just lose it. Unresolved Planned Meals in that Course from today on are removed and their slots replanned; Pinned ones are listed in the dialog before it is confirmed. Slot Rules on that Course are removed and listed too. All of it is one transaction.
6. **Planner semantics.** The planner walks `(date, Meal Slot, Course)` cells: slots in time order, and within a slot the main Course first (it decides covering), then the slot's other Courses in the slot's order. Cool-down, recency and Variety Rules count a Recipe across Courses (it is the same Recipe in any Course), and one Recipe fills at most one Course of one slot on one date. Slot Rules target one Course of a slot. Leftover first works per cell, with Course fit and the same two rules as fresh Recipes: one Recipe per slot and date, and no Whole meal in the main Course while another Course of the slot is Pinned, Cooked or Not cooked. Attendance is per slot and the same for each of its Courses, so each Course needs the slot's portions and cooks its own Batches. Details are in the spec, §7.2.

**Considered options**

- *Keep one Planned Meal per slot and give it several Recipes* (a list of Recipe ids on the Planned Meal): fewer key changes, but Pinned, Cooked, Swap, Leftovers, Reheat, Cook Mode and Stock deduction all work on one Recipe today; each would need a per-Recipe state inside one row, which is the same model with a worse shape. Rejected.
- *Model a Side as Ingredients of the Main* (or a "with" link between Recipes): no planner change, but the Household cannot vary the Side, plan a Dessert, or keep a Side's Leftover. Rejected.
- *Courses as Tags* ("side" Tag plus Slot Rules per Tag): no new concept, but a slot would still hold one Recipe, and Tags are free names created on first use, not an ordered household list with a main one. Rejected.
- *A Course list built into the code* (Starter, Main, Side, Dessert): simpler migrations, but the user decided the Household defines its own (Soup, Salad). Rejected.
- *Ready Meal implies Whole meal*: what the user first suggested, and no new flag to set. Rejected because the Whole meal flag is needed anyway for one-pot Recipes that are not Ready Meals, and because a Ready Meal in the main Course may still want a Side (a frozen pizza with a salad). Kept as the default instead (point 3).
- *Main Course by position* (the first Course in the household order is main): no flag, but reordering the list in Settings would silently change which Recipes cover a slot. Rejected in favour of an explicit flag.
- *Main Course by name* ("Main"): breaks on rename and on other languages. Rejected.
- *Whole meal covers when planned in the slot's first Course* (per slot, not the household flag): handles a slot without the main Course, but then a slot's Course order changes the planner's meaning. Rejected: one rule, one main Course.
- *Variety Rules and Cool-down per Course*: lets the same Recipe be a Starter today and a Main tomorrow, but that is exactly what Cool-down exists to stop, and a per-Course count would double every Tag limit. Rejected. (An optional per-Course *default* Cool-down, still counted across Courses, is a separate open question: plan Q1 and spec §7.6. It is not part of this decision.)
- *Leftovers tied to the Course they were cooked in*: simpler matching, but a soup cooked as Monday's Main is a fine Starter on Wednesday. Rejected in favour of Course fit on the Recipe.
- *Removing a Course with history for good* (reassigning old Planned Meals to the replacement): would collide with the `(date, Meal Slot, Course)` key where the replacement was planned too, and rewrites history. Rejected for Archive.
- *Per-Course Attendance* ("Sam skips dessert"): left out for now (open question in the plan); Attendance stays per slot.

**Consequences**

- Two migrations, in the same release. **1400** rebuilds `planned_meals`, `plan_unfilled` and `slot_rules` with the Course in their keys (keeping `planned_meals`' AUTOINCREMENT counter, so no Planned Meal id is handed out twice), adds the Course to Leftovers and cook scopes, seeds the four Courses, gives every Recipe, Meal Slot and Slot Rule the main Course and marks Ready Meals Whole meal. **1410** rewrites the stored reminder keys; it ships with the notification change that writes the new keys, so the two never disagree. Neither can be undone; going back means restoring the snapshot `feeder-pre-1400.db` taken before 1400 and starting the image that ran before (plan, *Migration*).
- Every plan route gains a `{courseId}` segment; the course-less routes stay as aliases for the main Course only while the SPA moves over, and are removed before the release (the SPA ships in the same binary). The slot-wide actions get new paths (`…/{slotId}/all/not-cooked`, `…/all/cooked`), so a cached old SPA can never mark a whole slot by calling an old path. Plan, Today and board payloads carry a `courses` list per slot.
- Cook Mode scopes become `meal:<date>/<mealSlotId>/<courseId>`; Start cooking reminders are per Course, Confirm Cooked stays one per slot.
- The Recipe File gains the optional `courses` (Course names) and `wholeMeal` (boolean or null, no default; null means absent); it stays version 1, and files without them import as above. The Recipe Assistant's output schema is a projection of the Recipe File schema, so it gains both as required properties; the model says "none" with `[]` and `null`, both pruned, so the import defaults apply.
- The Shopping List needs no new rule: it sums every Planned Meal, so every Course.
- A slot whose main Course is a Whole meal shows the covered Courses as part of that Planned Meal, not as empty or Couldn't plan; a kept Planned Meal in another Course of that slot shows as its own row, as usual.
